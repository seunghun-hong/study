[학습] kotest — 세 모듈로 나뉜 Kotlin 테스트

kotest 가 Kotlin 테스트를 어떤 모양 — 스펙 안의 테스트 함수 · matcher · property 테스트 — 으로 쓰게 하고, 그 모양을 쓸 때 kotest 문서가 무엇을 조심하라고 적었는지 안다.

읽는 사람 — 배우는 사람 — Kotlin 이나 Java 로 서버를 만들고 JUnit 으로 단위 테스트를 써 본 개발자. kotest · MockK · ArchUnit 은 써 본 적이 없거나 이름만 들었고, 헥사고날 아키텍처 · 피처 플래그는 말만 들어 봤다. 0편(지도)을 먼저 읽고 필요한 편을 골라 읽는다.

정의 스펙(spec)과 테스트 스타일(testing style)

스펙은 테스트 함수를 담는 클래스로, 특정 테스트 스타일을 구현한 상위 클래스를 상속해 만든다. 스펙 안에서는 kotest DSL — 테스트 함수를 만들고 겹쳐 두는 함수 모음 — 으로 테스트를 만든다.

테스트 스타일은 테스트를 정의하는 방식이고, 스타일 사이에 기능 차이는 없다.

정의 matcher

matcher 는 특정 검사를 하는 assertion 을 부르는 kotest 의 말이다. double 이 0 보다 큰지, 파일이 비지 않았는지를 확인하는 함수 하나하나가 matcher 다.

정의 property 테스트(property testing)

property 테스트는 같은 테스트에 값 수백 · 수천 개를 넣고, 그 값은 대개 프레임워크가 무작위로 만든다. 입력 몇 개와 기대 결과를 직접 고르는 보통의 단위 테스트와 다른 점이다.

이 편은 kotest 문서를 아래 다섯 단계로 따라간다.

이 편을 읽는 순서
  1. 1 스펙과 테스트 테스트가 스펙 안의 함수라는 것과 스타일 9개가 쓰는 키워드를 본다찾을 것 — 기능이 같은 스타일을 무엇으로 고르나 테스트 함수 — 이름과 람다가 테스트 하나다테스트 스타일 — 기능이 같아 읽히는 모양으로 고른다
  2. 2 테스트 사이의 상태 — 전환점 테스트 앞뒤 함수와 스펙 인스턴스를 만드는 방식을 본다. 테스트 하나의 모양이 여러 테스트 사이의 상태 문제로 꺾이는 자리다찾을 것 — 스펙 본문의 mock 이 왜 둘째 테스트의 검증을 깨나 lifecycle hook — 테스트와 스펙 앞뒤에 함수를 건다isolation mode — 기본은 스펙 인스턴스 하나다mock 쓰기 — 인스턴스가 하나면 mock 도 하나다
  3. 3 여러 입력과 확인 입력 세트마다 테스트를 만드는 법과, 값 · 예외 · 시간을 확인하는 도구를 본다찾을 것 — 실패를 모으는 블록에 다른 라이브러리의 검사를 어떻게 넣나 withXXX 함수 — 행마다 테스트를 만든다matcher — 확장 함수와 infix 두 형식예외 확인 — 블록을 감싸 던졌는지 본다soft assertion — 실패를 모아 끝에 알린다
  4. 4 만든 입력 프레임워크가 만든 입력을 1000번 넣고, 실패하면 그 입력을 줄인다찾을 것 — 실패한 입력을 왜 줄이고 어떤 순서로 줄이나 test function — 성질을 람다 하나로 적는다generator — Arb 는 무작위로 Exhaustive 는 전부shrinking — 테스트를 깨는 가장 작은 입력을 찾는다
  5. 5 바깥 도구 · 비교 · 한계 가상 시계 · Spring · 6.0 기능을 보고, JUnit · AssertJ 와의 비교와 문서가 적은 한계를 모은다찾을 것 — 테스트를 메서드로 가정한 도구가 어디서 걸리나 TestDispatcher — 가상 시계로 delay 를 건너뛴다Spring 확장 — 생성자 주입과 테스트 이벤트JUnit · AssertJ 와 비교 — kotest 문서가 든 차이한계 — kotest 문서가 적은 경고와 제약
흐름이 꺾이는 곳은 둘째 단계다 — 기본값에서 모든 테스트가 스펙 객체 하나를 나눠 써서, 스펙 본문에서 만든 mock 이 다음 테스트로 호출 기록을 넘긴다.

실행 환경가상 시계로 delay 를 건너뛰고, Spring 이 만든 객체를 생성자로 받는다Spring 의 테스트 이벤트는 테스트를 메서드로 가정해, 함수로 겹치는 kotest 테스트와 하나씩 맞지 않는다
JUnit · AssertJ 와 비교Java 에서 넘어오는 사람에게 kotest 의 장점을 든다장점만 들고, 단점은 기능마다의 경고에 흩어져 있다
한계기능마다 경고를 달고, 6.0 의 깨지는 변경을 따로 적는다Gradle 은 중첩 스타일에서 맨 끝 테스트의 이름만 보고한다

답을 모으면 두 문장이다 — kotest 의 테스트는 스펙 안에서 DSL 로 만든 Kotlin 함수이고, 통과 · 실패는 그 함수 안의 assertion 이 던진 예외가 정한다. 조심할 곳은 모든 테스트가 나눠 쓰는 기본 스펙 객체와, 테스트를 메서드로 가정한 바깥 도구다.

3스펙과 테스트 — 테스트는 스펙 안의 함수다

이 절의 목표 kotest 의 테스트가 스펙 클래스 안 DSL 로 만든 함수이고, 스타일 9개는 키워드만 다를 뿐 기능이 같다는 것을 안다
왜 여기 있나 앞 절의 답은 테스트가 스펙 안의 함수라 했지만, 그 함수가 어떻게 생기고 어떻게 겹쳐지는지는 아직 비어 있다. Writing Tests 쪽과 Testing Styles 쪽이 그것을 채운다.

여기서 읽을 것 — 테스트 하나가 무엇으로 이루어지고 통과 · 실패가 어디서 정해지는지, 테스트를 겹치고 실행 중에 만드는 법을 본다.

kotest 의 테스트는 테스트 로직을 담은 함수 하나다. 그 함수는 kotest DSL 로 만들고 겹쳐 두는데, 대부분의 스타일이 테스트를 겹치게 해 주고 스타일마다 다른 것은 바깥 테스트를 만드는 키워드뿐이다.

정의 컨테이너 테스트와 leaf 테스트

컨테이너 테스트는 다른 테스트를 담을 수 있는 테스트이고, 끝에 놓인 leaf 테스트는 test case 라 부른다.

leaf 테스트는 다른 테스트를 담지 못하는 끝 테스트다. 둘 다 테스트 로직과 assertion 을 담는다.

테스트 스타일 — 기능이 같아 읽히는 모양으로 고른다

여기서 읽을 것 — 스타일 9개가 무엇이 같고 무엇이 다른지, 기능이 같은데도 스타일을 여럿 두는 까닭과 그래서 무엇으로 고르는지 본다.

스펙은 스타일 하나를 구현한 상위 클래스 — FunSpec · DescribeSpec · BehaviorSpec 같은 것 — 를 상속하고, init { } 블록 안에서 테스트를 만든다. 스타일마다 테스트에 이름을 붙이고 겹치는 키워드가 다르다 — FunSpec 은 test 를, DescribeSpec 은 describe · it 을, BehaviorSpec 은 given · when · then 을 쓴다.

kotest 문서는 스타일 사이에 기능 차이가 없다고 적는다. 어느 스타일이든 threads · tags 같은 같은 종류의 설정을 받고, 테스트를 어떻게 짤지는 취향의 문제라는 것이다. 그런데도 스타일이 여럿인 까닭은 같은 쪽에 있다 — 일부는 다른 인기 테스트 프레임워크를 본떠 그 프레임워크를 쓰던 사람이 익숙하게 느끼게 했고, 일부는 kotest 가 새로 만들었다.

주의 키워드가 걸리는 두 곳

BehaviorSpec 의 when 은 Kotlin 키워드라 backtick 으로 감싸거나 Context · Given · When · Then 같은 대문자 변형을 쓴다. Then 범위에는 Gradle 버그 때문에 and 범위가 없다.

테스트를 끄는 모양도 비슷하다 — 끄기 변형을 적은 스타일 6개는 xtest · xcontext 처럼 키워드 앞에 x 를 붙이고, 끈 컨테이너 테스트 안의 테스트도 함께 꺼진다.

Testing Styles 쪽 안에서 어긋나는 두 곳

Testing Styles 쪽 머리는 스타일이 8가지라 적지만 테이블과 절은 9개다. String Spec 절은 문자열 뒤에 테스트 블록을 붙인 root 테스트를 말하는데, 그 절의 예는 FreeSpec 처럼 - 로 컨테이너를 겹친 코드다.

그래서 기능이 같다는 것이 고를 때 좋은 점이다. 어느 스타일을 골라도 잃는 기능이 없으니 남는 기준은 테스트가 읽히는 모양이고, 팀에 익숙한 프레임워크의 말을 쓰거나 테스트 내용에 맞는 모양을 고르면 된다. 망설여지면 kotest 문서의 권고대로 FunSpec 을 쓰고, StringSpec 대신에는 같은 문법에 겹치기까지 되는 FreeSpec 을 쓴다 — 한 스타일로 정하든 섞어 쓰든 옳고 그름은 없다고 적는다.

4테스트 둘레 — hook 과 isolation mode 가 정하는 상태

이 절의 목표 lifecycle hook 과 isolation mode 가 테스트 사이 상태를 정하고, 기본값 SingleInstance 에서 스펙 본문의 mock 이 테스트 사이에 남는다는 것을 안다
왜 여기 있나 앞 절은 테스트 하나의 모양을 보였다. 테스트가 여럿이면 그 사이에 남는 상태가 문제가 되고, kotest 문서는 그 상태를 테스트 앞뒤에 도는 함수(lifecycle hook)와 스펙 인스턴스를 만드는 방식(isolation mode)으로 다룬다.

lifecycle hook — 테스트와 스펙 앞뒤에 함수를 건다

여기서 읽을 것 — hook 을 거는 두 방법과, 가장 흔한 테스트 hook 과 스펙 hook 이 저마다 언제 불리고 무엇에 쓰는지 본다.

정의 lifecycle hook

lifecycle hook 은 테스트 앞뒤나 같은 파일의 모든 테스트 앞뒤에 도는 함수이고, 테스트에 드는 setup · teardown 을 여기서 한다.

kotest 는 스펙 안에 바로 정의하는 hook 을 여럿 준다.

hook 을 거는 방법은 두 가지이고 기능은 같다 — 스펙 안에서 람다를 받는 DSL 메서드(beforeTest { … } 같은 것)를 부르거나, 스펙의 같은 이름 함수를 override 한다. kotest 문서는 팀이 좋아하는 쪽을 고르라고 한다. DSL 메서드는 함수를 받으므로, hook 로직을 BeforeTest 같은 typealias 의 함수로 빼 두면 여러 스펙이 그 함수를 다시 쓴다.

가장 흔히 쓰는 hook 은 beforeTest · afterTest 다. 테스트 종류와 상관없이 테스트마다 바로 앞뒤에 불리고(beforeAny · afterAny 의 별칭이다), 건너뛴 테스트에서는 불리지 않으며, afterTest 는 테스트가 실패해도 불린다. 테스트마다 상태를 되돌리고 테스트가 쓸 자원을 준비하고 치우는 데 쓰고, leaf 테스트에만 걸려면 beforeEach · afterEach 를 쓴다. 파일 안에서 hook 을 두는 순서는 상관없다.

참조 — 테스트 hook 이 저마다 불리는 때

hook 은 테스트의 TestType 두 값으로 갈린다 — Container 는 다른 테스트를 담는 컨테이너 테스트, Test 는 더 담지 못하는 leaf 테스트다. each 와 container 는 한 종류에만, any 는 두 종류 모두에 불린다.

afterProject 는 DSL 메서드로 쓰지만 beforeProject 는 없다 — 프레임워크가 스펙을 돌릴 때는 프로젝트가 이미 시작했다. 프로젝트 시작 · 끝처럼 스펙 밖에서 일어나는 이벤트는 extension 으로 건다.

스펙 hook 인 beforeSpec · afterSpec 은 테스트가 아니라 스펙 인스턴스를 따라 불린다. beforeSpec 은 엔진이 스펙 인스턴스를 만든 뒤 그 인스턴스의 테스트 hook 보다 먼저, afterSpec 은 그 인스턴스의 테스트가 모두 끝난 뒤에 돌고, beforeSpec 이 예외를 던지면 afterSpec 은 건너뛴다. 새 스펙 인스턴스가 생길 때마다 할 준비와 정리를 여기서 한다 — 인스턴스가 몇 번 생기는지, 곧 스펙 hook 이 몇 번 불리는지는 다음 소절의 isolation mode 가 정한다.

isolation mode — 기본은 스펙 인스턴스 하나다

여기서 읽을 것 — isolation mode 네 가지 가운데 기본 모드와 권하는 모드가 스펙 인스턴스를 언제 새로 만드는지 kotest 문서의 예와 출력으로 따라가고, 그래서 어느 모드를 고르는지 본다.

정의 isolation mode

isolation mode 는 테스트 엔진이 테스트를 돌리려고 스펙 인스턴스를 어떻게 만드는지 정하는 동작이다.

모든 스펙이 이 동작을 고를 수 있고, enum IsolationMode 로 정한다.

값은 네 가지다 — SingleInstance · InstancePerRoot · InstancePerLeaf · InstancePerTest. 테스트 사이에 나눠 쓴 상태를 되돌리려고 새 스펙 인스턴스에서 테스트를 돌리고 싶으면 모드를 바꾼다.

바꾸지 않으면 기본 SingleInstance 가 스펙 클래스의 인스턴스 하나를 만들고, 모든 테스트가 끝날 때까지 테스트를 순서대로 돌린다.

단추를 누르면 기본 SingleInstance 와 kotest 문서가 권하는 InstancePerRoot 를 문서의 예와 그 출력으로 걸음마다 따라간다. 걸음마다 어느 테스트가 어느 인스턴스에서 돌고 무엇을 찍는지 보면, 모드가 인스턴스를 언제 새로 만드는지 보인다.

여기서 읽을 것 — 스펙 본문에서 만든 mock 이 기본값에서 왜 둘째 테스트의 검증을 깨는지 참여자 사이의 걸음으로 보고, kotest 문서가 드는 출구 세 가지를 비교한다.

kotest 자체에는 mock 기능이 없다 — test double 을 만드는 fakery 만 있다. 대신 좋아하는 mock 라이브러리를 쉽게 붙이고, 문서는 MockK 를 예로 든다.

예 코드의 MockK 이름은 한 문장씩만 알면 된다 — mockk<T>() 는 보통 mock 을 만들고, every { … } 는 stubbing 블록을, verify { … } 는 검증 블록을 연다. just Runs 는 맞은 호출이 Unit 을 돌려준다고 정하고, verify(exactly = 1) 은 호출이 꼭 한 번인지 확인한다 — 상세는 2편 이 다룬다.

5data-driven testing — 입력 한 세트가 테스트 하나다

이 절의 목표 data-driven testing 이 입력 세트마다 테스트를 만들고, 컨테이너 안에만 둘 수 있다는 제약과 플랫폼 제약이 있다는 것을 안다
왜 여기 있나 앞 절까지는 테스트를 하나씩 손으로 썼다. 여러 입력 조합을 같은 로직으로 확인하려면 입력마다 테스트를 늘어놓는 boilerplate 가 생기고, kotest 는 그것을 프레임워크 안의 기능으로 푼다.

withXXX 함수 — 행마다 테스트를 만든다

여기서 읽을 것 — 입력 한 세트(행)가 어떻게 테스트 하나가 되는지 걸음으로 따라가고, 스타일마다 쓰는 함수 이름을 찾는다.

정의 data-driven testing

data-driven testing 은 주어진 입력 값마다 test case 를 저절로 만들어, 지루한 boilerplate 를 피하는 기법이다.

table-driven testing 이라고도 부르고, kotest 는 이 기능을 프레임워크 안에 갖추고 있다.

로직을 따라가는 테스트라면 특정 시나리오를 거치는 코드 경로가 맞다. 예를 드는 테스트라면 파라미터 조합을 많이 돌려 보는 편이 도움이 되고, data-driven testing 은 그때 쓰는 기법이다.

입력 한 세트를 행(row)이라 부르고, 행을 클래스에 싸서 data test 함수에 넘긴다. 함수 이름은 스타일의 DSL 을 따라 withXXX 형식이라, test 로 테스트를 만드는 Fun Spec 은 withTests 를 쓴다.

kotest 문서의 예는 섭씨를 화씨로 바꾸는 fun cToF(celsius: Int): Int = (celsius * 9 / 5) + 32 를 행 4개로 확인하고, 그 뒤 행 Pair(15, 20) 을 더해 실패를 보인다. 재생기의 cToF 값은 행마다 그 식을 Int 로 계산한 값이다.

6assertion — 실패하면 예외를 던지는 함수

이 절의 목표 kotest 의 assertion 이 실패하면 예외를 던지는 함수이고, 그 둘레에 실패를 모으는 · 맥락을 붙이는 · 기다리는 도구가 있다는 것을 안다
왜 여기 있나 앞 절들은 테스트를 어떻게 만들고 늘리는지 다뤘다. 테스트 안에서 실제로 무엇을 확인하는지는 assertion 라이브러리가 맡고, 이 모듈은 테스트 프레임워크와 따로 쓰인다.

matcher — 확장 함수와 infix 두 형식

여기서 읽을 것 — 같은 확인을 두 형식으로 적는 법과, matcher 를 이어 쓰고 컬렉션에 걸고 직접 만드는 법을 본다.

assertion 모듈의 중심은 상태를 확인하는 함수이고, kotest 는 그 함수를 matcher 라 부른다. shouldBe 같은 범용 matcher 와 문자열 길이를 보는 str.shouldHaveLength(10) 같은 특정 matcher 가 있고, 대부분은 표준 라이브러리 타입용이며 프로젝트마다의 matcher 와 서드파티 라이브러리가 주는 matcher 가 더 있다.

matcher 는 두 형식으로 쓰고, kotest 는 둘 다 지원한다. 같은 확인이 형식마다 이렇게 적힌다.

  • 확장 함수 형식 — 값 뒤에 점을 찍어 a.shouldBe(b) · a.shouldStartWith("foo") 처럼 부른다. IDE 가 matcher 를 자동 완성해 준다는 것이 좋은 점이다.
  • infix 형식 — 값과 matcher 사이에 점을 찍지 않고 a shouldBe b · a should startWith("foo") 처럼 쓴다. 조금 더 깔끔해 보여 이쪽을 좋아하는 사람도 있다.

부정은 형식마다 쓰는 법이 다르다. infix 형식은 should 자리에 shouldNot 을 써 a shouldNot startWith("boo") 로 적고, 확장 함수 형식은 함수마다 있는 부정 짝을 불러 a.shouldNotStartWith("boo") 로 적는다.

있는 matcher 로 모자라면 Matcher<T> 인터페이스를 구현해 직접 만든다 — T 는 확인할 대상의 타입이다. 직접 만든 matcher 는 있는 matcher 를 엮어도 되고 홀로 써도 된다.

예외 확인 — 블록을 감싸 던졌는지 본다

여기서 읽을 것 — 예외를 확인하는 함수 네 개가 무엇을 받고 무엇을 돌려주는지, 이름에 Unit 이 붙은 짝은 왜 있는지 본다.

matcher 가 값을 확인한다면, 예외 확인 함수는 코드 블록을 감싸 그 블록이 예외를 던지는지 확인한다. 기본은 shouldThrow<T> { … } 다 — 블록이 T 나 그 하위 타입의 예외를 던지면 통과하고, 잡은 예외를 돌려주어 그 message 를 matcher 로 다시 확인하게 한다.

kotest 6.2 문서 「Exceptions」 잡은 예외 확인

2 // code in here that you expect to throw an IllegalAccessException
3}
4exception.message should startWith("Something went wrong")message 를 다시 확인한다

거꾸로 shouldNotThrowAny { … } 는 블록이 아무것도 던지지 않아야 통과한다. 예외가 나면 안 되는 코드를 감쌀 때 쓰고, 소스를 보면 블록 타입이 () -> T 라 블록이 돌려준 값을 그대로 돌려준다.

소스에는 이름 끝에 Unit 이 붙은 짝 — shouldThrowAnyUnit · shouldNotThrowAnyUnit 같은 것 — 도 있다. 변수에 값을 넣는 대입은 값이 없는 문장이라 블록이 요구하는 Any 타입이 아니어서, 대입을 감싸면 컴파일되지 않는다. 그래서 대입처럼 값을 돌려주지 않는 블록을 감쌀 때는 Unit 짝을 쓴다.

soft assertion — 실패를 모아 끝에 알린다

여기서 읽을 것 — assertSoftly 가 실패를 어떻게 모으는지, 다른 라이브러리의 검사를 감싸는 shouldNotThrowAnyUnit 이 무엇을 하고 왜 Unit 짝이어야 하는지 본다.

정의 soft assertion

보통 shouldBe 같은 assertion 은 실패하면 곧바로 예외를 던진다. soft assertion 은 실패해도 테스트를 이어 돌리고, 블록 안의 실패를 모두 블록 끝에서 예외 하나로 알린다.

kotest 는 이 일을 assertSoftly 함수로 한다.

assertSoftly 는 블록 하나를 받는 형식과, 확인할 대상을 받아 그 대상을 receiver 로 하는 람다를 받는 형식이 있다. project config 로 모든 테스트에 assertSoftly 를 저절로 씌울 수도 있다.

그래서 다른 라이브러리의 assertion 은 감싸야 블록에 함께 모인다.

clue — 실패 메시지에 맥락을 붙인다

여기서 읽을 것 — 같은 실패가 clue 에 따라 어떻게 달라지는지 메시지를 비교하고, kotest 문서가 clue 를 언제 쓰라고 하는지 본다.

정의 clue

clue 는 assertion 에 맥락을 더해 실패가 스스로 설명되게 한다.

withClue 와 asClue 두 도우미가 그 일을 한다.

실패한 assertion 이 무엇이 틀렸는지 알 만큼 정보를 담지 못할 때 쓴다. user.name shouldNotBe null 이 실패하면 메시지는 <null> should not equal <null> 뿐이다.

같은 실패가 clue 에 따라 어떻게 달라지는지 메시지를 나란히 놓으면 아래와 같다. 도메인 객체 행의 HttpResponse 는 kotest 문서의 예가 상태 코드와 본문을 담으려고 만든 data class 로, 이런 객체를 asClue 로 clue 삼으면 객체가 통째로 메시지 머리에 온다.

eventually — 통과할 때까지 다시 부른다

여기서 읽을 것 — 끝날 때까지 기다려야 하는 코드를 흔한 방법 대신 eventually 로 확인하는 법과, 기다리는 동안 어떤 예외를 무시하는지 본다.

비결정적 코드는 테스트하기 어렵다 — 비동기 파일 쓰기가 잘 끝났는지 보려면 쓰기가 끝나 디스크에 flush 될 때까지 기다려야 한다. eventually 는 이럴 때 주어진 람다를 주기적으로 불러, 정한 예외는 무시하면서 람다가 통과하거나 timeout 이 되거나 반복이 너무 많아질 때까지 계속한다.

흔히 쓰는 방법 네 가지는 저마다 막히는 곳이 있고, eventually 는 그 방법들 대신 쓰는 도구다.

이 절의 목표 property 테스트가 generator 로 만든 입력을 1000번 넣어 성질을 확인하고, 실패하면 shrinking 으로 입력을 줄인다는 것을 안다

test function — 성질을 람다 하나로 적는다

여기서 읽을 것 — example-based 테스트가 무엇을 놓치는지, 같은 성질을 forAll 과 checkAll 로 어떻게 적는지 나란히 본다.

개발자는 보통 입력과 기대 결과를 주는 example-based 테스트를 쓴다. 이 방식은 개발자가 생각하지 못한 edge case(경계에 놓인 입력)나 고른 입력이 덮지 못한 곳의 오류를 놓치기 쉽다.

좋은 property 테스트 프레임워크는 음의 무한대 · 빈 리스트 · 비 ASCII 문자열처럼 example-based 테스트를 쓸 때 자주 잊는 값을 넣는다.

이름은 QuickCheck 같은 프레임워크가 모든 입력에서 참이어야 하는 성질 — 불변식 — 을 확인한 데서 왔다. 문자열 a · b 가 있으면 length(a + b) 는 늘 length(a) + length(b) 다.

넓은 입력이 도움이 되는 테스트면 무엇이든 맞다. kotest 문서는 사용자 이름을 검증하는 함수가 유효한 email 을 받는지 수천 조합으로 굳히는 예를 든다.

여기서 읽을 것 — Arb 와 Exhaustive 가 무엇을 만들고 언제 쓰는지 비교하고, Arb 가 늘 섞는 edge case 를 본다.

정의 generator

generator 는 property 테스트에 넣을 입력 값을 만드는 것이고, kotest 에서는 sealed class Gen 의 인스턴스가 값을 준다.

Gen 은 property 테스트 값의 입력 스트림 같은 것이라, Gen 하나가 한 타입의 값을 대개 끝없이 흘려보낸다.

generator 는 두 종류다. 한 테스트에 섞어 쓸 수 있고, kotest 문서는 양의 정수 100개를 Arb 로, 0 부터 200 까지의 짝수 전부를 Exhaustive 로 함께 넣는 예를 든다.

정의 edge case

edge case 는 Arb 가 무작위 표본과 따로 넣는, 미리 정해 둔 흔한 경계 값이다. 일부 타입의 값에 흔한 edge case 를 늘 넣는 것이 kotest property 테스트의 설계 특징이다.

참조 — Arb 가 쓰는 edge case 예
  • ints — 0 · 1 · -1 · Int.MAX_VALUE · Int.MIN_VALUE
  • doubles — 0 · 1 · -1 · Double.MAX_VALUE · Double.MIN_VALUE · Double.POSITIVE_INFINITY · Double.NEGATIVE_INFINITY · Double.NaN
  • strings — 빈 문자열 · 최소 길이 문자열 · 가장 낮은 codepoint
  • lists — 빈 리스트 · 원소 하나짜리 리스트 · 원소가 겹친 리스트
  • maps — 빈 map
  • nullable 값 — null

edge case 가 있는 까닭은 정수를 받는 함수라면 적어도 0 · 양수 · 음수로 테스트하고 싶은데, 무작위 값만으로는 0 이 나올 가능성이 꽤 낮아서다. 그래서 kotest 는 따로 정하지 않는 한 정수에 edge case 를 늘 넣고, 테스트를 돌릴 때 표본과 edge case 를 무작위로 번갈아 넣는다 — 기본 2% 가 edge case 다. 모든 Arb 에 edge case 가 있지는 않지만, 가장 흔한 타입의 Arb 에는 있다.

shrinking — 테스트를 깨는 가장 작은 입력을 찾는다

여기서 읽을 것 — 실패한 입력을 왜 줄여야 하는지, shrinking 이 어떤 순서로 도는지를 kotest 문서의 출력으로 따라가고, 직접 만든 generator 에서는 무엇을 챙기는지 본다.

property 테스트는 generator 가 만든 입력 — 대개 무작위 값 — 으로 같은 성질을 기본 1000번 확인한다. 그러다 처음 찾은 실패 사례에는 복잡한 것이 많이 들어 있을 수 있어, 그 값만 봐서는 무엇이 테스트를 깼는지 가리기 어렵다. 그래서 실패를 재현하는 더 작은 입력을 찾는 장치가 있다.

정의 shrinking

shrinking 은 실패한 사례를 단순하게 줄여 가장 작은 재현 사례를 찾는 장치다.

kotest 에서 generator 의 실패 사례를 어떻게 줄일지는 Shrinker 인터페이스의 구현이 정한다 — 내장 generator 에는 프레임워크가 정한 기본 Shrinker 가 있고, 직접 만든 generator 에는 직접 만든 Shrinker 를 줄 수 있다.

줄이기는 테스트가 실패했을 때 이 순서로 돈다.

  • 후보 만들기 — 실패한 값을 shrink 함수에 넣으면 테스트를 다시 해 볼 새 값 목록이 나온다. 줄이는 법은 타입마다 달라 문자열이면 첫 글자나 끝 글자를 떼고 정수면 하나 줄이거나 반으로 나누는 식이고, 빈 문자열 · 정수 0 같은 edge case 의 줄이기도 정해 두었다.
  • 다시 돌리기 — 후보마다 테스트를 다시 돌린다. 통과한 후보는 버리고, 여전히 실패하는 후보에서 다시 줄인다. 이 걸음은 문서가 문장으로 적지 않았고, 아래 원문 출력에서 읽은 것이다.
  • 결과 — 기본 1000번까지 줄이고(바꿀 수 있다), 끝에 가장 작은 실패 값을 Shrink result 로 보인다.

TestDispatcher — 가상 시계로 delay 를 건너뛴다

여기서 읽을 것 — TestDispatcher 가 무엇을 주고, 하루짜리 delay 가 테스트 안에서 어떻게 곧바로 끝나는지 참여자 걸음으로 본 뒤, 테스트 · 스펙 · 모듈 가운데 어디에 켜는지 본다.

정의 TestDispatcher

TestDispatcher 는 가상 시계를 다루고 delay 를 건너뛰게 하는 특별한 CoroutineDispatcher 다.

kotlinx-coroutines-test 모듈이 준다.

참조 — TestDispatcher 가 주는 연산
  • currentTime — 지금 가상 시각을 얻는다
  • runCurrent() — 지금 가상 시각에 잡힌 작업을 돈다
  • advanceUntilIdle() — 줄 선 작업을 더 없을 때까지 모두 돈다
  • advanceTimeBy(timeDelta) — 가상 시각이 timeDelta 만큼 갈 때까지 줄 선 작업을 돈다

테스트 하나에 쓰려면 테스트 config 에서 coroutineTestScope 를 켜고, 그 테스트 안에서는 확장 val testCoroutineScheduler 로 scheduler 를 얻어 advanceTimeBy 로 시계를 옮기고 currentTime 으로 지금 가상 시각을 읽는다. kotest 문서의 예는 평소라면 하루 동안 잠들 coroutine 을 띄우고 시계를 하루 옮긴다.

Spring 확장 — 생성자 주입과 테스트 이벤트

여기서 읽을 것 — Spring 확장을 켜는 법과 생성자 주입, Spring 의 테스트 이벤트가 kotest 테스트와 하나씩 맞지 않는 까닭과 그 때문에 transaction 이 어떻게 갈리는지 본다.

kotest 의 Spring 확장은 Spring 프레임워크로 의존성 주입을 하는 코드를 테스트하게 한다. 모든 스펙에 켜려면 project config 에 SpringExtension 을 등록하고, 스펙마다 켜려면 @ApplyExtension 을 단다. Spring 이 쓸 configuration 은 스펙 클래스에 @Configuration 같은 Spring Test 어노테이션을 달아 알린다.

9JUnit · AssertJ 와 비교 — kotest 문서가 든 차이

이 절의 목표 kotest 문서가 JUnit · AssertJ 보다 낫다고 든 점과, 두 라이브러리를 바꿀 대상이자 함께 쓸 대상으로 두는 자리를 안다
왜 여기 있나 앞 절들에서 본 기능을 kotest 문서는 Java 테스트 라이브러리와 비교해 한 쪽에 모은다. JUnit 으로 테스트를 써 온 독자에게는 무엇이 달라지는지 보는 자리다.

Why Kotest 쪽은 Java 에서 Kotlin 으로 옮기는 사람에게, 흔한 Java 테스트 라이브러리보다 kotest 가 나은 점을 정리한다. 그 쪽은 kotest 의 장점만 들고, JUnit · AssertJ 의 장점이나 kotest 의 단점은 적지 않는다.

왼쪽은 JUnit 과, 오른쪽은 AssertJ 와 비교한 목록이다.

vs Junit
  • coroutine 통합 — 모든 테스트가 coroutine 이라 runBlocking 같은 boilerplate 없이 suspend 함수를 부른다. coroutine 디버깅을 한 줄로 켜고, callback 으로 자식 coroutine 의 context 를 바꾸고, dispatcher 를 바꾸며, suspend 해도 서로 막지 않는 테스트를 병렬로 띄운다
  • 멀티플랫폼 — JVM · Native · Javascript 를 지원하고, 모든 대상에서 테스트 구조가 같다
  • 유연한 레이아웃 — 테스트 이름을 backtick 으로 감쌀 필요가 없는 DSL, 제한 없는 계층, JavaScript 프레임워크 같은 describe / it, ScalaTest 스타일, given / when / then 의 BDD 스타일
  • data driven testing — 보통 Kotlin 함수로 되풀이 테스트를 만들고, data class 를 행 객체로 쓴다
  • 동시성 도구 — eventually 로 정한 시간 안에 끝나는지, continually 로 정한 시간 동안 계속 통과하는지를 스레드를 막지 않고 확인한다
  • callback — lifecycle 이벤트를 함수로 다루는 callback 과 around-advice 스타일의 test interceptor
vs AssertJ
  • IDE 에서 찾기 쉬운 확장 함수 assertion
  • Sequence · Pair · Regex 같은 Kotlin 고유 타입의 assertion
  • 대부분의 assertion 이 멀티플랫폼
  • 여러 assertion 을 감싸 테스트를 끝내기 전에 모든 오류를 모은다
JUnit 쪽 목록은 테스트를 만들고 돌리는 프레임워크의 장점이고, AssertJ 쪽 목록은 값을 확인하는 assertion 의 장점이다 — kotest 의 두 모듈과 짝이 맞는다.

같은 문서는 JUnit 과 AssertJ 를 비교 상대로만 두지 않는다. 테이블은 문서가 두 라이브러리를 부르는 세 자리다.

10한계 — kotest 문서가 적은 경고와 제약

이 절의 목표 기능 하나에 묶이지 않는 한계 — Gradle 이 보고하는 테스트 이름과 6.0 의 깨지는 변경 — 와, 그 가운데 Gradle 과 Spring 의 한계가 테스트를 메서드로 가정한 데서 온다는 것을 안다
왜 여기 있나 앞 절들은 기능마다 kotest 문서가 단 경고를 그 기능과 함께 보였다. 기능을 고른 뒤 프로젝트에 도입할 때는 기능 하나에 묶이지 않는 한계도 걸리는데, 문서는 그것을 따로 적는다.

11다시 보는 구조 — 세 모듈과 조심할 곳

이 절의 목표 세 모듈과 조심할 곳을 한 줄씩 다시 잇고, kotest 문서가 답한 것과 다른 쪽으로 미룬 것을 가른다
왜 여기 있나 세 모듈의 모양과 조심할 곳이 여러 절에 흩어졌다. 절마다의 결론을 한 줄씩 모으고, JUnit · AssertJ 에 대한 문서의 판정과 이 편이 다른 쪽으로 미룬 물음을 가른다.
  • 스펙과 테스트 — 테스트는 스펙 안에서 이름과 람다로 만든 함수이고, 스타일 9개는 기능이 같아 읽히는 모양으로 고른다
  • 테스트 둘레 — 테스트 hook 은 테스트마다, 스펙 hook 은 스펙 인스턴스가 생길 때마다 불리고, 기본 SingleInstance 에서는 스펙 본문의 mock 이 호출 기록을 다음 테스트로 넘긴다
  • data-driven testing — 행 하나가 따로 통과 · 실패하는 테스트이고, leaf 범위 안에는 둘 수 없다
  • assertion — matcher 는 값 뒤에 붙는 함수이고, assertSoftly 는 kotest 의 실패만 모아 다른 라이브러리의 검사는 shouldNotThrowAnyUnit 으로 감싸야 함께 모인다
  • property 테스트 — 만든 입력을 기본 1000번 넣고, 실패하면 shrinking 이 후보를 다시 돌려 같은 테스트를 깨는 더 작은 입력을 찾는다
  • 실행 환경 — 가상 시계로 delay 를 건너뛰고, Spring 이벤트는 테스트를 메서드로 가정해 모드를 고르며 기본 모드에서는 테스트마다 rollback 된다
  • 비교 — 문서는 kotest 의 장점만 들고, JUnit · AssertJ 와 섞어 쓰는 방법도 둔다
  • 한계 — Gradle 보고와 Spring 이벤트의 한계는 테스트를 메서드로 가정한 바깥 도구에서 오고, 6.0 은 설정 위치와 확장 등록을 바꿨다

8줄은 한 줄로 모인다 — kotest 의 테스트는 스펙 안의 Kotlin 함수라 겹치고, 실행 중에 만들고, 행과 만든 입력으로 늘린다. 조심할 곳은 그 함수들이 나눠 쓰는 스펙 객체와, 테스트를 메서드로 가정한 바깥 도구다.

  • property 테스트가 실패하면 무엇을 받나? shrinking 이 후보를 다시 돌려 찾은, 같은 테스트를 깨는 더 작은 입력이다 — 문서의 예에서는 1792716902 가 89839 로 줄었다. 직접 만든 generator 는 Arb.bind 로 만들어야 필드마다 줄어든다.
