[학습] 헥사고날 아키텍처 — 포트와 어댑터로 바깥 떼기

헥사고날 아키텍처가 목적별 포트와 바꿔 끼우는 어댑터로 애플리케이션을 UI · DB 에서 떼어 놓는 원칙 · 장치 · 코드와, 쓰는 조건 · 권하는 법 · 대가를 안다.

읽는 사람 — 배우는 사람 — Kotlin 이나 Java 로 서버를 만들고 JUnit 으로 단위 테스트를 써 본 개발자. kotest · MockK · ArchUnit 은 써 본 적이 없거나 이름만 들었고, 헥사고날 아키텍처 · 피처 플래그는 말만 들어 봤다. 0편(지도)을 먼저 읽고 필요한 편을 골라 읽는다.

1물음 — 바깥 기술에서 떼어 놓는 법과 그 대가

이 절의 목표 애플리케이션은 목적별 포트로만 바깥과 말하고 기술은 어댑터가 맡는다는 답의 모양을 안다
왜 여기 있나 0편은 이 주제를 한 절로 훑고 물음 한 줄과 함께 이 편으로 넘겼다. 떼어 놓는다는 말과 대가라는 말이 원문에서 무엇을 가리키는지 알아야 뒤 절이 어느 답의 조각인지 보인다.

0편이 이 주제에 건 물음을 받는다 — 헥사고날 아키텍처는 애플리케이션을 UI · DB 같은 바깥 기술에서 어떻게 떼어 놓고, 그 대가로 무엇을 치르나? Cockburn 은 2005년 원전 머리에 목표부터 적었다 — 애플리케이션을 UI 도 데이터베이스도 없이 돌아가게 만든다.

정의 포트(port)

포트는 목적이 있는 대화 하나를 가리키고, 그 대화의 프로토콜은 API 로 나타난다.

대화의 목적이 그 프로토콜을 정한다.

정의 어댑터(adapter)

어댑터는 바깥 장치마다 하나씩 있어, 포트의 API 를 그 장치가 쓰는 신호로 바꾸고 그 반대로도 바꾼다.

GUI 는 사람의 움직임을 포트의 API 로 바꾸는 어댑터의 한 예다.

헥사고날 아키텍처는 포트와 어댑터 패턴이라고도 부르며, 애플리케이션 구성요소를 데이터 저장소나 UI 에 의존하지 않고 따로 테스트할 수 있는 느슨하게 결합된 구조를 목표로 한다. 2005년 Alistair Cockburn 이 제안했다.

이 편을 읽는 순서
  1. 1 설계 원칙 UI 쪽과 DB 쪽 문제를 한 원인으로 묶고 규칙 하나를 세운다찾을 것 — 레이어를 하나 더 두는 해법은 왜 실패하나 설계 원칙 — 안쪽 코드는 바깥으로 새지 않는다
  2. 2 포트와 어댑터 포트마다 어댑터가 여럿 끼고, 어댑터는 두 종류로 나뉜다찾을 것 — 테스트 도구와 mock 은 각각 어느 쪽에 끼나 포트와 어댑터 — 포트는 목적을 어댑터는 기술을 맡는다
  3. 3 원문 코드 — 전환점 개념이 코드로 넘어가, 애플리케이션 코드가 아는 것을 줄 단위로 본다찾을 것 — 어느 어댑터를 끼울지 정하는 코드는 어디 있나 원문 코드 — 할인 계산기와 Lambda 예약 예제
  4. 4 쓰는 곳 유스케이스를 쓰는 경계 · 적용 조건 · 노리는 결과 · 실제 쓰임찾을 것 — 입력과 출력이 하나뿐인 애플리케이션에도 맞나 유스케이스와 쓰임새 — 경계에서 쓰고 조건이 맞을 때 쓴다
  5. 5 비교 · 권고 · 대가 레이어드와 비교하고 권하는 쓰는 법과 대가로 닫는다찾을 것 — 어댑터 층이 값을 하지 못하는 때 레이어드와 헥사고날 — 의존이 향하는 곳이 다르다대가와 한계 — 어댑터 층이 는다

이 편은 원문 셋을 따라간다. Cockburn 의 2005년 원전(v0.9), AWS Lambda(다른 AWS 서비스가 진입점으로 불러 돌리는 함수) 예제를 붙인 AWS 패턴 쪽, DDD(도메인 주도 설계)와 함께 쓰자는 AWS 안내서 7쪽이다. 원전의 패턴 이름은 Ports and Adapters, 다른 이름이 Hexagonal Architecture 이고, AWS 안내서는 onion architecture 도 같은 것으로 부른다(4편의 ArchUnit 이 검사하는 onion 아키텍처).

이 절이 세운 것 답의 모양 — 애플리케이션은 포트로만 바깥과 말한다

떼어 놓는다는 것은 애플리케이션 코드가 포트의 API 만 알고 바깥 기술은 어댑터가 맡는다는 뜻이다. 다음 절은 원문 셋의 답을 먼저 모은다.

2저자들이 내린 답 — 바깥은 목적별 포트 뒤에 둔다

이 절의 목표 원문 부분마다 저자가 내린 답을 본문보다 먼저 안다
왜 여기 있나 본문은 원칙 · 장치 · 코드 · 쓰임 · 비교 · 권고 · 대가로 길게 이어진다. 답을 먼저 알고 읽어야 각 절이 어느 답의 근거인지 보인다.

원문 셋이 부분마다 내린 답과, 그 답을 받치는 원문의 사실이다.

원문 부분저자가 내린 답근거

원문 코드애플리케이션은 인터페이스만 쓰고, 무엇을 끼울지는 바깥 코드가 넘긴다할인 계산기는 생성자로, 예약 예제는 팩토리로 어댑터를 받는다
유스케이스와 포트 수유스케이스는 대개 바깥 기술을 빼고 안쪽 육각형의 기능과 이벤트로 적는다포트는 대화의 목적마다 하나이고, 저자는 둘에서 넷을 고르는 편이다
실제 쓰임 — Cockburn인터페이스를 기술이 아니라 목적으로 다시 짜자 새 기술을 바로 붙였다기상 경보 시스템이 http 피드와 이메일 알림 어댑터를 더했다
쓰는 조건과 대가 — AWS입력과 출력이 여럿이거나 바뀔 때만 어댑터 층이 값을 한다어댑터 층은 지연을 낳을 수 있고, 조건 밖이면 유지할 층이 될 뿐이다
레이어드와의 차이도메인이 인터페이스를 정해, 바깥이 바뀌어도 도메인은 그대로다레이어드에서는 데이터 모델의 변경이 비즈니스 레이어까지 번진다
권하는 쓰는 법 — AWS도메인을 모델링하고 처음부터 테스트를 쓰며 테스트와 배포를 자동화한다폴더를 entrypoints · domain · adapters 셋으로 나눠 개념에 맞춘다

답 8개는 한 문장으로 모인다 — 인터페이스를 기술이 아니라 목적으로 짜 바깥을 어댑터로 바꿔 끼우고, 그 어댑터 층은 입력과 출력이 여럿이거나 바뀔 때 값을 한다.

이 답은 코드 한 조각에 대어 참 · 거짓을 가릴 수 있다. 할인 계산기의 Discounter 코드에는 데이터베이스 기술의 이름이 하나도 없고, 어느 저장소를 쓸지는 사용자 쪽 어댑터가 생성자로 넘긴다.

이 절이 세운 것 답은 한 방향 — 기술은 포트 뒤의 어댑터가 맡는다

세 원문의 답은 같은 방향이고, 대가로 AWS 패턴 쪽이 적은 비용 셋은 어댑터 층에서 나온다. 다음 절은 그 답이 나온 문제를 Cockburn 의 Motivation 부터 본다.

3설계 원칙 — 안쪽 코드는 바깥으로 새지 않는다

이 절의 목표 핵심 원칙이 로직과 바깥 기술의 엉킴을 끊는 안팎의 구분이라는 것을 안다
왜 여기 있나 앞 절의 답은 안쪽 코드가 바깥으로 새지 않게 하라고 했지만, 그 규칙이 무엇을 막으려고 생겼는지는 아직 비어 있다.

AWS 패턴 쪽은 이 패턴을 비즈니스 로직(도메인 로직)을 DB · 외부 API 접근 같은 인프라 코드에서 떼어 놓는 데 쓴다고 적는다. Cockburn 은 그 까닭을 사용자 쪽 문제와 데이터 쪽 문제로 든다.

풀려는 문제 — 로직이 UI 와 DB 에 엉킨다

여기서 읽을 것 — 사용자 쪽과 데이터 쪽 문제, 레이어를 더하는 해법이 실패하는 까닭, 두 문제를 묶는 원인을 본다.

원전 머리의 목표는 셋이다 — 자동 회귀 테스트를 돌리고, 데이터베이스가 없어도 일하고, 사람 손 없이 애플리케이션끼리 잇는다. Cockburn 은 두 문제가 이어져 보이지 않지만 해법의 성질에서 대칭이 드러난다고 적는다.

여러 조직이 되풀이한 해법은 레이어를 하나 더 두고 이번에는 정말 비즈니스 로직을 넣지 않겠다고 약속하는 것이다. 그러나 어김을 알아챌 장치가 없어, 몇 년 뒤 그 레이어는 로직으로 차고 같은 문제가 돌아온다.

Cockburn 이 그리는 반대편은 모든 기능이 API 로 열린 애플리케이션이다 — 자동 회귀 테스트와, GUI 세부가 정해지기 전에 업무 전문가가 만든 자동 테스트가 돌고, headless(API 만 열린 채 UI 없이 도는 상태)로 배포해 다른 프로그램이 쓴다. 그 회귀 테스트가 로직을 프레젠테이션 레이어 밖에 두겠다는 약속의 위반까지 잡는다.

귀결 두 문제의 원인은 하나다

Cockburn 은 사용자 쪽과 데이터 쪽 문제가 같은 설계 오류에서 나온다고 본다 — 비즈니스 로직과 바깥 존재와의 상호작용이 엉킨 것이다.

이 소절이 세운 것 막으려는 것은 로직이 바깥 기술 없이 돌지 못하는 상태다

약속만으로 지키는 레이어는 그 엉킴을 막지 못한다. 다음 소절은 엉킴을 끊는 규칙을 본다.

안과 밖의 비대칭 — 좌우가 아니라 안팎을 가른다

여기서 읽을 것 — 안과 밖을 가르는 규칙 하나와 육각형이라는 모양을 고른 까닭을 본다.

정의 안과 밖의 비대칭(inside-outside asymmetry)

안과 밖의 비대칭은 애플리케이션의 왼쪽과 오른쪽이 아니라 안쪽과 바깥쪽 사이의 구분이고, 안쪽에 속한 코드는 바깥쪽으로 새지 않는다.

헥사고날은 이 상황의 대칭을 짚어 문제를 푼다 — 안쪽 애플리케이션이 몇 개의 포트로 바깥과 대화하고, 바깥의 것은 대칭으로 다룬다.

Cockburn 은 육각형이라는 모양을 두 가지를 눈에 띄게 하려고 골랐다고 적는다.

육각형 그림무엇을 보이나Cockburn 이 든 까닭

(b) 정해진 수의 포트서로 다른 포트 둘 · 셋 · 넷저자가 그때까지 본 가장 많은 수가 넷이다

포트와 어댑터라는 이름그림의 부분이 맡는 목적포트는 목적 있는 대화이고, 한 포트에 어댑터가 여럿 낀다

이 패턴의 첫 목적은 안팎의 비대칭이고, 그동안은 바깥의 것이 모두 같다고 짐짓 여긴다. 좌우의 비대칭은 다음 절의 driving 쪽 · driven 쪽이 다룬다.

레이어를 더해도 다시 생기는 엉킴을, Cockburn 은 안쪽 코드가 바깥으로 새지 않는다는 규칙 하나로 끊는다. 바깥과의 대화는 다음 절의 포트와 어댑터가 맡는다.

4포트와 어댑터 — 포트는 목적을 어댑터는 기술을 맡는다

이 절의 목표 포트마다 기술별 어댑터가 끼고, 어댑터는 대화를 여는 쪽과 받는 쪽으로 나뉜다는 것을 안다
왜 여기 있나 원칙은 바깥을 대칭으로 다루라고 했지만, 바깥 기술이 안쪽과 실제로 어떻게 이어지는지는 아직 비어 있다.

포트라는 말은 운영체제나 전자 기기의 포트처럼 프로토콜만 맞으면 어떤 장치든 꽂히는 것을 떠올리게 하려고 고른 말이고, AWS 패턴 쪽은 USB 포트에 비유한다.

한 포트에 어댑터 여럿 — 기술을 바꿔 끼운다

여기서 읽을 것 — 포트와 어댑터가 각각 무엇에 매이는지와 한 포트에 끼는 어댑터들을 AWS 그림으로 본다.

AWS 패턴 쪽의 말로, 포트는 기술에 매이지 않은 구성요소의 입구이고 누가 구현하든 바깥 행위자가 대화할 인터페이스를 정한다. 어댑터는 특정 기술로 포트를 거쳐 데이터를 주고받으며 다음 처리에 맞게 바꾼다.

원문 그림 [hex-aws-pattern-1] 은 AWS 패턴 쪽의 High-level architecture 그림이다. 가운데 앱 구성요소에 포트 넷이 붙고, 왼쪽 INPUT PORT 에는 모바일 앱 · 웹 앱 어댑터가, TEST PORT 에는 테스트 스크립트 어댑터가, 오른쪽 DATA PORT 와 PAYMENT PORT 에는 어댑터가 둘씩 낀다.

정의 test harness 와 mock 데이터베이스

test harness 는 FIT · Fitnesse 처럼 애플리케이션을 몰아 테스트하는 자동 테스트 도구이고, GUI 와 같은 포트에 끼는 어댑터다.

mock 데이터베이스는 메모리 안에 있어 실제 데이터베이스가 있든 없든 상관없이 도는 데이터베이스 어댑터다.

mock 이라는 말은 Cockburn 이 mock object 운동에서 바깥 secondary actor 를 메모리에서 대신하는 것의 이름으로 빌렸다 — Kotlin 의 mock 은 2편이 다룬다.

AWS 패턴 쪽은 어댑터를 더해도 다른 쪽이 흔들리지 않는다고 강조한다 — REST 어댑터가 있는 포트에 GraphQL 어댑터를 더해도 REST API · 포트 · 애플리케이션에 영향이 없다. 구성요소는 포트에 데이터를 넘기기만 하고, DB · 파일 시스템 · Amazon S3 가운데 어디에 쓸지는 어댑터가 정한다.

구성요소를 어느 층에서든 바꿀 수 있어, 환경 전체를 띄우지 않고 인프라 코드 없이 따로 테스트할 수 있다. 무엇을 포트로 볼지는 대체로 취향 문제다 — Cockburn 의 예로 기상 경보 시스템과 커피 머신 컨트롤러는 자연스러운 포트가 넷이고, 병원 투약 시스템은 셋일 수 있다.

데이터 쪽에서 Cockburn 이 짚는 것은, SQL 데이터베이스를 플랫 파일이나 다른 데이터베이스로 옮겨도 API 너머의 대화가 바뀌지 않아야 한다는 점이다. 그래서 같은 포트에 SQL 어댑터 · 플랫 파일 어댑터와 함께, 무엇보다 mock 데이터베이스 어댑터가 낀다.

이 소절이 세운 것 포트는 대화의 목적마다 하나, 어댑터는 기술마다 하나다

어댑터는 기술만 다를 뿐 같은 API 로 말하므로, 더하거나 바꿔도 포트와 애플리케이션은 그대로다. 다음 소절은 어댑터의 두 종류를 본다.

driving 쪽과 driven 쪽 — 누가 대화를 시작하나

여기서 읽을 것 — 어댑터가 두 종류로 나뉘는 기준과 쪽마다 알맞은 테스트 어댑터를 한 테이블에서 본다.

Cockburn 은 모든 포트가 근본적으로 비슷하다고 짐짓 여기고 패턴을 썼고, 그 가정이 아키텍처 수준에서 쓸모 있다고 말한다. 구현에서는 두 종류가 나타나고, 그는 이를 primary · secondary 또는 driving 어댑터(애플리케이션을 모는 쪽)와 driven 어댑터(애플리케이션이 모는 쪽)라 부른다.

정의 driving 어댑터와 driven 어댑터

driving 어댑터는 애플리케이션을 모는 행위자(primary actor)의 어댑터로, 쉬고 있는 애플리케이션을 깨워 내세운 기능 하나를 하게 한다.

driven 어댑터는 애플리케이션이 모는 행위자(secondary actor)의 어댑터로, 애플리케이션이 답을 얻거나 알리기만 하려고 부른다.

둘을 가르는 것은 누가 대화를 일으키거나 이끄느냐다.

두 쪽을 줄마다 비교하면 아래와 같다 — 원전 · AWS 안내서의 primary · secondary 를 이 편은 driving · driven 으로 부른다.

Cockburn 은 이 짝을 기억해 둘 만하다고 하면서도, 포트와 어댑터 아키텍처를 쓴 결과로 써야지 지름길로 쓰지 말라고 적는다. 포트와 어댑터 구현이 끝내 주는 것은 애플리케이션을 완전히 떼어 돌리는 능력이다.

이 절의 목표 두 예제에서 애플리케이션은 인터페이스만 쓰고 어댑터는 바깥 코드가 고른다는 것을 코드로 안다
왜 여기 있나 앞 절은 어댑터를 바꿔 끼운다고 했지만, 애플리케이션 코드가 무엇을 알고 무엇을 모르는지는 코드를 봐야 가릴 수 있다.

원문의 예제 코드는 둘이다. Cockburn 은 FIT 문서에 딸린 할인 계산기를 세 단계로 키우고, AWS 패턴 쪽은 Lambda 예약 서비스의 도메인 모델을 DynamoDB(데이터를 테이블에 쓰는 AWS 저장 서비스) 접근 코드와 떼어 보인다.

할인 계산기 — 저장소를 생성자로 받는다

여기서 읽을 것 — 세 단계가 어느 쪽 어댑터를 바꾸는지와, 마지막 단계에서 Discounter 가 저장소를 생성자로 받게 된 줄을 본다.

예약 Lambda — 입력 포트가 출력 포트를 부른다

여기서 읽을 것 — 요청 하나가 API Gateway · Lambda · DynamoDB 를 지나는 순서와, 어느 어댑터를 끼울지 정하는 팩토리를 본다.

Lambda 함수에는 비즈니스 로직과 DB 연동 코드가 엉키기 쉽고, 둘을 떼면 DB 코드 없이 로직을 단위 테스트할 수 있다. 원문 그림 [hex-aws-pattern-2] 에서 Amazon API Gateway 의 REST API 가 Lambda 함수를 부르고, 함수가 로직을 돌려 DynamoDB 테이블에 쓴다.

유스케이스 — 대개 애플리케이션 경계에서 쓴다

여기서 읽을 것 — 유스케이스를 애플리케이션 경계에서 쓰라는 까닭과, AWS 예제에서 그 경계의 입구인 입력 포트를 본다.

Cockburn 은 애플리케이션의 기능 명세 — 아마 유스케이스로 적을 — 를 바깥 기술 하나가 아니라 안쪽 육각형의 인터페이스에 대고 만든다고 적고, 이 패턴으로 유스케이스를 쓰는 바람직한 방식을 굳힐 수 있다고 말한다.

정의 애플리케이션 경계(application boundary)

애플리케이션 경계는 안쪽 육각형이고, 유스케이스는 대개 이 경계에서 바깥 기술과 상관없이 애플리케이션이 지원하는 기능과 이벤트를 적는다.

흔한 실수는 유스케이스에 각 포트 바깥 기술의 속사정을 담는 것이다 — 두 방식을 Cockburn 의 평가로 비교하면 아래와 같다.

바깥 기술을 담은 유스케이스경계에서 쓴 유스케이스
적는 것각 포트 바깥 기술의 속사정애플리케이션이 지원하는 기능과 이벤트
Cockburn 의 평가길다 · 읽기 어렵다 · 지루하다 · 깨지기 쉽다 · 유지비가 비싸다짧다 · 읽기 쉽다 · 유지비가 덜 든다 · 오래 안정적이다

유스케이스는 포트 수와도 이어진다 — 유스케이스마다 포트를 주면 포트가 수백 개가 되고, 모두 합치면 왼쪽 · 오른쪽 둘만 남는데, 저자는 어느 극단도 최적이 아니라고 본다. Cockburn 의 경계를 AWS 예제에 대어 본 대응은 아래와 같고, 이 대응은 이 편이 두 원문을 나란히 놓은 것이다.

적용 조건 — 바깥이 여럿이거나 바뀌거나 완전한 테스트가 필요할 때

노리는 결과 — 출시가 빨라지고 품질과 변화 대응이 나아진다

여기서 읽을 것 — AWS 안내서가 내건 결과 셋과, 그 근거인 클라우드 테스트와 로컬 테스트의 차이를 본다.

C2 위키의 익명 예부품마다 목적이 있는 인터페이스를 둔 컴포넌트 오디오를 시스템 비유로 썼다간단한 선과 어댑터로 부품을 거의 무한한 방법으로 잇는다
분산된 큰 팀의 개발여러 곳의 팀이 FIT 과 mock 으로 따로 테스트하고, 30분마다 CruiseControl 빌드가 모든 애플리케이션을 FIT + mock 조합으로 돌린다아직 시범 사용이라 쓰임으로 세지 않는다 — 완성되는 대로 mock 을 테스트 DB 로 바꾼다
UI 와 로직 개발 떼기UI 와 백엔드가 정해지기 전에 FIT 테스트와 mock 으로 보여 줄 기능을 만든다아직 초기 시범이라 쓰임으로 세지 않는다 — 어떻게 되는지 지켜보라고 적는다
이 소절이 세운 것 쓰임이 보이는 것은 목적으로 짠 인터페이스의 값이다

기상 경보 시스템은 인터페이스를 목적으로 다시 짜자 새 어댑터 · 제품 풀기 · 독립 회귀 테스트를 얻었다.

이 절이 세운 것 쓰는 곳은 바깥이 여럿이거나 바뀌거나 완전한 테스트가 필요한 구성요소다

유스케이스는 경계의 말로 쓰고, 어댑터 층이 값을 하는 것은 입력과 출력이 여럿이거나 바뀔 때다. 이 구조가 레이어드 아키텍처와 갈리는 곳은 다음 절이 비교한다.

7레이어드와 헥사고날 — 의존이 향하는 곳이 다르다

이 절의 목표 두 구조는 의존 방향이 달라 바깥이 바뀔 때 도메인이 받는 영향이 갈린다는 것을 안다
왜 여기 있나 독자가 아는 구조는 레이어드 아키텍처다. 같은 축에서 비교해야 헥사고날을 고르는 까닭이 아는 말로 보인다.

AWS 안내서는 레이어드 아키텍처를 구조를 갖춘 프로젝트에서 가장 흔한 선택으로 소개하고, 두 접근 사이에 미묘하지만 강력한 차이가 있다고 적는다.

레이어드 아키텍처 — 위 레이어가 아래에 의존한다

여기서 읽을 것 — 레이어드 아키텍처의 의존 방향과 가장 큰 단점, Cockburn 이 레이어 그림에서 본 두 문제를 본다.

레이어드 아키텍처는 소프트웨어 프로젝트를 비즈니스 로직 · 표현 로직 같은 큰 관심사를 나타내는 층으로 짜고, 위 레이어가 아래 레이어에 의존하게 한다. 아래 레이어가 위 레이어에 의존하는 일은 없다.

원문 그림 [hex-aws-overview-1] 에서 화살표는 위에서 아래로 향한다 — 프레젠테이션 레이어(UI · API · 명령줄)가 비즈니스 레이어에, 비즈니스 레이어가 데이터 접근 레이어와 외부 서비스에 의존한다.

AWS 안내서가 꼽는 가장 큰 단점은 이 의존 구조다. 저장 모델이 바뀌면 데이터 접근 인터페이스와 그에 의존하는 비즈니스 레이어가 바뀌어, 도메인 로직을 건드리지 않고는 인프라를 바꿀 수 없고 회귀 버그 가능성이 커진다.

Cockburn 은 포트가 사용자 쪽과 DB 쪽 둘뿐인 애플리케이션이 많아 한 줄로 세 · 네 · 다섯 층을 쌓는 구조가 자연스러워 보인다고 적고, 그런 그림의 문제 둘을 든다.

  • 첫째이자 가장 나쁜 것 — 사람들이 레이어 그림의 선을 진지하게 여기지 않아, 애플리케이션 로직이 레이어 경계를 넘어 샌다
  • 둘째 — 포트가 둘보다 많을 수 있어, 아키텍처가 한 줄짜리 레이어 그림에 들어맞지 않는다
이 소절이 세운 것 레이어드에서는 아래가 바뀌면 위까지 바뀐다

의존이 위에서 아래로 향해 데이터 모델의 변경이 위로 번진다. 비교의 실마리는 인터페이스의 위치다 — 레이어드에서는 아래 레이어 쪽에 있다.

헥사고날 아키텍처 — 바깥이 도메인의 포트를 구현한다

여기서 읽을 것 — 헥사고날이 의존을 어떻게 다르게 정하는지와 그 근거인 의존 역전 원칙을 본다.

원문 그림 [hex-aws-overview-2] 에서는 화살표가 모두 가운데로 향한다 — 왼쪽 primary 어댑터(예: AWS Lambda)와 오른쪽 secondary 어댑터(예: DynamoDB 클라이언트)가 가운데 도메인과 인터페이스를 가리킨다.

헥사고날은 결정을 도메인 비즈니스 로직 둘레에 모으고 모든 인터페이스를 그 로직이 정한다 — 레이어드에서 아래 레이어 쪽에 있던 인터페이스가 도메인 쪽으로 옮겨 왔다. 인프라 구성요소마다 그 포트를 구현하므로, 그 구성요소가 바뀌어도 핵심 도메인 로직은 흔들리지 않는다.

AWS 안내서는 헥사고날을 의존 역전을 다루는 원칙이라 부르고, 도메인이 의존 역전 원칙으로 포트를 거쳐 바깥과 대화한다고 적는다. Cockburn 도 이웃 패턴으로 Bob Martin 의 의존 역전 원칙(높은 수준 모듈은 낮은 수준 모듈에 의존하지 않고 둘 다 추상에 의존한다)을 들고, 그 구현이 바꿔 끼우는 driven 어댑터를 만드는 법을 보인다고 적는다.

이 소절이 세운 것 인터페이스가 도메인 쪽으로 옮겨 간다

도메인이 인터페이스를 정하고 바깥이 구현하므로 의존 화살표가 모두 도메인으로 향한다. 다음 소절은 두 구조를 같은 물음으로 비교한다.

두 구조 비교 — 바깥이 바뀔 때 도메인이 흔들리는가

여기서 읽을 것 — 두 구조를 의존 방향 · 바깥이 바뀔 때 · 포트 수 · 경계 지키기로 한 테이블에서 비교한다.

비교의 축은 바깥이 바뀔 때 도메인 코드가 같이 바뀌는가다 — AWS 패턴 쪽의 적용 조건에 UI 와 DB 의 주기적인 기술 교체가 들어 있다.

레이어드 아키텍처헥사고날 아키텍처
의존 방향위 레이어가 아래 레이어에 의존한다바깥 구성요소가 도메인이 정한 포트를 구현한다
인터페이스를 정하는 쪽아래 레이어 — 데이터 접근 레이어와 인터페이스도메인 — 도메인과 인터페이스가 함께 있다
DB 저장 모델이 바뀌면데이터 접근 인터페이스를 거쳐 비즈니스 레이어까지 바뀐다새 어댑터가 같은 포트를 구현하고 도메인 모델은 그대로다
도메인을 바꾸면영속 레이어도 함께 바꿔야 한다다른 코드를 깰 걱정 없이 도메인 모델을 바꾼다
포트가 둘보다 많으면한 줄로 쌓은 그림에 들어맞지 않는다육각형에 포트를 필요한 만큼 넣는다
경계를 지키는 것새 레이어에 로직을 넣지 않겠다는 약속모든 기능을 API 로 열어 자동 회귀 테스트가 로직 누수를 잡는다
저장 모델이나 도메인이 바뀔 때 번지는 범위가 갈리는 것은, 인터페이스를 아래 레이어가 정하느냐 도메인이 정하느냐가 갈리기 때문이다.

Cockburn 은 같은 애플리케이션을 세 층 그림으로도 그려, 어댑터 여럿이 맨 위와 맨 아래 층에 끼는 모습을 보였다.

이 소절이 세운 것 갈리는 것은 인터페이스를 누가 정하느냐다

아래 레이어가 정하면 바깥 변경이 위로 번지고, 도메인이 정하면 핵심 도메인 로직에 닿지 않는다.

이 절이 세운 것 의존 방향이 뒤집히면 바깥 변경이 번지는 범위가 줄어든다

같은 애플리케이션을 두 구조로 그릴 수 있지만, 헥사고날은 도메인이 포트를 정해 저장 기술 · UI 의 변경이 도메인에 닿지 않게 한다. 세우고 키우는 법은 다음 절이 본다.

8권하는 쓰는 법 — 도메인과 테스트부터 시작한다

이 절의 목표 AWS 안내서가 권하는 쓰는 법과 피할 것을 안다
왜 여기 있나 앞 절은 구조가 무엇을 주는지까지 말했다. 그 구조를 어떤 순서로 세우고 키우는지는 AWS 안내서의 권고가 맡는다.

AWS 안내서의 첫 권고는 비즈니스 도메인에서 거꾸로 소프트웨어 설계로 가라는 것이다.

AWS 안내서의 여섯 권고 — 도메인에서 폴더 구조까지

여기서 읽을 것 — 권고의 바탕인 DDD 의 두 낱말을 세우고, Best practices 의 여섯 권고를 본다.

도메인 주도 설계에서는 도메인이 소프트웨어 시스템의 핵심이고, 도메인 모델은 다른 모듈보다 먼저 정의되며 낮은 수준의 모듈에 의존하지 않는다. DB · 프레젠테이션 레이어 · 외부 API 같은 모듈은 모두 도메인에 의존하고, bounded context 는 해법을 기술이 아니라 비즈니스 로직으로 나눈 단위다. AWS 안내서는 헥사고날의 핵심을 bounded context 의 도메인 모델로 짓자고 하면서 DDD 의 모든 면을 다루지는 않는다고 밝힌다.

여섯 권고를 한 테이블에 모으면 아래와 같다 — 앞 셋은 도메인과 테스트를, 뒤 셋은 자동화 · 확장 · 구조를 다룬다.

헥사고날은 핵심을 떼어 두어 그 테스트를 복잡한 어댑터 없이 돌리게 한다. 다음 소절은 테스트를 나누는 법이다.

테스트 나누기 — 통합 테스트는 어댑터만 본다

여기서 읽을 것 — 테스트 종류마다 확인하는 것과 TDD 로 실제 어댑터까지 가는 순서를 본다.

end-to-end 테스트는 요청의 생애 전체를 덮고 프로젝트마다 적어도 하나는 있어야 한다. 그러나 경계 사례를 늘리면 테스트마다 진입점부터 통합 지점을 모두 지나야 해, 환경을 꾸미고 결과를 확인하는 데 개발자의 시간이 많이 든다.

4CI 에서 자동으로 돈다설계 패턴을 써서 리팩터링한다실제 어댑터도메인 로직이 아직 이상적이지 않아도 테스트가 회귀 버그를 막으며 구조를 키운다
실제 어댑터는 테스트가 성공한 뒤에야 만들고, 그 전까지 도메인 테스트는 복잡한 어댑터 없이 mock 과 fixture 로 돈다.

좋은 관행으로, 통합 테스트는 비즈니스 로직을 확인하지 말고 driven 어댑터가 바깥 서비스를 제대로 부르는지만 확인한다. 서버리스면 수동 통합 · end-to-end 테스트용 인스턴스를 빠르게 띄우고, 저장소에 올리는 변경마다 테스트를 자동으로 돌리라고 AWS 안내서는 권한다.

이 소절이 세운 것 로직은 로컬 단위 테스트가, 바깥 호출은 통합 테스트가 본다

경계 사례는 mock 으로 떼어 낸 로직 테스트가 맡고, 통합 테스트는 driven 어댑터의 바깥 호출만 본다. 다음 소절은 driving 쪽을 키우는 법이다.

자라는 서비스 — command 에서 CQRS 로

여기서 읽을 것 — 새 요구를 command 로 더하는 법, service façade 와 CQRS 가운데 고르는 법, AWS 위의 구조가 자라는 순서를 본다.

정의 command 와 command handler

command 는 연산 하나를 끝내는 데 필요한 정보를 모두 담은 객체다. command handler 는 command 를 받아 도메인의 상태를 바꾸고 부른 쪽에 응답을 돌려주는 메서드다.

AWS 안내서는 도메인의 모든 연산에 둘을 쓰라고 권한다 — 새 기능은 새 command 와 command handler 를 더해 기존 비즈니스 로직을 고치지 않고 넣는다.

driving 어댑터는 클라이언트의 읽기 · 쓰기 요청을 도메인과 느슨하게 잇는다. 그 방법으로 AWS 안내서가 드는 둘 가운데, service façade 는 프레젠테이션 레이어나 마이크로서비스 같은 클라이언트에게 읽기 · 쓰기 연산 여럿을 주는 앞면 인터페이스다. CQRS 는 읽기와 쓰기를 query 와 command 로 나눠 서로 다른 모듈에 구현하는 패턴이다.

service façadeCQRS
하는 일요청을 도메인에 넘기고 응답을 클라이언트에 맞게 바꾼다command 는 상태를 바꾸고, query 는 바꾸지 않고 데이터만 돌려준다
맞는 곳연산이 여럿인 단일 책임 마이크로서비스키우고 오래 유지할 프로젝트, 특히 이벤트 주도 아키텍처
커질 때모든 연산이 한 인터페이스에 모이고 의존이 늘며, 여러 개발자가 같은 façade 를 고치게 된다command 를 비동기 이벤트로, query 를 API 로 동기로 돌릴 수 있고 query 에 맞춘 DB 도 쓸 수 있다
AWS 안내서의 권고크게 늘지 않을 것이 분명한 서비스에만키우고 오래 유지할 프로젝트에, 고르기 전에 신중히 평가해서

CQRS 를 바로 고르지 않아도 처음부터 command 와 command handler 로 짜 두면, 읽기 · 쓰기를 나누지 않았어도 나중에 CQRS 로 리팩터링하기 쉽다.

인프라 예도 단순하게 시작해 필요할 때마다 키우는 순서다 — 전환의 단추로 네 그림을 같은 위치에서 차례로 본다.

AWS 위의 헥사고날 — 단순한 구조에서 여러 도메인까지
단계마다 클라이언트와 어댑터가 늘지만 도메인은 포트로만 이어진다 — DynamoDB 에서 Amazon RDS 로 바꿀 때도 새 어댑터를 쓰면 도메인은 그대로다.
조직 확장 — Inverse Conway Maneuver

소프트웨어 아키텍처는 회사의 소통 구조를 닮아 간다(Conway 의 법칙). 데이터베이스 · 서비스 버스 같은 기술 전문성으로 팀을 나누면 사일로가 생겨 그 문제가 아키텍처에 비친다. AWS 안내서는 그 대신 Inverse Conway Maneuver 를 들어, DDD 와 event storming 으로 찾은 bounded context 하나 이상을 교차 기능 팀에 맡기라고 권한다.

이 소절이 세운 것 command 로 시작해 커지면 CQRS 로 나눈다

연산마다 command 와 command handler 를 두면 커질 때 CQRS 로 옮겨 가기 쉽다. 커진 프로젝트를 담을 폴더 구조는 다음 소절이다.

프로젝트 구조 — 폴더를 헥사고날 개념에 맞춘다

여기서 읽을 것 — 권하는 폴더 셋이 헥사고날의 어느 개념에 대응하는지 본다.

AWS 안내서는 IaC(인프라 자원을 소스 코드로 정의하고 관리하는 방식)가 클라우드 개발에서 널리 쓰인다고 적고, 애플리케이션 코드와 인프라 코드를 한 저장소에 두며 애플리케이션을 헥사고날 개념에 맞춘 폴더 셋으로 나누라고 권한다.

9대가와 한계 — 어댑터 층이 는다

이 절의 목표 원문 아홉 쪽이 적은 대가와 한계를 모두 안다
왜 여기 있나 앞 절까지는 얻는 것을 말했다. 저자들이 스스로 적은 대가와 한계를 모아야 언제 이 구조를 쓰지 말아야 하는지 보인다.

이 편이 원문 아홉 쪽에서 모은 대가와 한계는 일곱 가지다 — 복잡도 · 유지 부담 · 지연은 AWS 패턴 쪽 Issues and considerations 의 비용이고, 나머지 넷은 Cockburn 과 AWS 안내서가 다른 절에 단 단서다.

대가 · 한계적힌 대가 · 한계언제 문제가 되나
복잡도비즈니스 로직과 인프라 코드를 떼는 일이 복잡하다조심해 다루면 민첩성과 테스트 범위, 기술 적응을 얻지만 아니면 풀기 복잡한 문제가 된다
유지 부담갈아 끼울 수 있게 하는 어댑터 코드가 더 생긴다입력과 출력이 여럿이 아니고 바뀌지도 않으면 유지할 층만 하나 는다
지연포트와 어댑터가 층을 하나 더한다그 층 때문에 지연이 생길 수 있다
포트 수무엇이 포트인지는 대체로 취향 문제다틀린 수를 골라도 특별한 해가 없어 보여 직관에 맡긴다 — 두 극단은 어느 쪽도 최적으로 보이지 않는다
로컬 테스트로 못 보는 것게이트웨이 · Lambda · DynamoDB · IAM 설정은 클라우드에서만 확인되고, 구성요소 통합도 그럴 수 있다Moto · LocalStack 같은 mock 도구는 실제 API 계약을 정확히 반영하지 못하거나 기능이 모자랄 수 있다
service façade커질수록 모든 연산이 한 인터페이스에 모인다단일 책임 원칙과 개방-폐쇄 원칙을 지키기 어렵다

복잡도 · 유지 부담 · 지연은 어댑터 층에서 나오는 대가이고, AWS 패턴 쪽은 그 층이 입력과 출력이 여럿이거나 바뀔 때만 값을 한다고 적는다.

같은 Issues 목록의 나머지 둘 — DDD 와 특히 잘 맞는다는 것과 입출력이 추상이라 테스트하기 쉽다는 것 — 은 대가가 아니다. AWS 안내서의 FAQ 는 헥사고날이 꼭 있어야 하는 것도 아니라고 적는다 — TDD 도 제품 확장도 헥사고날 없이 할 수 있다. 다만 헥사고날은 TDD 를 더 쉽게 하고, 헥사고날과 DDD 는 확장을 더 쉽게 하며 큰 프로젝트에서 길게 보면 더 효과적이다.

MVP(minimum viable product — 최소 기능 제품)에는 익숙한 설계 패턴을 쓰라고 하면서도, 엔지니어가 익숙해질 때까지 헥사고날을 연습해 보라고 하고 새 프로젝트에 헥사고날을 세우는 데 아키텍처 없이 시작할 때보다 시간이 크게 더 들지 않는다고 적는다. MVP 에 비즈니스 로직이 있으면 자동 테스트는 꼭 쓰라고 한다.

이 절이 세운 것 대가는 어댑터 층이고, 그 층은 바깥이 여럿이거나 바뀔 때만 값을 한다

대가를 원칙 · 장치 · 코드와 한 번에 놓고 판정하는 일은 마무리 절이 한다.

10다시 보는 구조 — 바깥을 포트 뒤에 두고 치르는 값

이 절의 목표 절마다의 결론과 두 비교의 판정, 원문이 답한 것과 미룬 것을 안다
왜 여기 있나 원칙 · 장치 · 코드 · 쓰임 · 비교 · 권고 · 대가가 서로 다른 절에서 나왔다. 한 줄씩 모아야 물음의 답이 한 화면에 모인다.
  • 설계 원칙 — 로직과 바깥의 엉킴이 두 쪽 문제의 한 원인이고, 안쪽 코드는 바깥으로 새지 않는다
  • 포트와 어댑터 — 포트는 목적마다, 어댑터는 기술마다 두고, 어댑터는 driving 쪽과 driven 쪽으로 나뉜다
  • 원문 코드 — Discounter 는 RateRepository 하나만 쓰고, 예약 Lambda 의 어댑터는 팩토리 한 곳에서 고른다
  • 유스케이스와 쓰임 — 유스케이스는 애플리케이션 경계에서 쓰고, 패턴은 바깥이 여럿이거나 바뀌거나 완전한 테스트가 필요한 곳에 쓴다
  • 레이어드와 비교 — 인터페이스를 도메인이 정해 바깥 변경이 도메인 로직에 닿지 않는다
  • 권고 — 도메인과 테스트부터, 커지면 command 에서 CQRS 로, 폴더는 세 부분에 맞춘다
  • 대가 — 어댑터 층만큼의 복잡도 · 유지 부담 · 지연이고, 그 층은 바깥이 여럿이거나 바뀔 때만 값을 하며 포트 수에는 정답이 없다

이 줄들은 한 문장으로 모인다 — 애플리케이션은 목적별 포트로만 바깥과 말하고 기술은 바꿔 끼우는 어댑터가 맡으며, 대가는 바깥이 여럿이거나 바뀔 때만 값을 하는 어댑터 층이다.

답이 난 것
  • 헥사고날 아키텍처는 애플리케이션을 UI · DB 같은 바깥 기술에서 어떻게 떼어 놓나? 애플리케이션은 목적별 포트의 API 로만 바깥과 말하고, 기술은 그 포트에 꽂히는 어댑터가 맡는다. 무엇을 끼울지는 바깥의 어댑터나 팩토리가 생성자로 넘긴다.
  • 그 대가로 무엇을 치르나? 어댑터 층만큼의 복잡도 · 유지 부담 · 지연이고, 그 층은 입력과 출력이 여럿이거나 바뀔 때만 값을 한다.
  • 포트는 몇 개를 두나? 대화의 목적마다 하나 — 저자는 둘에서 넷을 고르는 편이다.
  • 유스케이스는 어디에 대고 쓰나? 대개 애플리케이션 경계(안쪽 육각형)에 대고, 바깥 기술 없이 기능과 이벤트로 쓴다.
  • 레이어드 아키텍처와 무엇이 다른가? 레이어드는 위 레이어가 아래 레이어에 의존하고, 헥사고날은 바깥이 도메인이 정한 포트를 구현한다.
답이 나지 않은 것과 이어지는 곳
  • 도메인이 어댑터에 의존하지 않는다는 규칙을 어떻게 검사하나 4편 — ArchUnit 의 layered · onion 아키텍처 검사
  • driven 쪽 포트를 Kotlin 테스트에서 mock 으로 바꾸려면 2편 — MockK
  • mock 과 실제 저장소를 고르는 FIT 어댑터는 어떻게 짜나 저자가 다룰 곳을 밝히지 않았다 — 새 정보가 적다며 싣지 않았다
  • 출력 포트와 테스트 fixture 의 전체 코드는 AWS 예제 저장소 aws-lambda-domain-model-sample
  • DDD 의 나머지 설계는 AWS 안내서가 가리키는 Domain Language 의 DDD 자료
  • 유스케이스 자체는 어떻게 쓰나 Cockburn 『Writing Effective Use Cases』(2001) — 원전 References
  • Lambda 도메인 모델은 어떻게 진화시키나 AWS 패턴 쪽 Related content 의 일본어 블로그 글과 Videos 의 일본어 영상

다음 읽을 곳으로 Cockburn 은 References 에 『Fit for Developing Software』, 『Design Patterns』 의 Adapter 패턴, Martin 의 의존 역전 원칙, Fowler 의 Dependency Injection 을 든다. 이 묶음에서는 mock 쪽으로 2편이, 의존 규칙 검사로 4편이 이어진다.

이 절이 세운 것 답은 목적별 포트와 바꿔 끼우는 어댑터, 대가는 어댑터 층이다

원문 셋은 떼어 놓는 장치와 그 값을 치를 조건까지 답했고, 의존 규칙의 검사는 4편에서, Kotlin 의 mock 은 2편에서 이어진다.
