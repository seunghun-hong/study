[학습] MockK — 협력자 mock과 호출 검증

대상 코드가 부르는 협력자를, 테스트가 답을 정하고 받은 호출을 확인하는 mock 으로 MockK 가 어떻게 바꾸는지와, MockK 문서가 mock 하지 말라고 막는 것과 적어 둔 한계를 안다.

읽는 사람 — 배우는 사람 — Kotlin 이나 Java 로 서버를 만들고 JUnit 으로 단위 테스트를 써 본 개발자. kotest · MockK · ArchUnit 은 써 본 적이 없거나 이름만 들었고, 헥사고날 아키텍처 · 피처 플래그는 말만 들어 봤다. 0편(지도)을 먼저 읽고 필요한 편을 골라 읽는다.

1물음 — 협력자를 mock 으로 바꾸는 한 바퀴

이 절의 목표 MockK 테스트 한 바퀴 — mock 을 만들어 대상 코드에 넘기고, 답을 정하고, 대상 코드가 부른 호출을 mock 의 기록에서 확인한다 — 와 이 편이 따라가는 README 의 순서를 안다
왜 여기 있나 0편은 MockK 를 한 줄 물음으로만 적었다. 물음과 테스트 한 바퀴의 모양을 먼저 알아야 뒤의 mock 종류 · DSL 테이블이 답의 어느 조각인지 보인다.

0편이 MockK 에 던진 물음을 받는다 — MockK 는 Kotlin 코드의 협력자를 어떻게 mock 으로 바꾸고 호출을 검증하며, 무엇은 mock 하지 말아야 하나? 협력자는 대상 코드가 일하며 부르는 다른 객체이고, mock 은 그 자리에 넣어 테스트가 답을 정하고 받은 호출을 확인하는 객체다.

stub 은 every 블록으로 맞는 호출에 돌려줄 답을 정해 두는 일이다. 검증은 mock 이 기록한 호출에 verify 블록에 적은 호출이 있었는지 확인하는 일이다. 아래 레인은 kotest 문서에 실린 MockK 예 하나를 테스트 · mock · 대상 코드의 세 열로 나눠, 누가 무엇을 넘기는지 순서대로 보인다.

MockK 테스트 한 바퀴 — kotest 문서의 MyService 예
테스트
mock(repository)
대상 코드(MyService)
1 mockk<MyRepository>() 로 mock 을 만들어 MyService(repository) 에 넘긴다 → repository
2 every { repository.save(any()) } just Runs 로 save 의 답을 정한다 — stub → save 에 정한 답
3 target.save(MyDataClass("a")) 로 대상 코드를 부른다 → MyDataClass("a")
4 넘겨받은 repository 의 save 를 부른다 → save 호출
5 정해 둔 답(Unit)을 돌려주고 그 호출을 기록한다 → 기록된 호출
6 verify(exactly = 1) { repository.save(MyDataClass("a")) } 로 그 호출이 꼭 한 번 기록됐는지 확인한다 — 검증
테스트는 mock 을 만들어 넘기고 답을 정한 뒤, 대상 코드가 부른 호출을 mock 의 기록에서 확인한다. kotest 문서는 이 예가 기대대로 돈다고 적는다 — 대상 코드가 넘겨받은 repository 의 save 를 한 번 불렀다는 뜻이다.

README 의 첫 예는 대상 코드 없이 테스트가 mock 을 바로 부르지만, 만들기 · stub · 검증의 순서는 같다. 기본 mock 은 엄격해 쓸 동작을 정해 줘야 하고, 끝 줄의 confirmVerified 는 기록에 확인하지 않은 호출이 남지 않았는지 본다.

2MockK 문서의 답 — 엄격한 기본값에 확인을 더한다

이 절의 목표 MockK 문서가 부분마다 내린 답 — 기본 mock 은 엄격하고, 대신할 대상마다 만드는 함수가 다르며, 확인 장치와 막는 목록이 쓰이지 않은 stub 과 mock 하기에 문제가 있는 클래스를 잡는다 — 을 본문 전에 안다
왜 여기 있나 본문은 mock 종류 · DSL 테이블 · 설정을 오가며 길어진다. 답을 먼저 알고 읽어야 각 절이 어느 답의 근거인지 보인다.

MockK 문서가 부분마다 내린 답과 그 근거를 모았다.

이 절이 세운 것 답은 엄격한 기본값에서 시작한다

결론은 모두 README 와 ANDROID 문서 안에서 났고, 답이 열린 채 남은 물음은 마무리 절이 모은다. 다음 절은 이 답들의 바탕이 되는 원칙을 MockK 문서가 스스로 밝힌 말로 모은다.

3설계 원칙 — 엄격한 기본값과 쓸데없는 코드 없는 테스트

이 절의 목표 MockK 문서가 스스로 밝힌 원칙 네 가지와, 원칙마다 그것을 지키는 기능을 안다
왜 여기 있나 앞 절의 답은 기능 이름으로 나왔다. 그 기능들이 무엇을 지키려고 있는지 알아야 쓸 때 고를 기준이 생긴다.

MockK 문서는 원칙을 한 절로 모으지 않는다. 원칙은 첫 예 앞의 설명, 쓸데없는 stub 절의 첫 문장, Restricted Mocking 의 목표, Android 지원 테이블의 기능 이름에 흩어져 있다.

Restricted Mocking 은 mock 하면 문제가 되는 클래스를 막는 기능이고, 그 목표는 더 나은 테스트 습관과 코드 유지보수, 시스템 작업과 핵심 자료구조에 묶인 클래스를 mock 하지 않는 것이다. 쓸데없는 stub 을 찾는 기능과 Restricted Mocking 은 둘 다 유지보수를 까닭으로 든다 — 앞의 것은 깔끔하고 유지보수할 수 있는 테스트 코드를, 뒤의 것은 코드 유지보수를 돕는다고 적는다.

이 절이 세운 것 원칙마다 지키는 기능이 따로 있다

엄격한 기본값은 mock 만들기에서, 쓸데없는 stub 은 확인 장치에서, 막는 목록은 쓰는 법 절의 Restricted Mocking 에서 다시 나온다. 다음 절은 첫째 물음 — mock 을 무엇으로 만드나 — 부터 연다.

4mock 만들기 — 대신할 대상마다 함수가 다르다

이 절의 목표 mock 으로 바꾸는 대상이 두 무리 — 대상 코드에 넘겨 줄 인스턴스와 대상 코드가 이미 부르는 object · 함수 · 생성자 — 로 갈리고, 무리마다 만드는 함수와 되돌리는 법이 다르다는 것을 안다
왜 여기 있나 엄격한 기본값은 보통 mock 의 이야기다. 대상 코드가 협력자를 받지 않고 직접 부르거나 새로 만들면 다른 함수가 필요하다.

mock 종류 — 넘겨 주는 mock 과 바꿔 놓는 mock

여기서 읽을 것 — mock 을 만드는 함수 여섯 가지가 대상 코드와 어떻게 이어지는지, 그 가운데 어느 것이 끝난 뒤 되돌려야 하는지 본다.

보통 mock 은 엄격하고, relaxed mock 은 정하지 않은 함수에도 단순한 값을 돌려주며, spy 는 넘긴 진짜 객체를 바탕으로 한다. 아래 관계도에서 위 줄의 셋은 만든 인스턴스를 대상 코드에 넘기고, 아래 줄의 셋은 대상 코드가 이미 부르는 object · 함수 · 생성자를 그 자리에서 mock 으로 바꾼다.

보통 mock 과 relaxed mock — 답을 정하는 범위

여기서 읽을 것 — 엄격한 보통 mock 과 relaxed mock 이 같은 호출에 어떻게 답하는지, 그 사이의 선택지를 본다.

정의 relaxed mock

relaxed mock 은 모든 함수에 단순한 값을 돌려주는 mock 이다. 경우마다 동작을 정하는 일을 건너뛰면서도 필요한 것은 stub 하게 해 주고, 참조 타입을 돌려주는 함수에는 chained mock 을 돌려준다.

같은 car.drive(Direction.NORTH) 호출에 두 mock 이 무엇을 돌려주는지 나란히 놓았다. 왼쪽은 Class mock 절의 보통 mock, 오른쪽은 Relaxed mock 절의 예이고, every 줄이 있고 없음이 두 칸을 가른다.

spy — 진짜 객체 위에 일부만 덮는다

여기서 읽을 것 — spy 가 진짜 객체와 어떻게 섞이는지, private 함수 · 속성 · 부모 호출까지 덮는 법을 본다.

코드에서 확인하기 — 만든 mock 이 돌려주는 것

앞 소절들이 세운 주장을 원문 코드로 확인하는 자리다. 상자마다 주장 하나를 적었고, 누르면 그 코드가 펼쳐진다.

5stub 과 검증 — 답을 정하고 호출을 센다

이 절의 목표 stub 과 검증이 같은 인자 matcher 를 쓰고, 검증 세 가지가 mock 의 같은 기록을 서로 다르게 본다는 것을 안다
왜 여기 있나 mock 을 만든 다음의 일은 둘이다 — 부를 호출에 답을 정하고, 대상 코드가 부른 호출을 확인한다. MockK 는 두 일에 같은 인자 문법을 쓴다.

MockK 문서의 Verification order 예로 순서를 따라간다. 둘째 인자를 slot(capture 가 잡은 인자 값을 담는 객체)에 잡아 답에 쓰는 stub 을 걸고, 세 번 부른 뒤, 검증 세 가지로 같은 기록을 본다.

인자 matcher — 어느 호출인지 조건으로 가린다

여기서 읽을 것 — every · verify 의 인자 자리에 들어가는 matcher 와, 맞은 인자를 slot 에 잡는 capturing 을 본다.

정의 인자 matcher — argument matchers

capturing 은 맞은 인자를 CapturingSlot 이나 MutableList 에 담는 것이다. slot 은 보통 slot<T : Any?>() 로 만들고 nullable · non-nullable 을 모두 잡으며, MutableList 는 여러 값을 잡을 때 쓴다.

vararg 는 1.9.1 부터 varargAll · anyVararg · varargAny 로 맞추고, 조건 안에서 position · nArgs 를 쓴다.

인자들이 제네릭 타입을 함께 쓰는 함수에서 첫 matcher 를 ofType(Box::class) 처럼 star projection 타입 Box<*> 로 쓰면, 둘째 matcher 가 Nothing 으로 추론돼 컴파일되지 않는다. 첫 matcher 를 ofType<Box<String>>() 처럼 밝혀 쓰거나 any<Box<String>>() 와 any() 로 쓰면 되고, 둘째 matcher 만 any() 로 바꾸면 풀리지 않는다.

matcher 가 모자라면 새로 붙인다 — MockKMatcherScope · MockKVerificationScope 에 match 를 쓰는 함수를 더하고, 더 복잡하면 Matcher 인터페이스를 구현한다. 원문 예는 순서를 보지 않고 목록을 비교하는 matcher 다.

matcher 는 reflection 과도 함께 쓴다. Reflection matchers 예는 reflection 으로 고른 함수(MyBuilder 를 돌려주는 것)마다 인자 자리에 any(Class) 를 넣어, 빌더 스타일 객체의 메서드를 모두 mock 한다.

Restricted Mocking — mock 하면 안 될 클래스

여기서 읽을 것 — MockK 가 기본으로 막는 클래스와 그 까닭, 막힌 클래스를 mock 할 때 경고와 예외 가운데 무엇이 나는지, 내 클래스를 더하는 법을 본다.

정의 Restricted Mocking

Restricted Mocking 은 mock 하기에 문제가 있는 클래스를 mock 하지 못하게 막는 MockK 기능이다. 그런 클래스를 mock 하는 것은 대개 테스트 설계가 나쁘다는 표시이고, 믿을 수 없거나 오해를 낳는 테스트 결과로 이어질 수 있다.

MockK 문서는 그런 클래스를 mock 할 때 생기는 문제를 넷으로 든다.

  • 거짓 안도감(False sense of security) — 구현이 약하거나 틀려도 테스트가 지날 수 있다
  • 강한 결합(Tight coupling) — 테스트가 낮은 층의 구현 세부에 지나치게 의존한다
  • 유지하기 어려운 테스트(Hard-to-maintain tests) — 코드를 고치면 상관없는 테스트가 깨져 유지 부담이 는다
  • code smell(Code smells) — 시스템 층 · 값 타입 클래스를 mock 하는 것은 흔히 나쁜 아키텍처의 신호다

기본으로 막는 클래스는 다섯이고, 하위 클래스와 구현까지 막는다 — ArrayList · HashSet · HashMap, File 을 상속하거나 Path 를 구현한 내 클래스도 막힌다.

클래스무엇인가하위 타입도 막나
java.lang.SystemSystem.currentTimeMillis() · System.getenv() 같은 시스템 API예
java.util.CollectionList · Set · Queue 같은 컬렉션예
java.util.MapHashMap 같은 키-값 자료구조예
java.io.File파일 I/O 클래스 — mock 하지 말고 추상화하라고 적는다예
java.nio.file.Path파일 시스템의 경로를 다루는 클래스예

막힌 클래스를 mock 할 때 무슨 일이 나는지는 mockk.throwExceptionOnBadMock 하나가 정한다. 적지 않으면 false 라 경고 로그만 남고, 끝까지 막으려면 true 를 밝혀 적는다.

원문의 예List should not be mocked! Consider refactoring your test.MockKException: Mocking java.util.HashMap is not allowed!

설정은 mockk.properties 의 mockk.restrictedClasses(막을 클래스의 전체 이름을 쉼표로)와 mockk.throwExceptionOnBadMock 두 줄이다. throwExceptionOnBadMock 은 시스템 속성이나 루트 프로젝트 gradle.properties 의 Gradle 속성으로도 준다.

Gradle 은 테스트를 따로 띄운 JVM 에서 돌리므로 속성을 그 JVM 으로 넘기고, 넘긴 값은 명시한 false 까지 mockk.properties 를 덮는다. Gradle 속성이 없으면 시스템 속성을 정하지 않아 mockk.properties 값이 그대로 쓰이고, 여러 모듈이면 그 설정을 쓸 모듈마다(또는 공유 convention plugin 으로) 넘긴다.

내 클래스도 mockk.restrictedClasses 에 적어 막는다. MockK 문서는 이것이 내 코드베이스 안에서도 올바른 테스트 습관을 지키게 한다고 적는다.

이 소절이 세운 것 막는 목록은 켜기 전까지 경고로만 드러난다

System · 컬렉션 · Map · File · Path 와 그 하위 타입은 기본으로 막힌 목록에 있지만, throwExceptionOnBadMock 을 켜기 전에는 테스트를 멈추지 않는다. 다음 소절은 mock 을 다 쓴 뒤의 정리다.

정리 — clear 와 unmock 은 지우는 것이 다르다

여기서 읽을 것 — clear 와 unmock 이 각각 무엇을 지우는지, 정리 함수 · scoped mock · JUnit5 확장이 그 정리를 맡는 자리를 본다.

정의 clear 와 unmock — Clearing vs Unmocking

clear 는 mock 에 딸린 객체 내부 상태를 지워 빈 객체로 만든다.

unmock 은 mock 하려고 바꾼 클래스 변환을 mock 전 원래 상태로 되돌린다.

정리 함수마다 clear 인지 unmock 인지와 그 대상이 다르다.

함수하는 일대상
clearMocks(mock…)clear정한 mock
clearStaticMockk · clearConstructorMockkclearstatic mock · constructor mock
clearAllMocks()clear — 기본(currentThreadOnly=false)은 스레드 안전하지 않다보통 · object · static · constructor mock 모두
unmockkObject · unmockkStatic · unmockkConstructorunmock — 보통 객체 · 클래스로 되돌린다각 종류

scoped mock 은 인자로 넘긴 코드 블록이 끝나면 스스로 unmock 되는 mock 이다. mockkObject · mockkStatic · mockkConstructor 가 그런 블록을 받는다.

JUnit5 확장은 테스트 클래스가 끝난 @AfterAll 에서 unmockkAll 과 clearAllMocks 를 부르고, 아래 어노테이션이 그 정리를 바꾼다. ReleaseMocks 를 켜지 않으면 mock 은 clearAllStubsFromMemory 를 부를 때까지 MockK 에 등록된 채 남는다.

어노테이션바꾸는 정리단서

@MockKExtension.ReleaseMocks테스트마다(PER_CLASS 면 클래스 뒤) 테스트 스레드에서 만든 mock 을 메모리에서 푼다mockk.junit.extension.releaseMocks=true 와 같고, 푼 mock 은 다시 쓰지 못한다

kotest 는 기본으로 스펙 인스턴스 하나를 모든 테스트가 함께 써 mock 이 테스트 사이에 다시 만들어지지 않으므로, 테스트마다 mock 을 새로 만들거나 clearMocks 로 비운다. 그 쓰는 법은 1편이 맡는다.

이 소절이 세운 것 되돌릴 것은 바꿔 놓은 mock 뿐이다

보통 mock 은 clear 로 상태만 비우면 되지만, object · static · constructor mock 은 unmock 이나 scoped mock 으로 클래스 변환까지 되돌린다. 다음 소절은 mock 마다 넘기던 값을 한 곳에 모으는 설정 파일이다.

설정 파일 — 전역 기본값을 한 곳에 둔다

여기서 읽을 것 — mockk.properties 로 바꾸는 전역 기본값과, 옛 파일 자리 · 파일을 읽는 때의 규칙을 본다.

mock 마다 넘기던 relaxed · relaxUnitFun · recordPrivateCalls 같은 값을 전역으로 바꾸려면 설정 파일 src/test/resources/mockk.properties 에 적는다.

옛 파일 src/test/resources/io/mockk/settings.properties 도 읽지만, 두 파일이 다 있으면 mockk.properties 가 이기고 옛 자리는 앞으로 지워질 예정이다.

파일은 설정이 처음 필요할 때 한 번 읽어, MockK 의 UnifiedPropertiesLoader 를 불러온 클래스로더가 사는 동안 그 결과를 쓴다. 실패한 읽기만 캐시하지 않아 다시 시도하고, 부르는 쪽마다 설정 사본을 받아 MockKSettings 로 바꿔도 캐시된 파일 내용은 그대로다.

다만 Restricted Mocking 의 시스템 속성은 설정을 만들 때마다 다시 읽고, 직접 넘긴 PropertiesLoader 도 설정마다 불린다.

이 소절이 세운 것 설정 파일은 처음 필요할 때 한 번 읽힌다

mockk.properties 는 mock 마다 넘기던 기본값과 막는 목록을 한 자리에 모으고, 한 번 읽은 내용을 클래스로더가 사는 동안 그대로 쓴다. 아래 확인 소절이 막는 목록의 두 결과와 설정 줄을 원문 코드로 본다.

Android — 테스트 종류마다 되는 기능이 다르다

여기서 읽을 것 — MockK 가 지원하는 테스트 세 가지와, Android P 를 경계로 계측 테스트에서 빠지는 기능을 본다.

MockK 는 보통 단위 테스트와 두 가지 Android 계측 테스트(instrumented test) — Android P 전의 subclassing, Android P 부터의 inlining — 를 지원하고, 구현은 dexmaker 프로젝트를 바탕으로 한다. Android P 부터는 계측 테스트가 inline 계측을 다 써 object mock · static mock · final 클래스 mock 이 된다.

Android P 전에는 subclassing 만 쓸 수 있어 'all-open' 플러그인이 필요하고, 그 전 기기에서 클래스를 열려면 DexOpener 를 쓸 수 있다. 지원 기능 테이블은 아래와 같다.

피하는 법 없이 적힌 경고도 7개다.

  • top-level 함수 하나를 mock 하면 같은 파일에 선언된 다른 함수의 mock 이 지워진다 — 그 파일 클래스에 clearStaticMockk 를 부른 것과 같다
  • module-wide extension 을 함수 참조로 넘겨도 extensionFunc 하나가 아니라 pkg.FileKt 클래스 전체가 mock 된다
  • useDependencyOrder 를 켜면 초기화에 3~5% 쯤의 성능 부담이 더해진다
  • 자동 확인(ConfirmVerification)은 IDE 에서 돌리면 기대대로 안 될 수 있다 — 실패 예외를 Gradle 이 다루기 때문이다
  • 클래스의 마지막 mock 을 풀면 inline 계측을 되돌려, 테스트마다 같은 클래스를 mock 하는 suite 는 매번 클래스를 다시 변환하는 비용이 든다
  • matcher 의 타입 인자는 컴파일만 이끌고, 실행 중 지워진 제네릭 인자는 확인하지 않는다
  • 설정 파일은 처음 읽은 뒤 고쳐도 반영되지 않고, 처음 찾을 때 파일이 없었으면 나중에 더해도 캐시된 결과가 그대로다

알려진 문제 넷은 함께 쓰는 도구(PowerMock) · Kotlin 언어 기능(inline 함수) · JDK 버전(21+ · 16+)에 걸리고, 이 소절에 모은 기능 절의 경고 14개 가운데 7개는 피하는 법이 함께 적혀 있다. 마무리 절은 이 편의 결론을 한 줄씩 모은다.

이 절이 세운 것 고를 기능은 상황이, 쓸 수 있는지는 환경이 정한다

MockK 문서는 상황마다 기능을 짝지어 두었고, 그 기능을 쓸 수 있는지는 JDK 버전(16+ 의 spy · mockkStatic)과 Android 테스트 종류(P 전 계측 테스트의 object · static · constructor mock)가 정한다. 다음 절에서 만들기부터 한계까지를 한 줄씩 다시 잇는다.

8다시 보는 구조 — 만들고 답하고 확인하고 정리한다

이 절의 목표 만들기 · 답 정하기 · 확인 · 정리 · 한계를 한 줄씩 잇고, MockK 문서가 답한 물음과 다른 자리로 넘긴 물음을 가른다
왜 여기 있나 mock 만들기 · stub 과 검증 · 쓰는 법 · 한계가 절마다 따로 나왔다. 한 줄씩 이어야 테스트 한 바퀴의 어느 자리에서 무엇을 고르는지 한 번에 보인다.

절마다 세운 결론을 한 줄씩 모은다.

  • mock 종류 — mockk · relaxed mock · spy 는 대상 코드에 넘겨야 쓰이고, object · static · constructor mock 은 원래 이름 그대로 답하고 끝난 뒤 unmock 으로 되돌린다
  • answer — every 뒤의 answer 가 답을 정하고, 이어 붙인 answer 가 다음 호출의 답이 된다
  • 인자 matcher — 그냥 값은 eq() 로 맞추고, 같은 matcher 문법이 stub 과 verify 에 함께 쓰인다
  • 검증과 확인 장치 — verify 는 횟수 · 순서 · timeout 을 받고, confirmVerified · checkUnnecessaryStub 가 남은 호출과 쓰이지 않은 stub 을 예외로 알린다
  • Restricted Mocking — System · 컬렉션 · Map · File · Path 와 그 하위 타입은 막히되, 기본은 경고만 남긴다
  • 정리 — clear 는 mock 의 상태를 비우고 unmock 은 바꾼 클래스를 되돌린다
  • 한계 — inline 함수는 mock 하지 못하고, JDK 16+ 에서 spy · mockkStatic 이 안 될 수 있으며, Android P 전 계측 테스트의 지원 테이블에는 바꿔 놓는 mock 이 없다

일곱 줄은 한 문장으로 모인다 — MockK 는 대신할 대상에 맞는 함수로 mock 을 만들고, 답과 확인을 Kotlin 블록에 적게 하며, 남은 호출과 쓰이지 않은 stub 과 막힌 클래스를 따로 잡는다. 바꿔 놓은 mock 은 끝난 뒤 unmock 이나 scoped mock 으로 되돌리고, JDK · Android 버전에 따라 쓸 수 없는 mock 이 있다.

답이 난 것
  • MockK 는 협력자를 어떻게 mock 으로 바꾸나? 대상 코드에 넘길 인스턴스는 mockk · relaxed mock · spyk 로 만들고, 대상 코드가 이름으로 부르는 object · top-level 함수 · 새로 만드는 객체는 mockkObject · mockkStatic · mockkConstructor 로 그 자리에서 바꾼다.
  • 답은 어떻게 정하고 호출은 어떻게 확인하나? every 뒤의 answer 로 답을 정하고 verify 로 기록된 호출의 횟수와 순서를 센다. 둘 다 같은 인자 matcher 로 어느 호출인지 가린다.
  • 무엇이 남지 않게 확인하나? confirmVerified 는 확인하지 않은 호출을, checkUnnecessaryStub 는 쓰이지 않은 stub 을 예외로 알린다. JUnit5 에서는 어노테이션으로 테스트마다 부른다.
  • 무엇은 mock 하지 말아야 하나? System · Collection · Map · File · Path 와 그 하위 타입이다. Restricted Mocking 이 기본으로 막되 경고만 남기고, throwExceptionOnBadMock=true 면 테스트가 실패한다.
  • 어디서 안 되나? inline 함수는 mock 하지 못하고, JDK 16+ 에서 spy · mockkStatic 이 안 될 수 있으며, Android P 전 계측 테스트의 지원 테이블에는 object · static · constructor mock 과 private 함수 mock 이 없다.
