[학습] 다섯 주제 지도 — 테스트 · 아키텍처 · 출시

kotest · MockK · 헥사고날 아키텍처 · ArchUnit · 피처 플래그가 저마다 무엇을 풀고 무엇을 조심하라는지 한 줄씩 알고, 원문이 직접 이은 자리(mock · 테스트 어댑터 · onion 검사 · 결정 주입)를 따라 다섯 주제가 테스트에서 만난다는 것을 안 뒤 이어 읽을 편을 고른다.

읽는 사람 — 배우는 사람 — Kotlin 이나 Java 로 서버를 만들고 JUnit 으로 단위 테스트를 써 본 개발자. kotest · MockK · ArchUnit 은 써 본 적이 없거나 이름만 들었고, 헥사고날 아키텍처 · 피처 플래그는 말만 들어 봤다. 0편(지도)을 먼저 읽고 필요한 편을 골라 읽는다.

1물음 — 다섯 주제는 무엇을 풀고 어디서 만나나

이 절의 목표 다섯 주제를 잇는 선은 한 원문이 직접 적은 연결뿐이고, 그 선이 mock · 자동 테스트 · Dependency Injection 을 지나 테스트 쪽으로 모인다는 것을 한 그림으로 안다
왜 여기 있나 다섯 주제는 원문도 저자도 달라 이름만 보면 서로 무관해 보인다. 어디서 이어지는지 먼저 알아야 뒤 절의 한 줄씩이 그림의 어느 선 위에 놓이는지 보인다.

kotest · MockK · 헥사고날 아키텍처 · ArchUnit · 피처 플래그는 저마다 어떤 문제를 풀고, Kotlin 서버 하나 안에서 서로 어디에서 만나나? 피처 플래그는 feature flag 를 옮긴 말이고, Pete Hodgson 의 원문은 Feature Toggle 이라 부르며 두 이름을 같은 뜻으로 쓴다.

다섯 원문은 저자도 쓰인 때도 달라, 서로를 잇는 것은 한 원문이 그 연결을 직접 적은 자리뿐이다. 아래 그림의 선이 그 자리이고, 선이 지나는 상자를 따라가면 다섯 주제가 어디서 만나는지 보인다.

공통 배경 — mock 이라는 말과 테스트의 층

여기서 읽을 것 — 원문들이 테스트에서 진짜 대신 끼우는 것을 무엇이라 부르는지와, 헥사고날 원문이 테스트를 어떤 층으로 나누는지 — 원문이 쓴 만큼

테스트에서 진짜 협력자 대신 끼우는 대역을 원문들은 대개 mock 이라 부른다. test double 이라는 말은 kotest 문서 첫 문장에 한 번 나온다 — kotest 에는 mock 기능이 없고 test double 을 만드는 fakery 만 있다.

정의 mock object — 대신 답하면서 호출을 지켜보는 객체

Cockburn 이 MockObjects.com 에서 옮겨 온 정의다. mock object 는 진짜 구현의 바깥 동작을 흉내 내는 대신 구현이면서, 다른 객체가 제 함수를 어떻게 부르는지 지켜보고 미리 정한 기대와 비교하는 객체다.

어긋나면 그 자리에서 테스트를 멈춰 알리고, 그 자리에서 못 잡은 것은 테스트하는 쪽이 부르는 검증 함수가 기대가 다 맞았는지 확인해 알린다.

주의 Cockburn 의 mock — 바깥 접점 하나를 대신한다

mock object 운동에서는 mock 을 바깥 접점만이 아니라 애플리케이션 곳곳에 쓴다. Cockburn 은 그 말을 빌려, 메모리 안에서 secondary actor(애플리케이션이 답을 얻거나 알리려고 부르는 바깥 쪽 — 데이터베이스 같은 것)를 대신하는 것만 mock 이라 부른다.

AWS 안내서는 헥사고날 아키텍처에서 테스트 셋이 저마다 무엇을 확인하고, 바깥 자리에 무엇을 두는지 적는다.

테스트무엇을 확인하나바깥 자리에 두는 것
비즈니스 로직 테스트비즈니스 로직을 떼어 확인한다 — 도메인 모델 단위 테스트와 합쳐 결합은 낮게, 커버리지는 높게mock 이나 fake 어댑터
통합 테스트secondary adapter 가 바깥 서비스를 제대로 부르는지 — 비즈니스 로직은 확인하지 않는다그 adapter 가 부르는 바깥 서비스
end-to-end 테스트들어온 요청의 생애 전체 — 진입점으로 요청을 보내 비즈니스 요구를 채웠는지 본다진입점(REST API · 큐)부터 모든 연결 지점
secondary adapter 는 애플리케이션이 부르는 바깥 쪽의 어댑터다. 로직 테스트가 mock 으로 바깥을 떼어 내고, 그 바깥을 부르는 코드는 통합 테스트가 따로 맡는다.
결론 로직은 mock 을 끼워 떼어 보고, 어댑터는 통합 테스트가 본다

mock 을 말하는 원문(kotest · MockK · Cockburn · AWS 안내서)에서 mock 은 모두 협력자를 대신하는 대역이다. 그 대역을 어느 자리에 끼우는지가 「만나는 자리」 절에서 원문마다 다르게 나온다.

이 절의 결론 선은 mock · 자동 테스트 · Dependency Injection 을 지난다

그 가운데 둘은 테스트 쪽 말이다 — mock 은 진짜 대신 끼우는 대역이고, 자동 테스트는 사람 없이 애플리케이션을 부르는 테스트다. 다음 절은 다섯 원문이 저마다 내세운 답을 먼저 모은다.

2다섯 원문의 답 — 문제는 다르고 만나는 곳은 테스트다

이 절의 목표 다섯 원문이 저마다 내세운 답과 근거를 본문 전에 알고, 다섯 모두 자동 테스트를 말하는 데서 만난다는 것을 안다
왜 여기 있나 주제마다 한 소절씩 읽기 전에 원문마다 스스로 내세운 답을 먼저 알면, 뒤 소절이 그 답의 근거를 채우는 자리로 읽힌다.

3다섯 주제 — 저마다 푸는 문제와 조심할 것

왜 여기 있나 앞 절의 답은 한 줄씩이라, 그 답이 원문의 어느 문장에서 왔는지와 원문이 무엇을 조심하라는지가 아직 비어 있다.

kotest — 스타일과 matcher 로 Kotlin 테스트를 쓴다

여기서 읽을 것 — kotest 가 무엇을 푸는지, 세 부분으로 나눈 설계, JUnit · AssertJ 대신 쓰는 때, 그리고 mock 과 함께 쓸 때 걸리는 기본값

  • 무엇을 푸나 — Kotlin 을 위한 유연하고 폭넓은 테스트 프로젝트다. multiplatform 을 지원해 JVM · JavaScript · Native 에서 같은 테스트 구조로 돈다
  • 핵심 설계 원칙 — 테스트 프레임워크 · assertion 라이브러리 · property 테스트(property-based testing — 입력을 generator 로 만들어 같은 성질을 여러 번 확인하는 테스트) 셋을 따로 쓸 수 있게 나눴다. assertion 만 JUnit 과 써도 되고, 테스트 모양은 여러 테스트 스타일 가운데 맞는 것을 고른다
  • 언제 쓰나 — Java 에서 Kotlin 으로 옮겨 오며 흔한 Java 테스트 라이브러리(JUnit · AssertJ) 대신 쓸 때
  • 대표 한계 — 기본으로 스펙 인스턴스 하나에서 모든 테스트가 돌아, mock 이 테스트 사이에 다시 만들어지지 않는다. 테스트 전에 새로 만들거나(beforeTest) 뒤에 지운다(clearMocks)

kotest 테스트 하나는 테스트 스타일과 matcher 로 적는다. 테스트 스타일은 테스트를 적는 문법의 틀이고, kotest 는 스타일을 여럿 두어 필요에 맞는 것을 고르게 한다. matcher 는 값이 기대와 맞는지 확인하는 assertion 함수이고, kotest 가 여러 타입에 쓸 matcher 를 300개 넘게 준다. matcher 는 모두 extension 함수라 값 뒤에 점을 찍으면 IDE 가 자동 완성으로 찾아 준다. 문서 첫 쪽의 첫 예는 FunSpec 스타일로 테스트 둘을 적고, shouldBe · should 로 값을 확인한다.

data-driven testing 은 입력 조합을 데이터로 적어 withData 에 넘기면 확인 블록이 조합마다 돌아, 같은 확인을 아주 많은 조합에도 쉽게 돌린다. property 테스트는 입력을 적지 않는다 — checkAll 이 자동으로 만든 값을 넘기고, 테스트는 어떤 값이 와도 맞아야 할 성질을 확인한다.

이 줄들이 넘기는 물음은 1편이 받는다 — kotest 는 Kotlin 테스트를 어떤 모양(스펙 스타일 · matcher · property 테스트)으로 쓰게 하고, 그 모양을 쓸 때 무엇을 조심해야 하나?

MockK — 엄격한 mock 으로 협력자를 바꾼다

여기서 읽을 것 — MockK 가 mock 으로 무엇을 하는지, 엄격한 기본값, Spring · Quarkus 에서 쓰는 때, 그리고 README 가 적은 알려진 문제

  • 무엇을 푸나 — Kotlin 테스트에서 협력자를 mock 으로 바꾼다. 부를 때 돌려줄 답을 정하고, 받은 호출을 확인한다
  • 핵심 설계 원칙 — mock 은 기본이 엄격하다(strict). 쓸 동작을 먼저 정해 줘야 하고, 확인하지 않은 호출이 남았는지도 confirmVerified 로 본다
  • 언제 쓰나 — 테스트 대상이 부르는 협력자를 바꿔 끼울 때. Spring 쪽은 springmockk(Spring Boot Kotlin 공식 튜토리얼이 소개한 Spring 지원 프로젝트), Quarkus 쪽은 bean 을 mock 하게 해 주는 quarkus-mockk 가 있다
  • 대표 한계 — inline 함수는 mock 할 수 없고, JDK 16 이상에서는 spy(mock 과 진짜 객체를 섞어 쓰는 것)와 static 을 mock 하는 mockkStatic 이 안 될 수 있다

README 의 첫 예다. every 는 mock 의 함수가 맞는 호출에 무엇을 돌려줄지 정하고(stub), verify 는 그 호출이 있었는지, confirmVerified 는 verify 하지 않은 호출이 남지 않았는지 확인한다.

README 가 「Known issues」 에 적은 문제는 이렇다.

  • PowerMock 과 함께 돌리려면 우회가 필요하다 — 우회 뒤에 두루 쓸 만한지는 README 도 모른다고 적는다
  • inline 함수는 mock 할 수 없다
  • JDK 21 이상에서는 테스트가 WARNING: A Java agent has been loaded dynamically 를 찍는다(JEP 451)
  • JDK 16 이상에서는 spy 와 mockkStatic 이 안 될 수 있고, InaccessibleObjectException · IllegalAccessException 이 날 수 있다
결론 MockK 의 mock 은 엄격하게 시작한다

이 줄들이 넘기는 물음은 2편이 받는다 — MockK 는 Kotlin 코드의 협력자를 어떻게 mock 으로 바꾸고 호출을 검증하며, 무엇은 mock 하지 말아야 하나?

헥사고날 아키텍처 — 포트 뒤로 바깥 기술을 뗀다

여기서 읽을 것 — 헥사고날 아키텍처가 풀려는 결합, 포트와 어댑터라는 원칙, 쓰라는 때, 그리고 AWS 안내서가 적은 대가

  • 무엇을 푸나 — 2005년 Alistair Cockburn 이 낸 포트와 어댑터 패턴이다. 비즈니스 로직이 데이터베이스의 stored procedure 와 UI 에 박히면 결합이 단단해져 데이터베이스 이전과 UX 현대화가 막힌다 — 이 패턴은 비즈니스 로직을 인프라 코드에서 떼어, 부품을 데이터 저장소 · UI 없이 따로 테스트하고 그 기술에 묶이지 않게 한다
  • 핵심 설계 원칙 — 애플리케이션은 포트라는 인터페이스로만 바깥과 말하고, 어댑터가 기술마다 주고받음을 옮긴다. 기술이 아니라 목적으로 설계하고, 안쪽 코드는 바깥으로 새지 않는다(Cockburn)
  • 언제 쓰나 — 부품을 온전히 테스트하고 싶을 때 · 여러 클라이언트가 같은 도메인 로직을 쓸 때 · UI 와 데이터베이스를 애플리케이션 로직과 상관없이 주기적으로 바꿔야 할 때 · 입력 제공자와 출력 소비자가 여럿이라 로직을 맞추다 코드가 복잡해질 때
  • 대표 한계 — 어댑터 코드는 입력 · 출력이 여럿이거나 시간이 지나며 바뀔 때만 값을 한다. 그렇지 않으면 유지보수할 층이 하나 늘고, 층이 하나 더해져 지연이 생길 수 있다

아래는 AWS 안내서의 구조 그림이다 — 가운데 육각형이 애플리케이션 부품이고, 포트마다 기술별 어댑터가 붙는다. 왼쪽에는 애플리케이션을 쓰는 쪽(모바일 · 웹 · 테스트 스크립트), 오른쪽에는 애플리케이션이 쓰는 쪽(데이터베이스 · 파일 시스템 · 카드 · 인터넷 뱅킹)의 어댑터가 있다.

포트는 애플리케이션 부품으로 들어가는, 기술과 무관한 입구다 — USB 포트에 USB 어댑터만 맞으면 어떤 장치든 컴퓨터와 이어지는 것과 같다. 어댑터는 특정 기술로 포트를 거쳐 주고받고, 같은 포트에 GraphQL 어댑터를 더해도 REST API · 포트 · 애플리케이션은 그대로다.

안내서의 「Issues and considerations」 에는 유지보수 부담 · 지연과 함께 이런 항목도 있다.

  • DDD — 헥사고날 아키텍처는 domain-driven design 과 특히 잘 맞는다. 애플리케이션 부품 하나가 DDD 의 sub-domain 하나다
  • 테스트 용이성 — 입력 · 출력을 추상화하므로, 느슨한 결합 덕에 단위 테스트와 떼어 놓은 테스트가 쉬워진다
  • 복잡도 — 비즈니스 로직을 인프라 코드에서 떼는 복잡도는 조심해 다루면 민첩성 · 테스트 커버리지 · 기술 적응력을 주지만, 그렇지 않으면 풀기 어려운 문제가 된다
결론 헥사고날은 바깥을 포트 뒤로 떼고 그 대가로 어댑터 층을 둔다

이 줄들이 넘기는 물음은 3편이 받는다 — 헥사고날 아키텍처는 애플리케이션을 UI · DB 같은 바깥 기술에서 어떻게 떼어 놓고, 그 대가로 무엇을 치르나?

ArchUnit — 바이트코드를 읽어 아키텍처 규칙을 테스트한다

여기서 읽을 것 — ArchUnit 이 무엇을 검사하는지, 바이트코드를 가져와 규칙을 거는 설계, 쓰는 때와 모듈, 그리고 미리 만든 검사의 범위

  • 무엇을 푸나 — Java 코드의 아키텍처를 검사한다. 패키지 · 클래스 사이, 레이어 · slice(패키지로 나눈 클래스 덩어리) 사이의 의존과 순환 의존 같은 것을 본다
  • 핵심 설계 원칙 — 주어진 Java 바이트코드를 분석해 모든 클래스를 Java 코드 구조로 가져온 뒤 검사한다. 주된 초점은 아키텍처 · 코딩 규칙을 평범한 Java 단위 테스트 프레임워크로 자동 테스트하는 것이다
  • 언제 쓰나 — 아키텍처 규칙을 테스트가 자동으로 지키게 하고 싶을 때. JUnit 4 · 5 · 6 모듈이 가져온 클래스를 캐시하고, Kotlin 에서도 JUnit 지원을 Java 와 거의 같게 쓴다
  • 대표 한계 — 흔한 아키텍처 스타일을 검사하는 Library API(미리 만든 규칙 모음)는 지금 layered 아키텍처와 onion 아키텍처(헥사고날 아키텍처 · 포트와 어댑터라고도 부른다) 두 가지만 편하게 검사한다

피처 플래그 — 설정 하나로 숨긴 기능을 켠다

여기서 읽을 것 — 피처 플래그가 푸는 문제와 기본 원리, 플래그의 쓰임, 그리고 Fowler 가 붙인 경고와 마지막 선택이라는 판정

  • 무엇을 푸나 — 2주마다 출시하는데 석 달 걸릴 기능을 만들 때처럼, 출시 주기보다 오래 걸리는 기능을 mainline 에 두고 CI(Continuous Integration)를 하면서도 덜 만든 기능이 출시에 드러나지 않게 한다
  • 핵심 설계 원칙 — 설정 파일에 기능마다 플래그를 두고, 실행 중인 애플리케이션이 그 플래그로 새 기능을 보일지 정한다. 토글 검사는 기능을 숨기는 데 필요한 최소한의 toggle point — 사용자를 그 기능으로 이끄는 입구 — 에만 둔다
  • 언제 쓰나 — 덜 만든 기능 숨기기(release toggle) · A/B 테스트(experiment toggle) · 운영 담당자의 제어(ops toggle) · 사용자 일부에게만 열기(permissioning toggle)
  • 대표 한계 — 토글은 복잡도를 더한다(Hodgson). 구현 방법과 설정 관리 도구로 다스리되, 시스템의 토글 수 자체를 줄여야 한다

Fowler 는 flag 와 toggle 을 같은 뜻으로 섞어 쓰고, 지금은 flag 가 가장 흔한 말이 됐다고 각주에 적는다. 플래그는 대개 실행 중에 정하지만 build 때 정하는 release toggle 도 있고, 그 작은 이점은 새 기능 코드가 출시 실행 파일에 아예 들어가지 않는 것이다.

bliki 의 그림이다 — 왼쪽 UI 정의의 toggle 태그가 설정 파일의 petSurvey 값을 본다. true 면 실행 중인 프로그램에 pet survey 를 보이고, false 면 보이지 않는다.

UI 가 없는 기능(새 가격 알고리즘 같은 것)은 애플리케이션 코드에서 조건문이나 Dependency Injection 으로 이은 strategy 로 플래그를 본다. 조건문이 가장 쉽지만, 플래그를 보는 자리를 줄이려면 polymorphic substitution 같은 기법을 쓰라고 Fowler 는 권한다.

  • 드러남 — UI 를 토글 태그로 감싸는 것을 잊으면 숨길 기능이 드러난다. 보이면 안 되는 것을 하나하나 부르지 않고는 그런 테스트를 짜기 어렵고, 그 하나하나도 함께 잊기 쉽다
  • 조합 테스트 — 모든 조합을 테스트할 필요는 없다. release flag 는 다음 출시에 켤 플래그만 켠 조합과 모두 켠 조합, 두 가지면 대개 된다
  • 걷어 내기 — 기능이 운영에 자리 잡으면 release flag 를 설정 파일과 그 플래그를 쓰는 모든 코드에서 걷는다. 그러지 않으면 아무도 쓰는 법을 기억 못 하는 토글이 쌓인다
  • 마지막 선택 — 먼저 기능을 쪼개 조금씩 내보낸다 — 작게 자주 내보내면 위험이 줄고 사용자가 실제로 쓰는 모습에서 피드백을 얻는다. 그래도 숨겨야 하면 Keystone Interface(UI 진입점만 빼고 다 만든 뒤 마지막 출시 주기에 UI 를 붙이는 방법)를 쓰고, 둘 다 안 될 때만 release flag 를 쓴다
결론 피처 플래그는 설정 하나로 숨긴 기능을 켜고 걷어 낼 일을 남긴다

이 줄들이 넘기는 물음은 5편이 받는다 — 피처 플래그는 배포와 출시를 어떻게 떼어 놓고, 플래그 종류마다 어떻게 다르게 다루며, 늘어난 플래그가 무엇을 비용으로 남기나?

4만나는 자리 — 원문이 서로를 부르는 곳

이 절의 목표 그림의 선마다 그 연결을 적은 원문 문장과 코드를 알고, 서로를 이름으로 부르는 원문은 kotest 문서와 ArchUnit 가이드뿐이라는 것을 안다
왜 여기 있나 주제마다 따로 세운 한 줄로는 첫 그림의 선 하나하나가 어느 원문의 어느 문장인지 보이지 않는다.

다른 주제를 이름으로 부르는 원문은 둘이다 — kotest 문서가 MockK 를, ArchUnit 가이드가 헥사고날 아키텍처를 부른다. 나머지 선은 두 원문이 같은 말(mock · 자동 테스트 · Dependency Injection)을 저마다 써서 이어진다.

주의 원문 예제의 언어 — 헥사고날 · 피처 플래그는 Kotlin 이 아니다

kotest · MockK 의 예는 Kotlin 이고, ArchUnit 은 Java 예 옆에 Kotlin 예를 하나 둔다. 헥사고날은 Cockburn 이 Java, AWS 패턴 문서가 Python 이고, 피처 플래그는 Hodgson 이 JavaScript 와 Rails erb, Fowler 가 jsp 태그다. OpenFeature 문서는 Java SDK 쪽을 따로 둔다.

kotest 와 MockK — mock 기능은 바깥에서 끼운다

여기서 읽을 것 — kotest 가 mock 을 어디서 가져오라고 하는지, 그리고 MockK 와 함께 쓸 때 처음 부딪히는 오류의 까닭

kotest 문서는 mock 을 kotest 밖에서 끼우라고 한다 — 좋아하는 mocking library 를 손쉽게 붙일 수 있다며 MockK 를 예로 든다.

그 예에 테스트를 하나 더 붙이면 아래처럼 된다 — 스펙 인스턴스가 하나라 두 테스트가 같은 mock 을 쓴다.

두 테스트가 mock 하나를 나눠 쓴다

결론 kotest 와 MockK 는 테스트 하나 안에서 만나고 스펙 인스턴스를 나눠 쓴다

헥사고날과 테스트 — 포트 양쪽에 테스트 어댑터가 낀다

여기서 읽을 것 — 헥사고날 원문이 테스트를 포트 양쪽 어디에 끼우는지 — Cockburn 이 매긴 개발 순서와 AWS 안내서의 mock 주입

Cockburn 이 밝힌 이 패턴의 의도부터 테스트다. 사용자 · 프로그램 · 자동 테스트 · batch 스크립트가 애플리케이션을 똑같이 부르고, 실제 장치와 데이터베이스 없이 따로 개발하고 테스트하게 한다.

그래서 같은 포트의 어댑터로 FIT(표로 적은 테스트를 읽어 애플리케이션을 부르는 프레임워크) 같은 test harness 와 메모리의 mock 데이터베이스가 함께 든다. Cockburn 은 애플리케이션을 부르는 쪽을 primary · driving, 애플리케이션이 부르는 쪽을 secondary · driven 이라 한다.

개발 순서driving 어댑터 — 애플리케이션을 부르는 것driven 어댑터 — 애플리케이션이 부르는 데이터베이스
1FIT test harness메모리의 mock 데이터베이스
2GUI 를 붙인다아직 mock 데이터베이스
3 · 통합 테스트Cruise Control 같은 곳에서 도는 자동 테스트 스크립트테스트 데이터를 담은 진짜 데이터베이스
4 · 실제 사용애플리케이션을 쓰는 사람운영 중인 데이터베이스
mock 은 driven 포트에, FIT 는 driving 포트에 낀다. Cockburn 은 primary actor 를 대신할 자연스러운 테스트 어댑터가 FIT 이고 secondary actor 를 대신할 것이 mock 이라 짚는다.
주의 대응은 결과다 — 설계를 건너뛰는 지름길로 쓰지 않는다

Cockburn 은 primary · secondary 와 FIT · mock 의 대응을 기억해 두되, 포트와 어댑터를 따른 결과로만 쓰고 그 설계를 건너뛰는 지름길로 쓰지 말라고 한다. 포트와 어댑터로 얻는 궁극의 이득은 애플리케이션을 온전히 떼어 돌리는 것이다.

AWS 패턴 문서도 같은 말을 한다 — 어댑터를 바꿔 끼울 수 있어 의존을 mock 하기 쉽고, 데이터베이스 코드 없이 비즈니스 로직을 단위 테스트하며, 도메인 모델은 mock 클래스를 주입해 테스트한다. 다만 그 mock 의 코드 모양은 원문마다 다르다 — Cockburn 은 저장소 인터페이스를 손으로 구현하고, kotest 문서의 MockK 예는 저장소 mock 을 라이브러리로 만든다.

ArchUnit 과 헥사고날 — onion 검사가 의존 방향을 본다

여기서 읽을 것 — ArchUnit 가이드가 헥사고날 아키텍처를 무엇으로 부르고, 그 의존 방향을 어떤 규칙으로 검사하는지

ArchUnit 가이드는 onion 아키텍처를 헥사고날 아키텍처 · 포트와 어댑터라고도 부른다. 그 구조를 검사하는 규칙은 Library 층이 미리 만들어 둔 onionArchitecture() 이고, 검사에 쓸 도메인 패키지와 어댑터 패키지를 아래처럼 이어 정의한다.

ArchUnit 가이드 「Onion Architecture」
1onionArchitecture()
2 .domainModels("com.myapp.domain.model..")도메인 — 애플리케이션의 핵심
3 .domainServices("com.myapp.domain.service..")

  • applicationServices 는 애플리케이션과 유스케이스를 돌리는 서비스 · 설정이다 — domain 을 써도 되지만, domain 에서 애플리케이션 쪽으로 가는 의존은 없어야 한다
  • adapter 는 바깥 시스템 · 인프라와 잇는 로직이다 — 도메인과 애플리케이션을 써도 되지만 어댑터끼리는 서로 의존하지 않고, domain 과 애플리케이션 패키지는 어떤 adapter 에도 의존하지 않는다

가이드는 이 검사의 뜻이 가이드가 링크한 onion 아키텍처 글(jeffreypalermo.com)을 따른다고 밝힌다. pipes and filters 나 비즈니스 로직과 기술 인프라의 분리 같은 다른 스타일은 앞으로 더할 수 있다고만 적는다.

결론 ArchUnit 은 헥사고날의 의존 방향을 패키지 규칙으로 검사한다

규칙 문법과 layered · slice 검사, 기존 위반은 기록해 두고 새 위반만 알리는 freezing 같은 상세는 4편이 다룬다.

피처 플래그와 테스트 — 결정을 주입해 두 경로를 확인한다

여기서 읽을 것 — 토글 결정을 생성 때 주입하면 테스트가 무엇이 쉬워지는지, 그리고 헥사고날 원문이 같은 Dependency Injection 을 어디에 쓰는지

toggle router(어느 코드 경로를 켤지 정하는 것)로 기능을 켜고 끌 수 있으면, 자동 테스트가 토글 양쪽을 모두 확인한다고 Hodgson 은 적는다. 산출물이 CD 파이프라인을 지날 때는 운영에서 토글이 켜질지 모르니, 켠 상태와 끈 상태를 다 테스트해야 한다.

Hodgson 의 Inversion of Decision(토글 결정을 객체가 묻지 않고 생성 때 넘겨받게 하는 기법)은 그 테스트를 더 쉽게 한다. 아래 레인이 결정이 흐르는 순서다.

5다시 보는 지도 — 한 줄씩과 이어 읽을 편

이 절의 목표 다섯 주제의 한 줄과 만나는 선을 다시 모으고, 원문이 답한 것과 깊은 편으로 넘긴 물음을 가른다
왜 여기 있나 선과 한 줄이 여러 절에 흩어져 있다. 한자리에 모아야 무엇이 답이 났고 어느 편이 이어받는지 보인다.
  • kotest — Kotlin 테스트를 쓰는 틀이다. 세 부분을 따로 쓸 수 있고, 기본 스펙 인스턴스가 하나라 mock 은 테스트마다 새로 만들거나 지운다
  • MockK — 협력자를 엄격한 mock 으로 바꿔 every 로 답을 정하고 verify 로 확인한다. inline 함수는 mock 할 수 없다
  • 헥사고날 아키텍처 — 포트와 어댑터로 비즈니스 로직을 바깥 기술에서 떼어 따로 테스트한다. 어댑터 층은 입력 · 출력이 여럿이거나 바뀔 때만 값을 한다
  • ArchUnit — 바이트코드를 가져와 아키텍처 규칙을 단위 테스트로 검사한다. 미리 만든 아키텍처 검사는 layered · onion 두 가지다
  • 피처 플래그 — 설정의 플래그로 덜 만든 기능을 숨긴 채 mainline 에 둔다. 토글은 복잡도를 더하므로 다 쓴 release flag 는 걷어 내고, release flag 는 마지막 선택으로 쓴다

  • 헥사고날 아키텍처는 애플리케이션을 UI · DB 같은 바깥 기술에서 어떻게 떼어 놓고, 그 대가로 무엇을 치르나? 3편
  • ArchUnit 은 패키지 · 레이어 의존 같은 아키텍처 규칙을 어떻게 테스트 코드로 적고 지키게 하며, 무엇은 잡지 못하나? 4편
  • 피처 플래그는 배포와 출시를 어떻게 떼어 놓고, 플래그 종류마다 어떻게 다르게 다루며, 늘어난 플래그가 무엇을 비용으로 남기나? 5편
  • kotest 테스트 안에서 ArchUnit 규칙을 어떻게 돌리나? 저자가 다룰 곳을 밝히지 않았다 — ArchUnit 가이드는 Java 코드를 돌리는 테스트 프레임워크면 함께 쓴다고만 적는다(4편)
  • 헥사고날 원문의 예제를 Kotlin 으로 옮기면 어떤 모양인가? 저자가 다룰 곳을 밝히지 않았다 — Cockburn 은 Java, AWS 안내서는 Python 으로 보인다(3편)

다음 읽을 곳은 물음이 맞는 편이다 — 테스트 모양은 1편, mock 은 2편, 구조는 3편, 구조 검사는 4편, 출시 토글은 5편. 다섯 원문은 kotest 문서 · MockK · Cockburn 원문 · AWS 안내서 · ArchUnit 가이드 · Hodgson 원문 에 있다.
