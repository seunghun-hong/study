315장 동시성 — 갱신 없이도 경쟁 조건이 생긴다

이 절의 목표 갱신을 차례로 처리하는 상태 기계들도 메시지가 엇갈리면 어긋난다는 것을 전화 장면으로 안다

저자는 1960년대 전화 걸기를 예로, Bob 이 Alice 에게 거는 동안 전화국과 두 사람이 주고받는 신호를 시간 차례로 그린다. 그림이 보이듯 메시지는 상대에게 닿는 데 시간이 걸린다. 뒤에 나오는 경쟁 조건도 이 시간 차에서 생긴다고 이 문서는 읽는다.

두 사람이 함께 걸면 — TILT! 가 찍힌다

여기서 읽을 것 — Bob 이 거는 바로 그때 Alice 도 수화기를 들면, 어느 걸음에서 Alice 의 기계가 받을 수 없는 사건을 받는지

전화국은 Alice 의 벨을 울리려 했지만 소리가 나기 전에 Alice 가 Bob 에게 걸려고 수화기를 들었다. 전화국 쪽에서는 벨을 울렸고 Alice 가 들었으니 두 사람을 잇지만, Alice 는 발신음을 기다리고 Bob 은 '여보세요' 를 듣지 못한다.

저자는 이 장면을 테스트로 다시 만든다. 통화마다 전화국 기계를 하나씩 두어 기계가 4개다.

저자는 이 경쟁의 창이 좁아 여러 번 돌려서야 이 로그를 얻었다고 적는다. 경쟁 조건(race condition)을 이 장면으로 말하면 이렇다 — 경쟁 조건은 메시지가 엇갈려 서로 주고받는 상태 기계끼리 어긋나는 일이다.

통설이 생긴 사정 — 멀티코어의 걱정

여기서 읽을 것 — 함수형 언어가 동시성 때문에 인기를 얻은 사정과, 15장의 장면이 그 추론의 어디를 무너뜨리는지

저자의 결론은 사정 하나와 장면 하나에 기댄다. 아래 표는 통설이 기댄 사정과 15장이 보인 장면을 맞댄다.

이 소절이 세운 것 갱신을 없애는 것은 경쟁 조건의 해법이 아니다

15장은 함수형이 동시성 문제의 한 갈래만 없앤다고 답한다. 다음 절은 16장에서 디자인 패턴이 함수형으로 옮겨질 때 무엇이 남는지 본다.

416장 디자인 패턴 — 함수형에서도 모양이 같다

이 절의 목표 Abstract Server · Adapter · Command · Composite · Decorator 가 Clojure 에서 GOF 그림과 같은 의존을 이룬다는 것을 안다
왜 여기 있나 디자인 패턴이 함수형에는 필요 없다는 소문이 틀렸다는 결론은 패턴마다 그림과 코드가 맞아떨어지는 데 기댄다

아래 표는 이 절이 다루는 다섯 패턴이 푸는 문제와, Clojure 에서 주로 쓰는 장치를 늘어놓는다. 패턴마다 GOF 그림을 먼저 보고 Clojure 코드로 옮기는 차례는 같다.

저자는 디자인 패턴(design pattern)을 이렇게 정의한다 — 디자인 패턴은 특정한 맥락에서 흔한 문제에 붙인 이름 있는 해법이다. 스위치가 전등을 켜게 하라는 문제에서 Switch 가 Light 를 바로 부르면 선풍기나 텔레비전은 켤 수 없어, 두 클래스 사이에 Switchable 인터페이스를 끼운다.

Composite — 여럿임을 부르는 쪽에서 감춘다

여기서 읽을 것 — doseq 로 여러 전등을 켜는 코드와 composite-switchable 이 갈리는 점, 그리고 도형 묶음이 새 값을 돌려주는 모양

516장 Visitor와 Abstract Factory — 세부가 빠진다

이 절의 목표 Visitor 의 이중 디스패치는 닫힌 클래스 때문에 붙은 세부이고, 90도 회전이 남기는 의존 문제는 인터페이스를 떼어 푼다는 것을 안다
왜 여기 있나 소문이 옳은 자리는 Visitor 다. 무엇이 땜질이고 무엇이 패턴의 몸인지 갈라야 16장의 결론이 대체로 그대로 쓰인다는 까닭이 보인다

앞 절의 다섯 패턴은 Clojure 에서 GOF 그림에 거의 그대로 맞았다. 이 절의 두 패턴에서는 GOF 형태의 일부가 언어 제약 때문에 붙었다는 것이 드러나고, 저자는 그 일부를 떼어 내면서도 의존 규칙을 지키는 길을 보인다.

저자의 Clojure 판에서 빠지는 것남는 것
VisitorShapeVisitor 인터페이스와 이중 디스패치하위 타입마다 구현을 모은 모듈(90도 회전)
Abstract Factory하위 타입마다의 make 함수인터페이스 뒤로 생성을 숨기는 구조
빠지는 것은 닫힌 클래스와 90도 회전에서 생기는 세부이고, 패턴의 구조는 남는다.

Visitor — 하위 타입이 함수로 바뀐다

여기서 읽을 것 — Java 의 accept 와 visit 가 두 번 디스패치하는 차례와, Clojure 의 to-json 이 이중 디스패치 없이 같은 일을 하는 까닭

도형을 문자열로 바꾸는 기능을 더하려 한다. to-string 을 인터페이스에 더하면 쉽지만 XML · JSON · YAML 요구가 끝없이 이어지고, 저자는 그 메서드들로 도형 인터페이스를 더럽히지 않으려고 Visitor 를 쓴다.

저자는 하위 타입이 ShapeVisitor 의 메서드로 바뀌는 이 모양을 90도 회전(90-degree rotation)이라 부른다 — 90도 회전은 타입 모델의 하위 타입이 다른 모듈의 메서드로 바뀌는 변환이다. Java 에서 JSON 을 얻는 길은 아래처럼 디스패치를 두 번 거친다.

Java 에서 JSON 을 얻는 차례 — 이중 디스패치

저자는 이 복잡함이 언어 기능 하나 때문이라고 본다 — 닫힌 클래스다. 닫힌 클래스(closed class)는 새 소스 파일에 선언을 두는 것으로는 메서드를 더할 수 없는 클래스다.

Clojure 에서는 클래스가 언어 기능이 아니라 관례라 이 제약이 없다. 그래서 json-shape-visitor 의 defmulti 가 to-json 을 도형 모델에 바로 더한다.

90도 문제 — 인터페이스를 떼어 경계를 지킨다

여기서 읽을 것 — 삼각형 하나를 더할 때 json-shape-visitor 가 바뀌는 까닭과, 파일을 둘로 떼면 의존 화살표가 어떻게 돌아서는지

하위 타입마다 메서드를 가진 모듈은 타입 모델이 바뀔 때마다 함께 바뀐다 — 삼각형을 더하면 json-shape-visitor 에 defmethod 를 더해야 하니 OCP 를 어긴다. 더 큰 문제는 의존 규칙(Dependency Rule)이다 — 의존 규칙은 아키텍처 경계를 넘는 소스 의존이 모두 경계의 높은 수준 쪽을 향해야 한다는 규칙이다.

이 소절이 세운 것 경계를 넘는 OCP 는 타입 안전을 대가로 치른다

이 대가는 언어를 가리지 않는다 — Java 에도 Clojure 에도 피할 길이 없다. 다음 소절은 저자가 16장과 책을 맺으며 무엇이 그대로이고 무엇이 달라졌다고 보는지 본다.

맺음말 — Clojure 는 객체지향이기도 하다

6다시 보는 구조 — 남는 것과 빠지는 것

이 절의 목표 두 장의 결론 · 판정 · 답이 난 물음과 미룬 물음을 한 자리에서 확인하고 다음 읽을 곳을 안다
왜 여기 있나 본문에서 하나씩 본 결론을 모아 처음 물음에 답하고, 다음에 읽을 곳을 정한다
  • 전화 상태 기계 — 에이전트가 갱신을 차례로 처리해 동시 갱신 문제는 없지만, 엇갈린 메시지로 네 기계가 어긋나는 경쟁 조건은 남는다.
  • Abstract Server — 함수 인자 · 함수 맵 · 멀티메서드 어느 것으로도 부르는 쪽이 대상을 모르게 할 수 있다.
  • Adapter — 네임스페이스를 나누면 require 방향이 UML 의 의존과 같고, 클래스 형태만은 Clojure 에서 만들 수 없다.
  • Command — 명령 하나는 함수로 충분하지만, 되돌리기가 붙으면 실행 기록을 담은 새 명령과 멀티메서드가 돌아온다.
  • Composite · Decorator — 여럿임을 감추는 묶음과 기록을 덧붙이는 감싸기가 GOF 그대로 쓰이고, 도형 판은 새 값을 돌려준다.
  • Visitor — 이중 디스패치는 닫힌 클래스 탓이라 빠지고, 90도 회전이 남기는 의존 문제는 인터페이스를 떼어 푼다.
  • Abstract Factory — 생성 의존을 경계 아래로 내리고, 90도 회전을 토큰으로 없애면 타입 안전을 내준다.

묶어 말하면, 함수형으로 바꿔 사라진 것은 같은 값을 함께 고치는 충돌과 닫힌 클래스 탓 세부이고, 메시지를 주고받는 기계의 어긋남과 패턴의 구조는 남았다. 아래 표는 16장이 견준 두 형태를 저자의 말로 판정한다.

답이 난 것
  • 함수형으로 짜면 경쟁 조건이 사라지나 아니다 — 갱신이 없어도 메시지를 주고받는 상태 기계는 어긋난다(15장).
  • 함수형 언어에는 디자인 패턴이 필요 없나 아니다 — 불변을 지키는 한 GOF 패턴은 대체로 그대로 쓰인다(16장).
  • Visitor 의 이중 디스패치는 패턴의 본질인가 아니다 — 닫힌 클래스 언어에서만 필요한 덧붙임이다.
  • 경계를 넘어 OCP 를 지키면서 타입 안전도 지킬 수 있나 없다 — 어느 언어든 경계 어딘가에서 타입 안전을 내주고 실행 중 예외에 기댄다.
  • Singleton 은 어떻게 하나 저자의 답은 한 줄이다 — 하나만 만들면 된다.
답이 나지 않은 것과 이어지는 곳
  • 함께 도는 상태 기계의 경쟁 조건을 어떻게 막나 저자가 다룰 곳을 밝히지 않았다
  • Abstract Server 의 프로토콜 · 레코드 형태 저자가 연습으로 남겼다 — 다룰 곳은 밝히지 않았다
  • 16장이 다루지 않은 나머지 GOF 패턴 저자가 연습으로 남겼다 — 다룰 곳은 밝히지 않았다
