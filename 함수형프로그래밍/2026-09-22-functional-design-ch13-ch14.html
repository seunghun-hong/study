[학습] 함수형의 테스트 규율과 화면 부작용

Java 개발자가 『Functional Design』 13 · 14장을 읽고, 함수형 프로그램에서 테스트 규율은 그대로이고 속성 기반 테스트가 진단 도구로 더해지는 까닭과, 거북 그래픽이 화면을 바꾸는 부작용을 갱신 루프의 꼬리 한 자리에 모으는 구조를 코드로 따라 그리게 한다.

읽는 사람 — Java 로 테스트를 짜 본 개발자 — TDD · mock · 객체지향은 알고, Clojure 와 Quil 은 처음이다.

1실무 부의 두 장 — 테스트와 화면을 묻는다

이 절의 목표 두 장이 함께 답하는 물음과, 두 장이 다루는 프로그램의 부품 · 읽는 차례를 안다
왜 여기 있나 이 물음과 차례를 쥐지 않으면 13장의 테스트 코드와 14장의 거북 코드가 서로 무관한 두 이야기로 읽힌다.

이 문서가 붙드는 물음은 하나다 — 테스트를 먼저 쓰는 규율과 값을 돌려주지 않는 화면 그리기를 함수형 프로그램은 각각 어떻게 다루나? 13장은 테스트로, 14장은 GUI 로 이 물음의 한쪽씩에 답한다.

두 장은 책의 넷째 부인 실무(Functional Pragmatics) 부에 든다. 이 부는 테스트 · GUI · 동시성을 13 · 14 · 15장에서 다룬다.

두 장을 이 물음 하나로 묶은 것은 이 문서의 풀이다. 13장은 앞 장들이 따르던 시험이 먼저라는 규율을, 14장은 함수는 값을 돌려준다는 전제를 실무 앞에 세운다.

앞 장과는 저자가 직접 잇는다. 13장의 mock 절은 12장의 LSP(하위 타입이 기반 타입 자리를 대신한다)를 다시 부르고, 속성 기반 테스트의 두 번째 예제는 12장의 비디오 가게 명세서 코드를 다시 쓴다.

Clojure 문법은 따로 가르치지 않는다. 코드마다 논지에 필요한 줄만 곁주석으로 풀고, 괄호의 첫 자리가 부를 함수이고 나머지가 인자라는 것만 먼저 쥐면 읽힌다.

먼저 두 장이 다루는 프로그램을 부품과 이음으로 본다. 왼쪽은 13장이 테스트하는 소인수 함수와 그 둘레, 오른쪽은 14장의 거북 그래픽이다 — 오른쪽에서 값 대신 바깥을 바꾸는 선이 몇 개인지 세어 둔다.

3테스트 — 규율은 언어를 가리지 않는다

이 절의 목표 함수형에서도 TDD 규율은 그대로이고, 속성 기반 테스트가 그 규율 안에 진단 도구로 더해진다는 것을 코드로 안다
왜 여기 있나 첫 절 물음의 앞쪽, 테스트를 먼저 쓰는 규율에 답하는 장이다. 저자는 함수형 개발자들 사이의 통설에 차례로 답하며 결론에 닿는다.

13장은 코드를 키우는 장이 아니라 통설에 답하는 장이다. 아래 표가 저자가 짚는 통설 셋과 저자의 답이다.

규율 — 테스트는 REPL 실험보다 오래 남는다

여기서 읽을 것 — 저자가 규율을 언어와 떼어 놓는 근거와 첫째 통설(REPL)에 대한 답을 읽는다.

저자는 이 책 내내 TDD 로 테스트를 코드보다 몇 초 앞서 썼고, 20년 넘게 Java · C# · C++ · Ruby · Clojure 같은 여러 언어에서 그렇게 해 왔다. 그 세월에 배운 것은 언어가 규율과 상관없다는 것이다.

그래서 Clojure 가 함수형이라는 사실은 테스트 전략도 TDD 도 바꾸지 않는다 — 저자는 Java 프로그램처럼 Clojure 프로그램도 테스트부터 쓴다. 저자의 말로는 패러다임은 상관없고 규율은 보편적이다.

첫째 통설은 REPL(식을 넣으면 곧바로 값을 보여 주는 대화형 실행 창 — Java 의 JShell 자리)에서 다 시험하니 TDD 가 필요 없다는 것이다. 저자도 REPL 에서 많이 실험하지만 배운 것은 대부분 테스트로 옮긴다 — 테스트는 다이아몬드처럼 영원하지만 REPL 실험은 다음 날 아침이면 없다.

정의 speclj — 이 장의 테스트 틀

speclj 는 Micah Martin 등이 만든 Clojure 테스트 틀로, Ruby 의 RSpec 과 아주 비슷하다. describe 는 JUnit 의 테스트 클래스, it 은 테스트 메서드 자리이고, should= 는 assertEquals 처럼 기대값과 실제값을 견준다.

이 소절이 세운 것 규율은 그대로다 — 테스트는 여전히 코드보다 먼저 온다

이 장의 나머지는 규율을 바꾸는 이야기가 아니라 그 규율 안에서 함수형 코드에 쓰는 도구 이야기다. 다음 소절은 객체지향의 것으로 여겨지는 도구, mock 부터 본다.

mock — 함수를 갈아 끼워 대역을 세운다

여기서 읽을 것 — 둘째 통설이 생긴 까닭과, 저자의 테스트에서 with-redefs 한 줄이 무엇을 보이는지 읽는다.

mock 은 TDD 를 하는 사람이 시스템의 큰 덩어리를 대신하는 객체를 만들어, LSP 로 그 자리에 끼워 넣고 테스트를 떼어 놓는 기법이다. 정식 이름은 test double 이지만 저자는 흔히 쓰는 말 mock 으로 부른다.

통설이 생긴 까닭은 LSP 가 객체지향 원칙으로 여겨지고, 객체지향 언어의 mock 이 다형 인터페이스 위에 서기 때문이다. 저자는 LSP 가 함수형에서도 똑같이 서고 다형 인터페이스도 대개 쉽게 만들어지니, mock 은 조금도 막히지 않는다고 답한다.

저자가 든 예는 자기 앱 more-speech 의 테스트다. 저자는 이 테스트가 무엇을 하는지는 신경 쓰지 말고 with-redefs 만 보라고 한다.

with-redefs 는 괄호 안에서만 이름이 가리키는 함수를 바꿔 끼운다. 인터페이스를 따로 세우지 않고 함수 자리 하나를 갈아 끼워 대역을 세웠다는 것이 앞 답의 증거다.

두 stub 은 아무 인자나 받고 아무것도 돌려주지 않는 완벽한 no-op 이지만, 자기에게 일어난 일은 기억한다. 그래서 저자는 각주에서 이것이 엄밀히는 spy 라고 한다 — Mockito 로 치면 mock 보다 spy 에 가깝다.

이 소절이 세운 것 함수형에서도 mock 은 선다 — 함수 자리를 바꿔 끼운다

둘째 통설은 틀렸다는 것이 저자의 답이다. 다음 소절은 셋째 통설이 가리키는 속성 기반 테스트로 넘어가, 저자가 그것을 반론이 아니라 TDD 안의 도구로 보이는 첫 예를 본다.

속성 두 개 — 곱과 소수가 소인수를 정의한다

여기서 읽을 것 — 예시 테스트 열둘이 무엇을 확신하지 못하는지, 그 빈자리를 속성 두 개가 어떻게 메우는지 읽는다.

저자는 QuickCheck(속성 기반 테스트의 원조 도구)가 흔히 TDD 의 반론으로 나온다고 말하고, 그 다툼에 편들지 않겠다고 한다. 대신 TDD 안에서 속성 기반 테스트가 얼마나 강력한지 보이겠다고 한다.

저자의 정의로는 속성 기반 테스트는 입력을 무작위로 만들고 결함을 매우 강력하게 좁혀 내는 검증 · 진단 기법이다. 먼저 TDD 로 짠 소인수 함수 하나를 본다.

저자가 붙든 것은 출력의 속성이다. 왼쪽은 인수를 모두 곱하면 입력이 되는가를, 오른쪽은 인수가 모두 소수인가를 1 부터 10억 사이의 무작위 정수 천 개로 검사한다.

둘째 속성은 소수 판정 함수 is-prime? 를 쓴다. 저자는 이것을 끔찍하게 비효율적인 전통 알고리즘이라 부르지만, 속성 검사에는 그것으로 족하다.

2 (if (= 2 n)2 는 바로 참

6 true
7 (if (zero? (rem n (first candidates)))
8 false
9 (recur (rest candidates)))))))다음 후보로

축소 — 실패한 주문을 가장 작게 줄인다

여기서 읽을 것 — 12장의 비디오 가게 주문으로 속성 검사를 걸고, 실패 출력의 두 칸이 버그를 어떻게 가리키는지 읽는다.

이 소절이 세운 것 실패한 입력을 줄이면 원인만 남는다 — 이것이 진단이다

속성 기반 테스트는 고른 예시가 놓친 입력을 찾을 뿐 아니라, 찾은 실패를 원인만 남도록 줄여 준다. 다음 소절은 예시 테스트와 이 도구를 한 표에 놓고 저자가 장을 닫는 말을 본다.

예시와 속성 — 진단 도구가 규율 안에 더해진다

여기서 읽을 것 — 두 테스트를 넣는 입력 · 확인하는 것 · 실패했을 때 · TDD 와의 관계로 견주고, 저자가 함수형과 잇는 짐작을 읽는다.

소개가 끝났으니 Java 개발자에게 익은 예시 테스트와 새 도구를 한 표에 놓는다. 표의 기준은 둘이 갈리는 곳 — 무엇을 넣고, 무엇을 보고, 실패하면 무엇을 주는지 — 이다.

저자는 장을 Functional 머리글 아래서 닫는다 — quick-check 같은 도구가 왜 객체지향 언어에서 덜 쓰이나. 저자의 짐작은 아마 순수 함수에서 가장 잘 돌기 때문이고, 가변 시스템에서도 생성기와 속성을 세울 수는 있겠지만 훨씬 복잡할 것이라고 본다.

그래서 13장의 결론은 둘이다 — 규율이 언어를 가리지 않는다는 저자의 단정과, 함수형이 그 규율에 진단 도구 하나를 더한다는 것이다. 그 도구가 순수 함수에서 가장 잘 돈다는 까닭은 저자의 짐작으로 남는다.

4GUI — 화면 변경을 루프의 꼬리에 모은다

이 절의 목표 거북 그래픽이 화면을 바꾸는 부작용을 갱신 루프의 꼬리에 모아 GUI 가 될 수 있는 만큼 함수형인 구조를 안다
왜 여기 있나 첫 절 물음의 뒤쪽, 값을 돌려주지 않는 화면 그리기에 답하는 장이다. 저자는 두 GUI 틀 가운데 함수형인 Quil 로 짠 프로그램 하나를 끝까지 걷는다.

저자는 함수형 프로그램에서 두 GUI 틀을 써 봤다. Processing 을 바탕으로 한 Quil 은 함수형이라 쓰기 즐겁고 쉽지만, Swing 을 바탕으로 한 SeeSaw 는 가변 상태에 기대 쓰기 몹시 괴롭다고 한다.

저자는 SeeSaw 코드를 싣지 않고 Quil 로 짠 거북 그래픽(turtle-graphics) 한 프로그램을 따라 걷는다. 그래서 이 장은 코드를 키우지 않고, 다 된 코드를 루프 → 값 → 명령 차례로 읽는다.

그 프로그램이 그리는 것이 아래 별이다. 거북 스크립트 몇 줄이 꼭짓점 다섯을 잇는다.

거북 그래픽 — 스크립트는 값을 돌려주지 않는다

여기서 읽을 것 — 거북 그래픽의 뜻과 저자가 원한 API, 그리고 이 장이 풀 수수께끼를 읽는다.

거북 그래픽은 1960년대 말 Logo 언어를 위해 만든 명령 묶음으로, 종이 위에서 펜을 올리고 내리는 로봇 거북에게 앞 · 뒤로 가고 좌우로 돌라고 시킨다. 정사각형이면 펜을 내리고 앞으로 10 을 네 번 가며 그 사이 오른쪽으로 90 도씩 돈다.

저자가 원한 것은 명령을 치는 콘솔이 아니라, Clojure 로 그림 그리는 함수를 쓸 수 있는 API 였다. 그래서 거북 스크립트는 보통 Clojure 함수이고, forward · right 같은 이름이 두 벌 있다 — 스크립트가 부르는 쪽은 명령을 건네기만 하고 거북 모듈 쪽이 거북 값을 바꾼다.

거북 스크립트 — 별 그리기

2 (pen-down)
3 (speed 1000)
4 (dotimes [_ n]n 번 되풀이 — Java 의 for 문 자리

명령마다 거북과 화면이 바뀔 뿐, 돌려받는 값이 없다.

turtle-script 가 이 틀의 입구다 — 사용자는 그리기 명령을 이 함수에 넣는다. 그런데 저자가 짚듯 polygon 은 함수형으로 보이지 않는다: 입력에서 값을 내지 않고 화면에 그리며, 명령마다 거북의 상태를 바꾼다.

부작용은 함수가 입력에서 값을 돌려주는 대신 화면이나 거북처럼 바깥의 상태를 바꾸는 일이다. 그러니 거북 스크립트는 함수형이 아니다.

그런데도 저자는 거북 그래픽 틀은 함수형이라 한다 — 더 정확히는 GUI 프로그램이 될 수 있는 만큼 함수형이다. GUI 의 요점이 화면의 상태를 바꾸는 것이니 부작용을 없앨 수는 없고, 남는 물음은 그 부작용을 어디에 두느냐다.

이 소절이 세운 것 수수께끼 — 스크립트는 부작용투성이인데 틀은 함수형이다

이 수수께끼는 두 쪽에서 풀린다. 틀 쪽은 다음 소절의 갱신 루프가, 스크립트 쪽은 채널을 다루는 소절이 푼다.

갱신 루프 — 화면 변경은 재귀의 꼬리에 있다

여기서 읽을 것 — Quil 이 언제 어느 함수를 부르는지, 그 되풀이를 꼬리 재귀로 보면 왜 화면 변경이 해가 없는지 읽는다.

틀은 -main 에서 Quil 을 설정해 띄운다. 볼 것은 :setup · :update · :draw 세 칸이고, 저마다 함수 하나를 가리킨다.

꼬리 재귀는 함수가 마지막 자리(꼬리)에서 자기 자신을 다시 부르는 재귀다. 1장의 꼬리 호출 최적화(TCO)는 그 호출을 스택을 쌓지 않는 되풀이로 바꾸는 것이고, 위 코드의 recur 가 그 꼬리 호출이다.

저자의 논증은 세 걸음이고, 이 장의 판정이 여기에 선다.

  • 이 루프를 꼬리 재귀로 보면 화면의 내용은 꼬리 재귀의 값이다.
  • 화면을 바꾸더라도 재귀의 꼬리에서 바꾸니 그 변경은 해가 없다(각주 — 대체로).
  • 그래서 순수하게 함수형은 아니어도, TCO 시스템이 될 수 있는 만큼은 함수형이다.

판정이 이 한 문단에 선다는 것이 싱거울 수 있다. 저자는 대체로라는 단서를 각주로 달았을 뿐 더 따지지 않고, 곧바로 setup 으로 넘어간다.

(defn update-position
  [{:keys [position velocity heading distance] :as turtle}]
  (let [step (min (q/abs velocity) distance)
        distance (- distance step)
        step (if (neg? velocity) (- step) step)
        radians (q/radians heading)
        [x y] position
        vx (* step (Math/cos radians))
        vy (* step (Math/sin radians))
        position [(+ x vx) (+ y vy)]]
    (assoc turtle :position position
                  :distance distance
                  :velocity (if (zero? distance) 0.0 velocity))))

(defn update-heading [{:keys [heading omega angle] :as turtle}]
  (let [angle-step (min (q/abs omega) angle)
        angle (- angle angle-step)
        angle-step (if (neg? omega) (- angle-step) angle-step)
        heading (mod (+ heading angle-step) 360)]
    (assoc turtle :heading heading
                  :angle angle
                  :omega (if (zero? angle) 0.0 omega))))

채널 — 스크립트의 부작용은 명령 넣기 하나다

여기서 읽을 것 — 스크립트 스레드와 갱신 루프가 명령을 주고받는 길과, 프로그램 전체에서 부작용이 어디에 있는지 읽는다.

채널이 있는 까닭은 스레드가 둘이기 때문이다. setup 의 async/go 가 거북 스크립트를 가벼운 새 스레드에서 돌리고 갱신 루프는 Quil 쪽에서 도니, 둘 사이에 명령을 건네는 대기열이 채널이다.
