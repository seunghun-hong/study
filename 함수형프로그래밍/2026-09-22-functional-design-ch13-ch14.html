규율 · REPL · mock — 바뀌는 것이 없다

여기서 읽을 것 — 함수형 쪽의 통설 둘에 저자가 어떻게 답하는지. mock 시험은 with-redefs 한 줄만 보면 된다.

이 책의 시험은 대부분 speclj 로 썼다. Ruby 의 RSpec 과 매우 비슷한 틀이다. 저자는 20년 넘게 Java · C# · C · C++ · Ruby · Python · Lua · Clojure 에서 TDD 를 했고, 배운 것은 하나다 — 언어는 규율과 무관하다. Clojure 가 함수형이라는 사실은 시험 전략도 TDD 규율도 바꾸지 않는다.

주의REPL 이 있으니 TDD 가 필요 없다는 말에 대해

저자도 REPL 에서 실험을 많이 한다. 다만 대부분의 경우 알게 된 것을 시험으로 적어 둔다. 시험은 다이아몬드처럼 영원하고, REPL 의 실험은 다음 날 아침에 없다.

mock 은 시험을 시스템의 큰 덩어리로부터 떼어 놓는 기법이다. 그 덩어리를 대신하는 객체를 만들어 LSP 로 바꿔 끼운다. LSP 가 객체지향 원칙으로 여겨지고 객체지향의 mock 이 다형 인터페이스 위에 서다 보니, 함수형은 mock 을 못 쓴다는 통설이 생겼다. 그런데 12장에서 봤듯 LSP 는 함수형에서도 서고 다형 인터페이스는 만들기 쉽다. 저자의 more-speech 에서 가져온 시험이다.

속성 기반 검사 — 예시 뒤에 정의를 건다

여기서 읽을 것 — 예시 시험과 속성 시험이 각각 무엇을 보장하는지. 같은 함수에 둘을 차례로 거니 차이가 보인다.

함수형 프로그래머와 어울리다 보면 QuickCheck 와 속성 기반 검사 이야기를 듣게 되고, 대개 TDD 에 대한 반론으로 나온다. 저자는 그 논쟁을 편들지도 반박하지도 않고, 대신 TDD 규율 안에서 이 도구가 얼마나 힘이 센지 보인다. 속성 기반 검사는 입력을 무작위로 만들고 결함을 강력하게 고립시키는 검증이자 진단 기법이다.

4GUI — 화면을 고치는 프로그램은 어디까지 함수형인가

이 절의 목표화면을 고치는 것이 목적인 프로그램을 함수형으로 쓰면 어떤 모양이 되고, 부작용이 어디로 몰리는지 본다.
왜 여기 있나13장까지의 코드는 값을 받아 값을 돌려줬다. GUI 는 그럴 수 없다 — 프로그램의 목적 자체가 화면의 상태를 바꾸는 것이다. 그래서 함수형을 배우는 사람이 가장 먼저 부딪히는 자리이고, 저자는 자기가 쓴 작은 프로그램 하나로 답한다.
이 장에서 네 마디가 무엇인가
  1. 1틀이 둘, 차이가 크다Quil 은 함수형이라 쓰기 쉽고, SeeSaw 는 가변 상태를 계속 갱신해야 해서 고역이다
  2. 2루프 하나setup · update · draw 셋이 꼬리 재귀 루프 하나다. 화면 갱신은 꼬리에 있다루프
  3. 3거북이는 값필드 열여섯의 맵. 생성자와 갱신 함수가 명세를 사후 조건으로 확인한다거북이
  4. 4명령은 채널로스크립트는 다른 스레드에서 채널에 넣고, 루프는 멈춰 있을 때만 읽는다명령
둘째 마디가 이 장의 심장이다. GUI 가 함수형이 될 수 있는 만큼 함수형인 이유가 그 루프 하나에 있다.

저자는 함수형 프로그램에서 GUI 틀 둘을 써 봤다. Java 의 Processing 위에 선 Quil 과, 옛 Swing 위에 선 SeeSaw 다. Quil 은 함수형이라 함수형 프로그램에서 쓰기 쉽고 즐겁다. SeeSaw 는 전혀 함수형이 아니어서 가변 상태를 계속 갱신해야 하고, 함수형 프로그램에서 쓰기가 고역이다. 차이가 놀랍다고 저자는 적는다. spacewar 도 Quil 로 썼지만 그 소스를 훑는 것은 책의 범위를 넘고, 딱 맞는 크기의 프로그램이 하나 있다 — 거북이 그래픽.

거북이 그래픽은 1960년대 말 Logo 언어를 위해 만들어진 명령 몇 개다. 종이 위의 로봇 거북이에게 펜을 내리고, 앞으로 얼마 가고, 오른쪽으로 몇 도 돌라고 시킨다. 저자가 원한 것은 명령을 치는 콘솔이 아니라 Clojure 로 그림 그리는 함수를 쓸 수 있는 API 였다.

루프 — 화면 갱신은 꼬리에 있다

여기서 읽을 것 — Quil 이 부르는 함수 셋이 실은 루프 하나라는 것, 그리고 부작용이 그 루프의 어디에 있는지.

Quil 의 함수 셋은 setup 으로 첫 값을 만들고 draw 로 그린 뒤 update 로 새 값을 만들어 되돌아가는 루프다. 화면을 고치는 자리는 그 꼬리 하나뿐이다. 다음 소절은 그 루프를 지나는 값 — 거북이 — 이다.

거북이 — 값 하나와 그것을 갱신하는 함수

여기서 읽을 것 — 거북이가 무엇으로 이루어졌는지는 접힌 명세를 펴 보면 되고, 볼 것은 생성자와 갱신 함수의 사후 조건과, 한 프레임에 거북이가 얼마나 움직이는지다.

turtle.clj · 한 프레임의 갱신
⋯ update-position · update-heading — 삼각함수로 한 걸음
(defn update-position
  [{:keys [position velocity heading distance] :as turtle}]
  (let [step (min (q/abs velocity) distance)
        distance (- distance step)
        step (if (neg? velocity) (- step) step)
        radians (q/radians heading)
        [x y] position
        vx (* step (Math/cos radians))
        vy (* step (Math/sin radians))
        position [(+ x vx) (+ y vy)]]
    (assoc turtle :position position
                  :distance distance
                  :velocity (if (zero? distance) 0.0 velocity))))

(defn update-heading [{:keys [heading omega angle] :as turtle}]
  (let [angle-step (min (q/abs omega) angle)
        angle (- angle angle-step)
        angle-step (if (neg? omega) (- angle-step) angle-step)
        heading (mod (+ heading angle-step) 360)]
    (assoc turtle :heading heading
                  :angle angle
                  :omega (if (zero? angle) 0.0 omega))))
(defn make-line [{:keys [pen-start position weight]}]
  {:line-start pen-start
   :line-end position
   :line-weight weight})

(defn update-turtle [turtle]
  {:post [(s/assert ::turtle %)]}
  (if (= :idle (:state turtle))
    turtle
    (let [{:keys [distance
                  state
                  angle
                  lines
                  position
                  pen
                  pen-start] :as turtle}
          (-> turtle
              (update-position)
              (update-heading))
          done? (and (zero? distance)
                     (zero? angle))
          state (if done? :idle state)
          lines (if (and done? (= pen :down))
                  (conj lines (make-line turtle))
                  lines)
          pen-start (if (and done? (= pen :down))
                      position
                      pen-start)]
      (assoc turtle
             :state state
             :lines lines
             :pen-start pen-start))))

update-turtle 도 :post 로 명세를 확인한다. 큰 구조를 갱신하면서 작은 칸 하나를 망치지 않았는지 아는 것은 좋은 일이라고 저자는 적는다. 거북이가 :idle 이면, 즉 움직이지도 돌지도 않으면 아무것도 바꾸지 않는다. 아니면 위치와 방향을 한 걸음 갱신하고 안을 푼다. 남은 거리와 남은 각이 0 이면 끝난 것이고 :idle 로 돌아간다. 끝났는데 펜이 내려져 있었으면 그리던 선을 목록에 더하고 다음 선의 시작점을 지금 위치로 옮긴다. 위치와 방향의 갱신은 삼각함수 계산이고, 둘 다 속력으로 한 걸음의 크기를 정한다.

그래서왜 한 번에 그리지 않나

forward 400 은 한 프레임에 끝나지 않는다. 프레임마다 속력만큼 나아간 새 거북이가 나오고, 남은 거리가 0 이 되는 프레임에서야 선 하나가 목록에 확정된다. 그래서 거북이가 화면에서 움직여 보인다. 값을 고치지 않고 새 값을 돌려주는 것과 애니메이션이 같은 구조에서 나온다.

이 소절이 세운 것거북이는 명세로 지켜지는 값이고, 한 프레임에 한 걸음씩 새 값이 된다

생성자와 갱신 함수가 사후 조건으로 명세를 확인하고, 갱신은 받은 값을 고치지 않고 한 걸음 나아간 새 값을 돌려준다. 다음 소절은 그 거북이에게 명령이 어떻게 닿는지다.

명령 — 채널로 건너오고, 멈춰 있을 때만 읽는다

여기서 읽을 것 — 사용자 스크립트와 갱신 루프가 다른 스레드라는 것, 둘 사이에 채널 하나가 있다는 것, 그리고 루프가 채널을 언제 읽는지.

이 소절이 세운 것스크립트와 루프는 다른 스레드이고, 채널 하나가 둘을 잇는다

사용자 코드는 채널에 벡터를 넣고, 루프는 거북이가 멈춰 있을 때만 그 벡터를 꺼내 값을 갱신하는 함수에 넘긴다. 명령 처리와 애니메이션이 갈려 있고, 부작용은 채널 넣기와 화면 그리기 둘로 밀려나 있다. 다음 소절은 이것을 판정으로 묶는다.

불변식이 장의 판정

GUI 프로그램은 순수할 수 없지만, 될 수 있는 만큼 함수형일 수 있다. 화면을 고치는 부작용을 꼬리 재귀의 꼬리 한 자리에 두고, 나머지는 값을 받아 새 값을 돌려주는 함수로 쓴다. 거북이 스크립트 자체는 함수형이 아니어도 틀은 함수형이다 — "대체로 해가 없다" 는 단서와 함께.

이 소절이 세운 것부작용을 한 자리에 몰면 GUI 도 나머지는 값과 함수다

Quil 이 함수형인 이유는 화면 갱신이 루프의 꼬리에 있어서다. 거북이는 명세로 지켜지는 값이고, 명령은 채널로 건너와 값을 갱신하는 함수에 닿는다. 아래는 이 결론을 이 장이 받았던 물음으로 되돌린다.

이 절이 세운 것화면을 고치는 프로그램도 부작용을 꼬리에 몰면 나머지는 함수형이다

이 절이 있는 이유로 돌아온다 — 목적이 화면을 바꾸는 것인 프로그램을 함수형으로 쓰면 어떤 모양이 되는가였다. 답은 루프 하나다. 첫 값을 만들고, 그리고, 새 값을 만들어 되돌아간다. 그리기가 꼬리에 있어 그 부작용은 해가 없고, 루프를 지나는 거북이는 명세가 지키는 값이며, 명령은 다른 스레드에서 채널로 건너온다. 값을 돌려주지 않는 함수는 채널에 넣는 것과 화면에 그리는 것 둘뿐이다.

13장과 합치면 이렇다 — 시험 규율은 그대로이고 순수 함수 덕에 진단 도구가 하나 늘며, 순수할 수 없는 GUI 에서도 부작용을 한 자리에 몰면 나머지는 값과 함수다.

13장이 남긴 것

여기서 읽을 것 — 13장에서 세운 것을 네 줄로. 마지막 줄이 저자의 추측이다.

  • TDD 규율은 언어와 무관하다. 아홉 언어에서 같았다. REPL 실험은 시험으로 적어 둔다 — 시험은 영원하고 실험은 다음 날 없다.
  • mock 은 함수를 갈아 끼우는 것으로 선다. with-redefs 와 이름 붙은 스텁. 함수형이 mock 을 못 쓴다는 통설은 근거가 없다.
  • 속성 기반 검사는 TDD 안의 진단 도구다. 생성기가 명세의 나무를 거꾸로 타고, 속성이 정의를 확인하고, 실패는 가장 작게 축소된다.
  • 순수 함수에서 가장 잘 돈다 — 객체지향에 덜 퍼진 이유일 것이라고 저자는 추측한다.
이 소절이 세운 것13장은 잃는 것이 없음과 더하는 것 하나를 남겼다

규율과 mock 은 그대로이고, 속성 기반 검사가 순수 함수 위에서 더해진다. 다음은 14장이 남긴 것이다.

14장이 남긴 것

여기서 읽을 것 — 14장에서 세운 것을 네 줄로. 셋째 줄이 판정의 근거다.

  • GUI 틀 둘의 차이가 놀랍다. Quil 은 함수형이라 쉽고, SeeSaw 는 가변 상태를 계속 갱신해야 해서 고역이다.
  • Quil 의 함수 셋은 꼬리 재귀 루프 하나다. setup 으로 첫 값, draw 로 그리고, update 로 새 값. 화면은 아무것도 기억하지 않는다.
  • 화면 갱신이 꼬리에 있어 그 부작용은 해가 없다. 거북이는 명세가 사후 조건으로 지키는 값이고, 한 프레임에 한 걸음씩 새 값이 된다.
  • 명령은 다른 스레드에서 채널로 건너온다. 값을 돌려주지 않는 함수는 채널에 넣는 것과 화면에 그리는 것 둘뿐이다.
불변식두 장을 덮고 남는 것

함수형으로 일한다는 것은 시험을 바꾸는 일이 아니라 순수 함수 덕에 도구를 하나 더 얻는 일이고, 순수할 수 없는 자리에서는 부작용을 한 자리에 몰아 나머지를 값과 함수로 남기는 일이다.

이 소절이 세운 것14장은 부작용을 꼬리 한 자리에 몰았다

GUI 프로그램이 될 수 있는 만큼 함수형이라는 판정은 그 루프 하나에서 나온다. 다음 소절은 두 장이 각 스타일에 실제로 내린 판정을 표로 모은다.

못하는 것속성 기반 검사가 덜 퍼졌다. 가변 시스템에서 생성기와 속성을 세우는 것은 훨씬 복잡할 것이라고 저자는 추측한다. SeeSaw 는 가변 상태를 계속 갱신해야 한다GUI 는 순수할 수 없다. 거북이 스크립트 자체는 함수형이 아니고, 화면 갱신은 부작용이다
저자가 단 단서속성 기반 검사가 객체지향에 덜 퍼진 이유는 추측이다 — 잰 것이 아니다"될 수 있는 만큼 함수형" 이고 꼬리의 변경은 "대체로 해가 없다"
두 장 모두 어느 쪽 손도 들지 않는다. 13장은 도구를, 14장은 자리를 말한다.
그래서답이 난 것과 나지 않은 것

답이 났다 — 시험. 함수형은 시험 규율을 바꾸지 않고, 순수 함수 위에서 속성 기반 검사라는 진단 도구가 더해진다.

답이 났다 — GUI. 화면을 고치는 부작용을 꼬리 재귀의 꼬리에 두면 나머지는 값과 함수로 남는다.

답이 나지 않았다 — 객체와 함수의 거리. 9장이 미룬 물음은 여기서도 건드리지 않는다. 그리고 13장의 마지막 줄 — 속성 기반 검사가 객체지향에 덜 퍼진 이유 — 는 저자 스스로 추측이라고 적었다.

이 소절이 세운 것시험과 GUI 는 답이 났고, 객체와 함수의 거리는 여전히 남았다

두 장은 실무의 사례를 주고 우열은 묻지 않았다. 다음 소절은 남은 물음과 이 장들이 가리킨 뒤 장이다.

여기서 미뤄진 물음과 그것이 이어지는 곳

여기서 읽을 것 — 두 장 본문이 가리킨 뒤 장들. 제목으로 짚은 것이라 내용은 그 장을 읽어야 안다.

  • 15장 동시성 — 14장의 turtle-script 가 async/go 로 다른 스레드에서 돌고 채널로 명령을 건넸다. 스레드 둘과 채널 하나가 어떻게 안전한지가 여기다. 13장의 마지막 문장 "순수 함수에서 가장 잘 돈다" 도 이 장에서 값이 바뀌지 않는 것의 뜻과 만난다.
  • 16장 디자인 패턴 되짚기 — 12장이 미룬 Abstract Factory 와 함께, 14장의 명령 벡터를 함수 호출로 옮기는 handle-command 가 패턴으로 다시 나올 자리다.
  • 17장 Wa-Tor — 14장의 spacewar 처럼 Quil 위의 시뮬레이션. 12장이 미룬 Template Method 와 순환 의존 이야기가 여기서 실제 프로그램과 부딪힌다.
이 소절이 세운 것미뤄진 물음은 15장·16장·17장으로 이어진다

스레드와 채널은 동시성 장으로, 명령 해석은 패턴 장으로, Quil 위의 큰 프로그램은 Wa-Tor 로 간다. 객체와 함수의 거리는 이 셋 어디에도 명시되지 않았다.

이 절이 세운 것여덟 장을 잇는 선 하나와, 미뤄진 물음 하나

이 절이 있는 이유로 돌아온다 — 흩어진 조각을 한 화면에 모으려던 것이었다. 모으면 선 하나가 남는다. 상태 변화가 커질수록 갈리던 두 스타일이 아키텍처에서 만나고, 같은 원칙으로 나뉘며, 실무에서는 시험 규율을 지킨 채 부작용을 한 자리에 몬다. 답이 난 것은 시험과 GUI 이고, 답이 나지 않은 것은 객체와 함수의 거리다. 그 물음은 뒤 장으로 간다.
