[학습] 함수형 프로그램의 테스트 규율과 화면 부작용

Java 는 알고 Clojure 는 처음인 개발자가 『Functional Design』 13 · 14장을 따라, 함수형으로 짜도 테스트 규율은 그대로이고 속성 기반 테스트가 더해진다는 것과, GUI 는 화면 바꾸기를 루프의 꼬리에 둔다는 것을 원문 코드로 이해한다.

읽는 사람 — Java 는 알고 Clojure 는 처음인 개발자 — TDD · JUnit · mock 은 알고, 속성 기반 테스트와 Quil 은 처음이다.

저자는 두 장을 아래 차례로 풀어 간다. 13장은 함수형 쪽의 흔한 말 세 가지에 답하며 테스트를 키우고, 14장은 거북 그래픽 프로그램 하나를 루프 → 거북 값 → 명령의 차례로 읽는다.

313장 테스트 — 같은 규율과 더해지는 도구

이 절의 목표 13장이 테스트 규율과 속성 기반 테스트로 무엇을 보이는지 안다
왜 여기 있나 13장의 주장은 규율이 언어를 가리지 않는다는 것이고, 장은 함수형 쪽의 흔한 말 세 가지에 답하는 꼴로 그 주장을 세운다.

저자는 이 책 내내 TDD 로 테스트를 코드보다 몇 초 앞서 쓰며 코드를 키웠고, 그 테스트 대부분을 speclj(스페클)로 썼다. speclj 는 Ruby 의 RSpec 과 아주 비슷한 Clojure 테스트 틀로, describe 가 JUnit 의 테스트 클래스, it 이 테스트 메서드 자리다.

장의 뼈대는 함수형 쪽에서 흔히 듣는 세 말에 답하는 것이다. 아래 표가 세 말과, 저자가 무엇으로 답하는지다.

규율 — 언어와 REPL 에 상관없이 그대로다

여기서 읽을 것 — 저자가 TDD 규율을 언어와 상관없이 쓰는 까닭과, REPL 로 충분하다는 말에 대한 답.

저자는 20년 넘게 Java · C# · C · C++ · Ruby · Python · Lua · Clojure 같은 여러 언어에서 TDD 를 했다. 그 세월에 얻은 결론은 언어가 규율을 바꾸지 않는다는 것이다.

Clojure 가 함수형 언어라는 사실도 테스트 전략을 바꾸지 않아, 저자는 Java 프로그램처럼 Clojure 프로그램도 테스트 먼저 쓴다.

첫째 통설은 모든 것을 REPL(코드를 한 줄씩 넣어 바로 돌려 보는 대화형 창)에서 시험하니 TDD 가 필요 없다는 말이다. 저자도 REPL 에서 많이 실험하지만 대개 알게 된 것을 테스트로 옮긴다 — 테스트는 다이아몬드처럼 영원하고, REPL 실험은 다음 날 아침 남아 있지 않다.

이 소절이 세운 것 Clojure 에서도 테스트가 먼저다

그래서 이 장의 Clojure 테스트가 Java 개발자에게 낯익어 보이는 것은 저자가 보이려는 모습 그대로다. 다음 소절은 둘째 통설, 함수형 언어는 mock 을 쓸 수 없다는 말로 넘어간다.

mock — 함수를 갈아 끼워 만든다

여기서 읽을 것 — 함수형 언어는 mock 을 못 쓴다는 말이 어디서 나왔고, 저자가 어떤 테스트로 반박하는지.

mock 은 테스트를 시스템의 큰 부분에서 떼어 내려고, 그 부분을 대신하는 객체를 LSP(하위 타입이 기반 타입 자리를 대신할 수 있다는 원칙)로 끼워 넣는 기법이다. LSP 가 객체지향 원칙으로 여겨지고 객체지향 언어의 mock 이 다형 인터페이스에 기대다 보니, 함수형 언어는 mock 을 쓸 수 없다는 도시 전설이 생겼다.

저자는 LSP 가 함수형 언어에서도 객체지향 언어만큼 잘 통하고 다형 인터페이스도 대개 만들기 쉬워, mock 을 쓰는 데 걸림이 없다고 답한다. 증거는 저자의 more-speech 앱에 있는 아래 테스트이고, 저자는 이 테스트가 하는 일은 신경 쓰지 말고 with-redefs 만 보라고 한다.

with-redefs 는 테스트가 도는 동안만 함수 이름이 가리키는 구현을 바꿔 끼운다. 여기서 바꿔 끼우는 stub 은 인자를 몇 개든 받고 아무것도 돌려주지 않지만, 자기에게 일어난 일은 기억한다.

이 테스트에는 다형 인터페이스가 하나도 없다. with-redefs 한 줄이 함수 자리를 갈아 끼워 대역을 만들고, 그 한 줄이 함수형 언어도 mock 을 쓸 수 있다는 답의 증거다.

이 소절이 세운 것 대역은 인터페이스 없이 함수 자리를 바꿔 만든다

둘째 통설도 규율을 바꾸지 못한다. 셋째 통설인 속성 기반 테스트를 저자는 반론으로 다투지 않고, TDD 안에서 쓰는 모습으로 보인다.

소인수 — 두 속성이 합쳐 정의가 된다

여기서 읽을 것 — 예시 테스트 12개로 키운 소인수 함수에 무작위 입력으로 어떤 두 속성을 확인하는지, 두 속성이 합쳐 무엇이 되는지.

함수형 프로그래머와 어울리면 결국 QuickCheck 와 속성 기반 테스트(property-based testing) 이야기를 듣는데, 이 주제는 흔히 TDD 의 반론으로 나온다. 저자는 그 주장을 편들지도 반박하지도 않고, 속성 기반 테스트가 TDD 규율 안에서 얼마나 강력한지 보이겠다고 한다.

속성 기반 테스트는 입력을 무작위로 만들어 내고 결함을 아주 강력하게 가려내는 전략을 쓰는 검증 · 진단 기법이다. 예제는 정수 하나를 받아 소인수 목록을 돌려주는 factors-of 이고, 저자는 이 함수를 TDD 로 썼다.

소인수 함수 — factors-of
1(defn factors-of [n]
2 (loop [factors [] n n divisor 2]빈 목록 · n · 나눌 수 2 로 반복을 연다
3 (if (> n 1)
4 (cond
5 (> divisor (Math/sqrt n))나눌 수가 √n 을 넘으면 남은 n 이 소수다
6 (conj factors n)
7 (= 0 (mod n divisor))
8 (recur (conj factors divisor)인수를 붙이고 몫으로 다시
9 (quot n divisor)
10 divisor)
11 :else
12 (recur factors n (inc divisor)))
13 factors)))

1(defn is-prime? [n]

3 true
4 (loop [candidates (range 2 (inc (Math/sqrt n)))]2 부터 √n 까지 후보

6 true
7 (if (zero? (rem n (first candidates)))나누어떨어지면 소수가 아니다
8 false
9 (recur (rest candidates)))))))

영화 세 편은 그 정책이 처음 작동하는 개수다. 이름 "0" · 빈 제목 · 하루짜리 대여처럼 나머지 칸이 가장 작은 값으로 줄어든 것은 그 칸들이 실패와 상관없다는 뜻이다(이 문서의 풀이).

저자는 이 축소 동작이 속성 기반 테스트를 진단 기법으로 만든다고 한다.

거북 그래픽 — 스크립트는 보통 Clojure 함수다

여기서 읽을 것 — 거북 그래픽이 무엇이고, 저자가 왜 Clojure 함수로 그림을 그리게 했으며, 그 스크립트가 왜 함수형이 아닌지.

갱신 루프 — 화면은 꼬리에서만 바뀐다

여기서 읽을 것 — Quil 이 부르는 세 함수와 그것을 한 루프로 읽는 법, 그리고 저자가 그 루프로 틀을 함수형이라 부르는 까닭.

틀은 Quil 을 설정하고 부르는 것으로 시작한다. q/defsketch 에 넘기는 :setup · :update · :draw 가 저마다 함수 하나를 가리킨다.

명령과 채널 — 스크립트의 부작용은 넣기 하나다

여기서 읽을 것 — 그림 스크립트의 명령이 다른 스레드의 갱신 루프에 어떻게 닿고, 그래서 거북이 왜 한 프레임에 한 걸음씩 움직이는지.

명령을 채널로 주고받는 까닭은 turtle-script 와 갱신 루프가 다른 스레드에서 돌기 때문이다. 채널(channel)은 한 스레드가 넣은 값을 다른 스레드가 꺼내 가는 대기열로, Java 로 치면 두 스레드 사이에 둔 BlockingQueue 와 같다.

스크립트 쪽 명령 함수는 모두 한 줄이다 — 명령 이름과 인자를 벡터로 묶어 채널에 넣는다.

스크립트 쪽 명령 — 채널에 넣기

5(defn left [angle] (async/>!! channel [:left angle]))

11(defn speed [speed] (async/>!! channel [:speed speed]))

갱신 루프 쪽에서는 handle-commands 가 채널을 본다. 거북이 :idle 이면 명령을 받을 준비가 된 것이라 채널을 들여다보고(async/poll! — 비어 있으면 기다리지 않고 nil), 명령이 있으면 처리한 뒤 채널에 명령이 남지 않을 때까지 되풀이한다.
