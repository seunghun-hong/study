[학습] 상태 변화와 객체지향 · 함수형의 코드 분할 기준

7장 볼링과 8장 버스 기사 두 예제를 따라 읽고, 상태 변화가 클수록 객체지향과 함수형이 코드를 나누는 기준이 어떻게 갈리는지 코드에서 가려낼 수 있게 한다.

읽는 사람 — Java 는 알고 Clojure 는 처음인 개발자

1두 장의 물음 — 상태가 커지면 나누는 기준이 갈린다

이 절의 목표 두 장이 같은 물음의 두 조각이고, 두 예제가 어떤 부품으로 되어 있는지 안다
왜 여기 있나 뒤에서 코드 조각을 읽을 때 그것이 이 물음의 어느 쪽 답인지 붙잡게 하려고 먼저 둔다.

같은 문제를 Java(객체지향)와 Clojure(함수형)로 풀면, 프로그램을 이끄는 상태 변화가 커질수록 코드를 나누는 기준은 어떻게 달라지나? 코드를 나누는 기준, 곧 코드의 경계를 어디에 긋느냐(partitioning)는 8장 끝에서 저자가 세 예제를 돌아보며 내린 결론의 핵심이다.

7장 볼링 점수 계산(Bowling Game)과 8장 버스 기사 소문(Gossiping Bus Drivers)이 이 물음에 한 조각씩 답한다. Clojure 문법은 따로 가르치지 않고, 코드 줄 곁에서 논지에 필요한 만큼만 푼다.

책 안의 자리 — 같은 문제를 두 스타일로 푸는 부

여기서 읽을 것 — 이 두 장이 책에서 왜 자꾸 두 언어를 견주는지, 그리고 두 장이 어떤 축 위에 놓이는지 읽는다.

두 장은 책의 2부 비교 분석(Comparative Analysis)에 든다 — 6장부터 10장까지 같은 문제를 Java 와 Clojure 로 풀어 견주는 부다. 8장 첫머리에서 저자는 지금까지의 비교로는 함수형을 고를 강한 까닭을 찾지 못했다며 조금 더 흥미로운 문제로 넘어간다.

6장 소인수 분해(Prime Factors) 앞 장의 예제 — 상태 변화 없는 단순한 계산 두 스타일에 거의 영향받지 않는다
7장 볼링(Bowling Game) 배열 인덱스 정도의 작은 상태 변화 두 스타일에 조금 영향받는다
8장 버스 기사(Gossiping Bus Drivers) 순간마다 모든 기사의 자리와 소문이 바뀐다 두 스타일이 크게 갈린다
칸의 결과는 8장 결론에서 저자가 세 예제를 두고 내린 판단이다 — 이 문서는 둘째 · 셋째 칸을 다룬다.
이 소절이 세운 것 두 장은 상태 변화라는 한 축의 두 지점이다

7장에서는 두 풀이의 차이가 작게, 8장에서는 크게 나올 것을 쥐고 읽으면 된다. 다음 소절은 두 예제가 어떤 부품으로 되어 있는지 먼저 보인다.

두 예제의 부품 — 객체에 쌓나 값으로 넘기나

여기서 읽을 것 — 두 예제를 두 언어가 어떤 부품으로 짰는지, 상태가 어느 부품에 머무는지 그림으로 읽는다.

볼링 한 게임은 프레임 열 개다 — 프레임은 핀 열 개를 두고 공을 두 번까지 굴리는 한 차례이고, 핀을 다 쓰러뜨린 프레임은 다음 공을 덤으로 더 센다. 버스 기사 문제는 순환 노선을 도는 기사들이 같은 정류장에서 만나면 서로 아는 소문을 주고받는 모의실험이다.

읽는 차례 — 키우다가 꺾이는 자리를 찾는다

여기서 읽을 것 — 두 장이 어떤 차례로 나아가는지, 그리고 단계마다 무엇을 찾으며 읽을지 본다.

두 장은 같은 방식으로 나아가지 않는다 — 7장은 시험을 하나씩 더하며 두 풀이를 키우고, 8장은 다 만든 두 풀이를 놓고 견준다. 7장의 차이가 작게 느껴져도 그것이 이 사례의 자리다 — 저자는 8장 결론에서 앞 두 예제의 차이를 비교적 작다고 본다.

두 장을 읽는 차례
  1. 1 Java 로 시험을 하나씩 통과시킨다 7장 Java 풀이가 시험 다섯으로 자란다찾을 것 — 굴림을 어디에 모아 두고 언제 점수를 세나 Java 풀이 — 점수 셈이 굴릴 때에서 셀 때로 옮겨 간다
  2. 2 Clojure 로 같은 시험을 따라간다 같은 시험을 함수 몇 개로 통과시킨다찾을 것 — 한 번 더 세는 공을 다루려고 코드가 어디서 꺾이나 Clojure 풀이 — 덤을 프레임 자료에 담는다
  3. 3 7장 두 풀이를 견준다 저자가 관찰 셋과 판정을 낸다찾을 것 — 같은 모양의 분기가 한쪽은 점수를, 다른 쪽은 무엇을 내나 두 풀이 견주기 — 같은 분기가 다른 것을 낸다
  4. 4 8장 두 풀이를 나란히 놓는다 다 만든 두 풀이의 상태 자리를 짝짓는다찾을 것 — 상태를 쥔 자리가 객체의 필드인가 함수가 받는 값인가 Java 풀이 — 상태를 쥔 객체들이 서로를 고친다Clojure 풀이 — 모든 기사를 담은 값이 함수 둘을 지난다나란히 두기 — 같은 뼈대 위에서 상태의 자리가 갈린다
  5. 5 저자가 저울질하고 결론을 낸다 크기 · 객체 · 나누는 선을 따진다찾을 것 — 나누는 기준이 객체를 따르나 함수를 따르나 저자가 센 객체 — 참된 객체는 world 하나일까나누는 선의 저울질 — 지금은 괜찮지만 자라면 드러난다
넷째 단계가 전환점이다 — 상태가 사는 자리의 차이가 8장 결론, 곧 두 스타일이 코드를 나누는 기준의 차이로 곧장 이어진다.
이 소절이 세운 것 7장은 꺾이는 걸음을, 8장은 상태의 자리를 찾으며 읽는다

7장의 전환점은 한 번 더 세는 공이 들어오는 시험이고, 8장의 전환점은 상태를 쥔 자리의 짝짓기다. 다음 절은 이 두 전환점이 이끄는 결론을 본문보다 먼저 준다.

이 절이 세운 것 두 장은 상태 변화 축 위에서 코드를 나누는 기준이 갈리는 정도를 보인다

물음은 상태 변화가 커질 때 나누는 기준이 어떻게 달라지나이고, 두 예제의 부품 그림이 그 답의 모양을 미리 보여 준다. 다음 절에서 두 장이 실제로 내린 답을 먼저 쥔다.

2먼저 쥘 결론 — 7장은 조금 8장은 크게 갈린다

이 절의 목표 두 장이 내린 답과 그 근거, 도착점의 세 낱말을 본문보다 먼저 쥔다
왜 여기 있나 결론을 쥐고 읽으면 7장의 긴 시험 걸음이 어느 결론으로 가는 중인지 알 수 있다.

7장은 어느 풀이가 나은지를 판정하고, 8장은 두 스타일의 차이가 왜 커지는지를 설명한다.

정의 관심사 분리 — 7장에서 가르는 두 일

관심사 분리는 여기서 프레임마다 점수에 영향을 주는 공을 가려내는 일과 점수를 더하는 일을 서로 다른 함수에 두는 것이다. 저자는 두 풀이 모두 이 가려내기를 해야 하지만 Java 는 그 자리에서 한꺼번에(in situ) 하고, Clojure 는 두 관심사를 가른다고 짚는다.

정의 데이터 응집과 행위 응집 — 8장이 도착하는 두 낱말

데이터 응집은 한 데이터와 그 데이터를 바꾸는 일이 한 덩어리에 모이는 것이다 — 기사 객체 하나가 제 자리 · 제 소문과 그것을 바꾸는 일을 함께 쥐는 식이다. 행위 응집은 같은 일을 하는 코드가 한 덩어리에 모이고 데이터는 그 덩어리들을 지나가는 것이다 — 기사를 옮기는 일 한 덩어리, 소문을 주고받는 일 한 덩어리가 모든 기사를 담은 값을 차례로 받는 식이다. 저자가 두 말을 한 문장으로 정의하지 않아, 두 뜻풀이는 8장 결론과 코드에서 이 문서가 푼 것이다.

두 장을 닫는 문장 — 판정 하나와 미룬 물음 하나

여기서 읽을 것 — 두 장을 닫는 저자의 판정과, 두 장을 합치면 남는 한 문장을 본다.

7장은 저자의 판정으로 닫힌다 — Java 쪽이 조금 더 단순하게 끝났지만 결합도 조금 더 높다. Clojure 쪽의 관심사 분리를 보면 둘 가운데 Clojure 쪽이 더 유연하고 쓸모 있을 것이라고 저자는 확신한다.
