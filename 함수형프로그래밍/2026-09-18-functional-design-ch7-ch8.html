[학습] 상태 변화의 크기와 두 스타일의 차이

7장 볼링 게임과 8장 버스 기사 소문을 Java 와 Clojure 로 푼 두 풀이를 따라가, 상태 변화가 프로그램을 더 많이 몰고 갈수록 두 풀이가 어디서 얼마나 갈리는지 안다.

읽는 사람 — Java 는 알고 Clojure 는 처음인 개발자 — 객체지향 · TDD · SRP 는 알고, Clojure 문법과 이 책의 앞 장은 모른다.

1두 장을 꿰는 물음 — 상태 변화가 클수록 더 갈린다

이 절의 목표 두 장이 한 물음에 답한다는 것과 두 문제를 두 언어로 짠 모양을 먼저 잡는다
왜 여기 있나 7장만 보면 두 풀이의 차이가 작아 무엇을 봐야 할지 흐려진다. 8장 결론이 세운 축 위에 두 장을 먼저 놓아야 장마다 찾을 것이 선다.

같은 문제를 Java 와 Clojure 로 풀 때, 상태 변화가 프로그램을 더 많이 몰고 갈수록 두 풀이는 어디서 얼마나 갈리는가? 이 문서는 7장 볼링 게임(Bowling Game)과 8장 버스 기사 소문(Gossiping Bus Drivers)을 이 물음 하나로 읽는다.

상태 변화가 프로그램을 얼마나 몰고 가나
6장 소인수 분해(Prime Factors) 이 문서가 다루지 않는 앞 장 — 상태 변화가 없는 단순 계산 스타일의 영향이 적다
7장 볼링 게임 배열 칸 번호처럼 사소한 곳에서만 상태가 바뀐다 차이가 조금 난다
8장 버스 기사 소문 순간마다 바뀌는 상태가 프로그램을 몰고 간다 차이가 크게 난다
이 축은 저자가 8장을 마친 뒤 세 장을 돌아보며 아마 그렇다는 단서를 달고 세운 결론이고, 두 장을 이 물음 하나로 묶는 것은 이 문서의 풀이다. 7장에서 차이가 작게 보이는 것은 이 축의 가운데 칸이라 그렇다.

먼저 7장의 두 풀이가 점수를 어느 함수에서 계산하는지 본다. 볼링 점수는 프레임(한 사람의 한 차례)마다 세고 어떤 프레임은 뒤 공을 덤으로 더하는데, 그 덤을 가려내는 상자가 어디인지부터 본다.

2두 장이 내린 답 — 7장은 작게 8장은 크게 갈린다

이 절의 목표 두 장의 결론과 근거를 쥐고, 8장이 도착하는 두 응집의 뜻을 예로 안다
왜 여기 있나 결론을 모르고 읽으면 7장의 시험 걸음과 8장의 긴 코드가 사건 나열로 지나간다. 장마다 원문이 닫은 말을 먼저 쥔다.
7장 볼링 게임8장 버스 기사 소문
저자가 닫는 말Java 쪽이 조금 더 단순하게 끝났지만 결합도 조금 더 높다. 둘 가운데 Clojure 쪽이 더 유연하고 쓸모 있을 것이다객체지향 스타일은 데이터 응집을, 함수형 스타일은 행위 응집을 따라 코드를 나누게 된다
근거프레임마다 영향을 주는 공을 가려내는 일을 Java 는 점수를 더하는 반복 안에서, Clojure 는 따로 한다상태가 순간마다 바뀐다. Java 는 그 상태를 고쳐 쓰는 객체 안에, Clojure 는 모든 기사를 담은 한 값에 둔다
함께 남긴 관찰작은 잔재주가 코드를 끌고 가기 쉽다 — Clojure 의 실제 문제Clojure 코드는 거의 나뉘지 않아, 자라면 그 문제가 거세게 드러난다
판정둘 가운데 Clojure 쪽을 고른다 — 열두 줄 남짓의 코드 이야기라는 단서와 함께어느 응집이 나은가는 판정하지 않았다 — 뒤 장으로 미뤘다
칸은 저자가 그 장을 닫는 말과 근거를 코드 이름 없이 옮긴 것이다. 7장의 판정은 저자가 확신한 것이고, 8장의 우열은 미룬 것이라 두 칸의 무게가 다르다.

7장이 발견한 것은 덤 공을 가려내는 일과 점수를 더하는 일을 가르는 관심사 분리다. 관심사 분리는 두 가지 일을 한 자리 안에서 함께 하지 않고 서로 다른 코드 단위로 떼어 두는 것이다.

정의 데이터 응집 — 데이터와 그것을 바꾸는 일이 함께 산다

데이터 응집은 한 덩어리의 데이터와 그 데이터를 바꾸는 일을 한 코드 단위에 모으는 것이다.

예: 기사 한 명을 나타내는 객체가 제 위치 · 제가 아는 소문과 그것을 바꾸는 일을 함께 쥔다.

정의 행위 응집 — 같은 일을 하는 코드가 함께 산다

행위 응집은 같은 일을 하는 코드를 한 단위에 모으고 데이터는 그 단위들 사이를 지나가게 두는 것이다.

예: 기사를 옮기는 일 한 덩어리, 소문을 주고받는 일 한 덩어리가 모든 기사를 담은 값을 차례로 받는다.

두 장을 합쳐 이 문서가 읽은 답은 이렇다 — 상태 변화가 작으면 두 풀이는 한 계산 안에서 일을 어디에 두느냐로 조금 갈린다. 상태 변화가 프로그램을 몰고 가면 코드를 나누는 선 자체가 객체와 함수로 크게 갈린다.

이 절이 세운 것 7장의 답은 관심사 분리, 8장의 답은 두 응집이고, 우열은 7장에서만 났다

이제 7장으로 들어가 이 답이 어느 시험 걸음에서 생기는지 따라간다.

37장 볼링 게임 — 덤 공이 설계를 꺾는다

이 절의 목표 7장 두 풀이가 덤 공 때문에 어떻게 꺾이고 어디서 갈리는지 안다
왜 여기 있나 축에서 7장은 차이가 조금 나는 칸이다. 그 조금이 어느 시험 걸음에서 어떤 모양으로 생기는지가 7장의 답이다.

7장은 두 풀이를 시험 주도 개발(TDD)로 한 시험씩 키운다 — 저자가 Clean Craftsmanship 에 실었던 연습 문제를 크게 줄인 것이다. 설계를 떠미는 제약은 하나다 — 덤 공을 세려면 다음 공이 있어야 하는데, 굴리는 순간에는 아직 없고 모아 두었다 셀 때는 이미 있다.

한 게임은 프레임 열 개이고, 스페어(두 공으로 핀 열 개)는 다음 공 하나를, 스트라이크(첫 공으로 열 개)는 다음 공 둘을 덤으로 더한다. 거터는 핀을 하나도 못 맞힌 0점 공이고, 아래 표는 스페어 시험 하나의 점수를 프레임마다 센다.

48장 버스 기사 소문 — 걸음마다 상태가 바뀌는 문제

이 절의 목표 8장 두 풀이가 상태를 어디에 두고 그래서 코드를 무엇을 따라 나누는지 안다
왜 여기 있나 7장의 차이가 작았던 것은 상태 변화가 작아서다. 저자는 객체지향이 가장 잘하는 문제로 옮겨 그 차이가 커지는지 본다.

저자는 앞 비교에서 함수형을 택할 강한 까닭을 찾지 못했다며 조금 더 흥미로운 문제로 옮긴다. 객체지향은 1966년 Dahl 과 Nygaard 가 이산 사건 시뮬레이션을 위해 ALGOL-60 을 고치며 태어났고(SIMULA-67), 저자는 그래서 시뮬레이터 문제를 고른다.

이 문서의 풀이로는, 객체지향의 본고장인 이런 문제에서도 함수형이 밀리지 않으면 그것이 의미 있는 결과다. 이 장은 7장처럼 코드를 키우는 과정 대신 완성된 두 풀이를 견준다.

문제는 이렇다 — 기사 n 명이 저마다 순환 노선을 달리고, 같은 정류장에 함께 닿은 기사끼리만 소문을 주고받는다. 모든 기사가 모든 소문을 알 때까지 몇 걸음이 걸리는지 구하고, 480 걸음에서 멈춘다.

설계를 떠미는 제약은 걸음마다 상태가 바뀐다는 것이고, 저자는 이 문제를 참된 유한 상태 기계라 부른다. 유한 상태 기계는 들어오는 사건과 지금 상태에 따라 동작을 하며 상태에서 상태로 옮겨 가는 것이다.

원문의 작은 예로 걸음을 따라간다. 노선 [p q r] 을 도는 Bob 은 소문 X 를, [s t u p] 를 도는 Jim 은 소문 Y 를 안다 — 두 사람이 언제 같은 정류장에 서는지 본다.

5마무리 — 상태 변화가 클수록 갈리는 자리가 커진다

이 절의 목표 두 장의 답을 축 위에 모으고, 판정 · 답이 난 것 · 미룬 것 · 다음 읽을 곳을 안다
왜 여기 있나 문서를 꿰던 물음에 두 장이 준 답을 한 화면에 모아야 7장과 8장이 한 이야기로 선다.

첫 화면의 축에 두 장이 찾은 것을 채운다. 결과 칸이 이제 차이의 크기가 아니라 무엇이 갈렸는지를 말한다.

상태 변화가 프로그램을 얼마나 몰고 가나 — 두 장이 찾은 것
6장 소인수 분해(Prime Factors) 이 문서가 다루지 않는 앞 장 — 상태 변화 없음 단순한 함수라 스타일의 영향이 적다
7장 볼링 게임 배열 칸 번호 정도의 상태 덤 공을 가려내는 일을 한 반복에 두나 두 함수로 가르나 — 관심사 분리
8장 버스 기사 소문 순간마다 바뀌는 상태가 몰고 감 상태를 가변 객체에 두나 불변 값으로 흘리나 — 데이터 응집 · 행위 응집
상태 변화가 커질수록 갈리는 자리가 한 계산 안에서 코드 전체를 나누는 선으로 커진다.

잘하는 것조금 더 단순한 끝 모습가려내기와 더하기의 분리 — 더 유연하고 쓸모 있음
못하는 것조금 더 높은 결합 · 한 클래스 안의 공 쌓기와 점수 계산작은 잔재주에 끌려가기 쉬움
판정둘 가운데 덜 유연하다고 본다둘 가운데 더 낫다고 본다 — 열두 줄 남짓의 코드 이야기라는 단서가 붙는다
판정 근거덤 공을 가려내는 일을 점수를 더하는 반복 안에서 한다덤 공을 가려내는 to-frames 와 더하는 add-frames 를 두 함수로 가른다
7장 볼링 게임 — 저자가 우열을 가렸다.

못하는 것고른 선(노선 · 정류장 · 소문)이 좋은 선이라는 보장 없음거의 나뉘지 않은 코드 — 자라면 그 문제가 거세게 드러남
8장 버스 기사 소문 — 어느 쪽이 나은가는 판정하지 않았다. 데이터 응집과 행위 응집 가운데 어느 쪽이 나은지를 저자는 뒤 장으로 미룬다.
답이 난 것
  • 상태 변화가 프로그램을 더 몰고 갈수록 두 풀이는 더 크게 갈리나? 저자는 아마 그렇다고 본다 — 소인수 분해는 거의, 볼링은 조금, 버스 기사 소문은 크게 갈린다(8장 결론).
  • 7장에서 둘 가운데 어느 쪽이 나은가? Clojure 쪽 — 가려내기와 더하기를 두 함수로 갈라 더 유연하다고 저자는 본다. 열두 줄 남짓의 코드 이야기다.
  • 8장에서 두 풀이는 코드를 무엇을 따라 나누나? Java 는 상태를 쥔 객체를 따라(데이터 응집), Clojure 는 world 를 다루는 함수를 따라(행위 응집) 나눈다.
답이 나지 않은 것과 이어지는 곳
  • 데이터 응집과 행위 응집 가운데 어느 쪽이 나은가? 뒤 장들 — 저자가 어느 장인지는 밝히지 않았다
  • Clojure 풀이가 자라면 코드를 어떤 선으로 나누나? 저자가 다룰 곳을 밝히지 않았다 — world 를 다루는 연산을 따라 나누는 편이 나을 것 같다는 짐작만 남겼다
