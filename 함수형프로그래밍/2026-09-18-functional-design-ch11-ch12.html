[학습] 데이터 흐름 배관과 SOLID 원칙

Java 를 아는 개발자가 11장과 12장을 따라 읽고, 함수형 프로그램이 값을 흘리는 배관으로 짜인다는 것과 그 배관도 객체지향 때와 같은 SOLID 원칙으로 가른다는 것을 코드로 설명할 수 있게 한다.

읽는 사람 — Java 는 알고 Clojure 는 처음인 개발자 — 객체지향과 SOLID 의 이름은 알지만 Clojure 문법과 멀티메서드는 모른다.

1두 장을 꿰는 물음 — 배관을 무엇으로 나누나

이 절의 목표 11장과 12장이 무엇을 다루고 어떤 물음 하나로 이어 읽을 수 있는지 안다
왜 여기 있나 두 장은 예제도 주제도 달라, 이어 읽을 물음 없이 들어가면 12장이 11장과 떨어진 원칙 목록으로 읽힌다.

함수형 프로그램은 값을 흘려보내는 배관으로 짜이는데, 그 배관은 무슨 원칙으로 나누나? 11장이 배관을, 12장이 원칙을 답한다.

두 장을 이 한 물음으로 묶는 것은 이 문서의 풀이이고, 저자는 12장에서 11장을 부르지 않는다. 두 장은 3부 함수형 설계(Functional Design)다 — 6~10장이 같은 문제를 Java 와 Clojure 로 견줬다면, 11장부터는 함수형 설계 자체를 다룬다.

11장 첫 문장은 9장에서 한 말을 받아 시작한다 — 함수형 프로그램의 설계는 절차보다 배관(plumbing)에 가깝다. Clojure 문법은 따로 가르치지 않고, 논지에 필요한 문법만 그 줄 곁의 주석에서 한 줄로 푼다.

11장의 대상은 옛 CRT 화면을 흉내 내는 작은 프로그램 하나다. 아래 두 그림은 같은 프로그램을 Java 와 Clojure 로 짠 구조다 — 왼쪽은 무엇이 메서드들을 붙잡고 있는지, 오른쪽은 무엇이 함수 사이를 건너가는지부터 본다.

2두 장이 내린 답 — 값이 흐르고 원칙은 남는다

이 절의 목표 두 장이 내린 결론과 그 근거를 본문에 들어가기 전에 쥔다

두 장 모두 어느 방식이 낫다고 판정하지 않는다. 11장은 함수형으로 쓸 때 저자가 어느 쪽으로 기우는지를 말하고, 12장은 원칙이 객체지향 전용이 아니라는 것을 보인다.

12장의 답은 대응으로 읽으면 선명하다. 인터페이스 자리에는 멀티메서드 선언만 든 모듈이, 추상 클래스 자리에는 선언 넷과 구현 하나가 든 모듈이, 상속 자리에는 한 종류라는 선언 한 줄이 선다.

11장은 이 문장으로 닫힌다 — 가변 언어에서는 행위가 객체를 흐르고, 함수형에서는 객체가 행위를 흐른다.

12장은 이렇게 닫힌다 — 전체 구조는 객체지향 프로그램과 무척 닮았지만 온전히 함수형이다. 두 장을 합치면 한 문장이 남는다: 함수형 프로그램은 값을 흘리는 배관으로 짜이고, 그 배관도 객체지향 때와 같은 원칙으로 가른다.

311장 데이터 흐름 — 반복 대신 배관

이 절의 목표 CRT 문제를 Java 와 Clojure 가 어떻게 달리 풀고 저자가 그 차이를 무엇이라 부르는지 안다
왜 여기 있나 배관이라는 말은 같은 프로그램의 코드 두 벌을 나란히 봐야 뜻이 선다 — 이 절이 그 두 벌이다.

저자는 함수형 프로그램의 설계에 데이터 흐름 편향(data flow bias)이 있다고 한다. 함수형 프로그램의 설계는 목록을 한 원소씩 도는 대신 map · filter · reduce 로 목록을 다른 목록으로 바꾸는 쪽으로 기운다.

저자는 이 편향을 볼링 게임 · 버스 기사 · 급여 예제에서도 볼 수 있다고 하고, 새 예로 옛 CRT 화면을 흉내 내는 문제를 든다. CRT 는 전자빔이 화면을 훑는 순간에 맞춰 빔을 켜 픽셀을 밝히므로, 몇째 사이클인지와 빔이 지나는 픽셀 자리가 맞물린다.

흉내 낼 프로세서의 명령은 둘이다. noop 은 한 사이클을 쓰고 아무 일도 하지 않으며, addx n 은 두 사이클을 쓰고 두 사이클이 다 끝난 뒤에야 x 레지스터에 n 을 더한다.

사이클이 시작할 때 x 가 픽셀 자리(사이클 번호를 40 으로 나눈 나머지)와 하나 이내로 맞으면 그 픽셀이 켜지고(#), 아니면 꺼진다(.). 결과는 40자짜리 줄 여섯이다.

이 사례의 설계를 떠미는 것은 addx 의 두 사이클이다. 명령 하나가 사이클 둘에 걸치므로 명령을 읽는 걸음과 픽셀을 그리는 걸음이 하나씩 맞지 않는다.

아래 재생기는 이 문서가 고른 작은 입력(명령 셋)을 사이클마다 따라간다. addx 가 두 사이클 동안 x 를 그대로 두는 자리를 본다.

Java 쪽은 가변 필드가 메서드들을 결합해, 메서드 하나를 떼어 읽으려면 앞 호출이 필드에 남긴 값을 알아야 한다. Clojure 쪽도 결합은 남지만 결합하는 것이 주고받는 값의 모양(어느 키에 어떤 꼴의 값)이라, :cycles 의 꼴을 바꾸면 그 값을 쓰는 함수들을 함께 고친다.

그래서 Clojure 쪽은 함수 하나를 떼어 읽고 시험하기 쉽고, 차례가 코드에 드러난다. 저자는 이 차이를 편향으로 설명한다 — Clojure 로도 Java 에 훨씬 가까운 알고리즘을 쓸 수 있었지만 함수형 언어로 쓸 때는 데이터 흐름 쪽으로 기운다.

저자는 Java 와 C# 의 새 흐름 기능이 장황하고 덧붙인 듯 어색하다고 보고, 절차 · 객체지향 언어로는 배관(plumb)보다 반복(iterate)하게 된다고 한다.

저자는 이것을 한 문장으로 줄인다 — "가변 언어에서는 행위가 객체를 흐르고, 함수형에서는 객체가 행위를 흐른다". 아래 표는 이 문장에서 무엇이 제자리에 있고 무엇이 움직이는지를 가른다.

SRP — 변경을 요청하는 액터로 모듈을 가른다

여기서 읽을 것 — 시험 하나가 업무 규칙을 해석 코드에 끌어들이는 자리와, 그것이 왜 위험한지를 본다.

SRP 는 모듈을 바꾸게 만드는 원천에 모듈을 맞추라는 원칙이고, 그 원천은 사람이다. 모듈은 그것을 바꾸게 만드는 원천, 곧 변경을 요청하는 사람들에게 책임진다.

같은 것을 요구하는 사람의 무리를 액터(actor)라 한다. 한 모듈이 여러 액터에게 책임지면 액터들의 변경 요청이 서로 간섭하고, 간단한 기능 하나를 바꿨는데 엉뚱한 곳이 깨지는 취약함(fragility)이 생긴다.

저자의 예는 고객 기록을 글에서 해석하는 코드이고, 시험이 이야기를 들려준다며 시험부터 보인다. 시험 여섯 가운데 첫째는 올바른 입력을 보고, 다음 넷은 빠지거나 틀린 입력 같은 문법 오류를, 마지막 하나는 한도 5만을 넘으면 거부하는 업무 규칙을 본다.

OCP — 고치지 않고 늘린다

여기서 읽을 것 — copy 의 네 판에서 정책 쪽 코드가 무엇을 그대로 두는지 표로 먼저 보고 코드로 들어간다.

OCP 는 Bertrand Meyer 가 1988 년 책에서 처음 말한 원칙이다. 소프트웨어 모듈은 확장에는 열려 있고 수정에는 닫혀 있어야 한다 — 모듈의 동작을 늘리거나 바꿀 때 그 모듈의 코드를 고치지 않아도 되게 짜라는 뜻이다.

모순처럼 들리지만 늘 하는 일이다. C 의 copy 는 표준 입력을 표준 출력에 옮기는데, OCR 이나 음성 합성기를 새 장치로 더해도 고치지도 다시 컴파일하지도 않고 그 사이에서 글자를 옮긴다.

읽기와 쓰기가 누구의 것인지는 운영체제가 정한다.

이것이 되는 까닭은 고수준 정책이 저수준 세부를 추상 층을 거쳐 만나기 때문이다. 정적 타입 언어는 그 층을 인터페이스로, Python · Ruby 는 문법 없는 덕 타입으로 세우고, 함수형 언어에는 오래된 장치가 또 있다 — 함수다.

정의 멀티메서드 — 판별값으로 구현을 고른다

defmulti 는 멀티메서드를 선언하며 판별 함수를 받는다 — 부를 때 인자에서 판별값을 뽑는 함수다. defmethod 는 판별값 하나에 구현 몸통 하나를 붙인다.

Clojure 는 그 층을 네 가지 장치로 세울 수 있다. 네 판에서 새 장치를 더하는 쪽이 무엇을 쓰고 따로 배포할 수 있는지를 먼저 본다.

Clojure 는 그 층을 함수 · 맵 · 멀티메서드 · 프로토콜로 세운다. 다음 소절의 LSP 는 그 층에 끼워 넣는 세부가 지켜야 할 약속을 다룬다.

LSP — 하위 타입이 기대를 어기지 않는다

여기서 읽을 것 — 두 사례를 차례로 본다 — 급여를 받으면 안 되는 직원과, 시험을 다 통과했는데 틀린 정사각형.

LSP 는 Barbara Liskov 가 1988 년에 내린 하위 타입의 정의다. 하위 타입은 기반 타입을 쓰는 어떤 프로그램에서도 그 자리를 대신할 수 있어야 한다.

저자는 OCP 를 지원하는 언어는 LSP 도 지원해야 한다고 한다. LSP 위반은 모두 잠재된 OCP 위반이기 때문이다.

첫 사례는 급여다. 직원은 클래스가 아니라 함수 셋을 담은 맵이고, pay 는 그 셋 — 지급일인가 · 급여 계산 · 수표 보내기 — 만 꺼내 부른다(Java 로 치면 인터페이스 메서드만 부른다).

1(defn pay [employee pay-date]

pay 가 기대하는 것은 지급일 함수가 참 · 거짓을 돌려주는 것이다.

make-later-employee 로 만든 직원은 지급일 함수가 거짓 대신 :tomorrow 를 돌려준다. 내일 지급한다는 뜻으로 쓴 값이지만 Clojure 에서 거짓은 false 와 nil 뿐이라 :tomorrow 는 참으로 읽히고, pay 가 급여를 보내 지급일이 아닌 직원에게는 주지 않는다는 시험이 실패한다.

"이것은 LSP 위반이다" 라는 저자의 판정은 이 뜻이다. 참 · 거짓을 기대하는 쪽은 pay 이고 이 직원이 그 기대를 어겼다 — 직원 타입이 무엇인지 정하는 것은 직원을 다루는 pay 같은 함수들이라고 저자는 말한다.

왜 흉한가는 저자가 답하지 않고 남긴 물음이라 이 문서의 풀이로 답한다. 참 · 거짓을 돌려주기로 한 함수의 값에 = true 를 붙인 꼴이라 겉보기에 뜻 없는 군더더기이고, 이 직원 때문에만 필요한 조건이 정책 한가운데 박힌 것이다.

첫 사례가 약속을 어긴 세부를 보였다면, 둘째 사례는 약속을 지킨 것처럼 보이는 세부를 보인다. 객체지향 문헌은 하위 타입을 ISA("~은 ~이다")로 부르는데, 저자는 이 ISA 규칙이 깊이 오해를 부를 수 있다며 오래된 정사각형 · 직사각형 문제를 든다.

몇 년 잘 돌던 직사각형 시스템에 고객이 정사각형을 요구한다. 기하에서 정사각형은 직사각형이므로 ISA 규칙대로 직사각형을 받는 함수들이 정사각형도 받게 하는데, Clojure 에서는 두 변이 같은 직사각형을 만들면 된다.

저자의 판정은 LSP 위반이다 — minimally-increase-area 는 높이와 너비를 따로 바꿀 수 있다고 기대하는데 고객에게 정사각형은 그렇지 않다. 객체에 :type 칸을 더하고 이 함수에 if 를 넣어 고칠 수 있지만, 그 고침들은 OCP 를 어긴다.

저자는 다른 해법을 연습으로 남기고, 두 타입을 아예 떼는 쪽을 고른다. 까닭은 대리자 규칙이다 — 사물의 대리자는 그 사물들의 관계를 나눠 갖지 않는다.

코드 속 정사각형 객체는 도형이 아니라 도형의 대리자라, 기하에서 정사각형이 직사각형이라는 관계를 물려받지 않는다. 정사각형 객체는 직사각형 객체처럼 움직이지 않기 때문이다.

이 소절이 세운 것 LSP 는 쓰는 쪽의 기대로 하위 타입을 판정한다

어긴 세부를 정책에서 달래면 OCP 까지 깨진다. 다음 소절의 ISP 는 쓰는 쪽이 필요 없는 것까지 의존하게 되는 자리를 다룬다.

ISP — 쓰지 않는 것에 의존하지 않는다

여기서 읽을 것 — Java 인터페이스를 쪼개는 그림과 Clojure 의 세 선언을 차례로 보고, 동적 언어에서도 이 원칙이 왜 남는지 본다.

이 원칙의 이름은 정적 타입 객체지향 언어에서 왔다. 저자의 예는 Java 인터페이스 AtmInteractor 로, 요청 메서드 셋이 한 인터페이스에 묶여 있어 그중 하나만 부르는 사용자도 셋 모두에 의존한다.

Java — AtmInteractor

Clojure 에서는 덕 타입 장치 하나로 같은 일을 한다. 세 멀티메서드는 한 선언 아래 묶이지 않아 같은 파일에 둘 필요도 없고, 하나가 바뀌거나 새로 더해져도 나머지 사용자에게 닿지 않는다.

그래도 원칙은 남는다. 이름 속 인터페이스는 Java 문법이 아니라 한 모듈의 접근점 목록 전부라는 넓은 뜻이다.

Java 는 소스 파일마다 공개 클래스 하나를 두게 해 이 원칙이 피하려는 조건을 저절로 만든다. Clojure 같은 동적 언어는 어느 파일에 무엇이든 둘 수 있어, 필요 없는 것에 의존하게 만들기가 오히려 더 쉽다.

왜 신경 쓰나에 저자는 까닭 셋을 든다. 정적 언어에서는 쓰지 않는 함수 하나가 바뀌어도 다시 컴파일하고 배포해야 한다.

동적 언어에서는 비용이 줄지만 0 은 아니다. Clojure 는 모듈 사이의 소스 의존이 순환하면 안 되는데, 함수가 많은 모듈일수록 드나드는 의존이 많아 순환에 끼어들 확률이 커진다.

아마 가장 좋은 까닭은, 필요 없는 의존을 줄인 모듈 구조가 사람이 관심사를 가르고 결합을 낮추려 애쓴 흔적이라 읽는 사람이 고마워한다는 것이다. 저자가 말하는 ISP 의 참뜻은 세 줄이다: 함께 쓰이는 것은 모으고, 따로 쓰이는 것은 가르고, 필요 없는 것에 의존하지 않는다.

이 소절이 세운 것 ISP 는 모듈의 접근점을 쓰는 사람 단위로 가른다

다음 소절의 DIP 는 이렇게 가른 모듈 사이 의존의 방향을 정한다.

DIP — 소스 의존을 추상 쪽으로 뒤집는다

여기서 읽을 것 — 옛 구조에서 소스 의존과 실행 흐름이 나란하던 것이 인터페이스 하나로 어떻게 갈라지는지 그림 셋으로 본다.

저자는 원칙의 무게를 이렇게 매긴다 — OCP 는 도덕적 심장, SRP 는 조직하는 힘, LSP · ISP 는 구덩이 둘레의 경고 표지, DIP 는 모두의 밑에서 도는 장치다. 위반의 해법이 거의 늘 의존 몇을 뒤집는 것이라, 가장 긴 사례인 비디오 가게가 DIP 에 붙는다.

먼 옛날 소프트웨어는 소스 의존이 실행 의존과 나란히 흘렀다. 아래 그림에서 실선이 소스 의존, 점선이 실행 흐름이다.

1960년대 말 Dahl 과 Nygaard 는 ALGOL 컴파일러의 자료 구조 하나를 스택에서 힙으로 옮기다 객체지향을 발견했고, 의존을 쉽고 안전하게 뒤집는 능력이 함께 생겼다. 끊는 방법은 사이에 인터페이스 하나를 넣는 것이다.

이 능력으로 고수준 모듈이 저수준 모듈에 의존하지 않게 할 수 있다. 업무 규칙은 실행 때 UI 와 DB 를 부르지만 소스로는 둘을 모르므로, UI 와 DB 는 플러그인이 되어 업무 규칙을 건드리지 않고 갈아 끼워진다 — OCP 를 따르는 것이다.

모든 의존이 추상을 향한다는 데서 저자는 DIP 를 한 줄로 적는다 — 가능하면 모든 소스 코드 의존이 추상을 가리키게 한다. 동적 언어에서는 인터페이스가 소스 모듈로 있지 않고, 양쪽이 따르는 덕 타입이 그 자리를 맡는다.

이 소절이 세운 것 DIP 는 실행 흐름과 소스 의존의 방향을 가른다

다음 소절의 비디오 가게가 이 뒤집기를 Clojure 모듈 열한 개로 해 보인다.

비디오 가게 — 정책과 형식을 추상 뒤로

여기서 읽을 것 — 명세서 프로그램이 모듈 열한 개로 갈라지는 과정을, 계산과 형식을 떼는 걸음과 둘을 추상 뒤로 보내는 걸음으로 나눠 본다.

저자는 Martin Fowler 의 『Refactoring』 첫 판에 나온 비디오 가게 예를 Clojure 로 옮겨 온다. 손님이 비디오를 며칠 빌리면 비디오 종류(:regular · :new-release · :childrens)와 날수로 요금과 적립 점수를 계산하고 명세서를 찍는다.

처음 판의 시험은 명세서 문자열 전체를 견주는데, 저자는 이것을 끔찍한 SRP 위반으로 본다. 업무 규칙과 형식이 한 시험에 결합돼, 첫 줄의 Rental Record for 를 Rental Statement for 로만 바꿔도 시험이 모두 깨진다.

저자는 시험을 계산 · 형식 · 통합 셋으로 가르고, 명세서 문자열 대신 명세서에 들어갈 자료를 담은 맵을 돌려주게 바꾼다. 아래는 그 걸음에서 바뀐 함수다.

  • OCP — 정책과 세부 사이에 추상 층을 두어 세부를 늘려도 정책을 고치지 않는다(copy)

  • DIP — 소스 의존을 추상 쪽으로 뒤집어 UI · DB 같은 세부를 플러그인으로 만든다(비디오 가게)
