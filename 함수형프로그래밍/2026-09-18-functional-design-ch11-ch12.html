3데이터 흐름 — 반복하지 않고 배관한다

이 절의 목표함수형 프로그램이 절차가 아니라 배관에 가깝다는 저자의 말이 코드로 무엇인지 본다.
왜 여기 있나9장에서 함수형 프로그램은 절차보다 배관에 가깝다고 했지만 그때는 급여 문제 하나였다. 이 장은 그 편향을 이름 붙여 설명하고, 반복으로 풀면 어떻게 되는지를 Java 코드로 나란히 놓아 대조한다.

문제는 이렇다. 가로 40, 세로 6 픽셀 화면이 있고 빔이 시계에 맞춰 왼쪽에서 오른쪽으로 한 픽셀씩 지나간다. 시계 사이클 번호와 레지스터 x 가 맞으면 그 자리의 픽셀이 켜진다. 정확히는 x 가 세 칸 폭의 창이라 x-1, x, x+1 이 맞는다. 명령은 둘뿐이다. noop 은 한 사이클을 쓰고 아무것도 안 한다. addx n 은 두 사이클을 쓰고 둘째 사이클이 끝난 뒤에야 x 에 n 을 더한다. 명령을 다 돌리고 40자짜리 문자열 여섯 줄을 내면 된다.

그래서왜 이 문제인가

옛 CRT 화면이 실제로 이렇게 돌았다. 빔이 화면을 훑는 정확한 순간에 비트맵의 그 비트가 켜져 있으면 빔을 쏜다. 저자가 이 문제를 고른 이유는 하나다 — 사이클마다 상태가 바뀌는 문제라서, 절차형으로 쓰면 반복문과 가변 변수가 나오는 것이 가장 자연스러워 보이기 때문이다. 그 자연스러운 풀이와 배관 풀이를 나란히 놓는다.

이 장에서 네 마디가 무엇인가

  2. 2Java 로 풀면사이클마다 도는 반복문, 필드 여섯, addx 의 두 사이클을 세는 잔재주. 메서드는 작지만 필드가 묶는다Java 코드

Java 코드 — 사이클을 하나씩 돈다

여기서 읽을 것 — 메서드가 아니라 필드를 본다. 필드 여섯이 메서드 셋을 어떻게 묶는지, 그리고 addx 의 두 사이클을 세려고 무엇이 필요했는지.

Java, C, Go, C++, C# 같은 절차형·객체지향 언어라면 사이클을 하나씩 도는 반복문을 만들고, 그 안에서 명령을 소비하며 x 를 고치고 픽셀을 모을 것이다. 저자가 든 전형적인 Java 코드다. 필드 선언과 execute 만 펼쳐 두었다.

public class Crt {
  private int x;
  private String pixels = "";
  private int extraCycles = 0;
  private int cycle = 0;
  private int ic;
  private String[] instructions;

  public Crt(int x) {
    this.x = x;
  }
⋯ doCycles — 사이클마다 픽셀을 찍고 명령을 실행하는 반복문
  public void doCycles(int n, String instructionsLines) {
    instructions = instructionsLines.split("\n");
    ic = 0;
    for (cycle = 0; cycle < n; cycle++) {
      setPixel();
      execute();
    }
  }
  private void execute() {
    if (instructions[ic].equals("noop"))
      ic++;
    else if (instructions[ic].startsWith("addx ")
             && extraCycles == 0) {
      extraCycles = 1;
    }
    else if (instructions[ic].startsWith("addx ")
             && extraCycles == 1) {
      extraCycles = 0;
      x += Integer.parseInt(instructions[ic].substring(5));
      ic++;
    } else
      System.out.println("TILT");
  }
⋯ setPixel · getPixels · getX
  private void setPixel() {
    int pos = cycle % 40;
    int offset = pos - x;
    if (offset >= -1 && 1 >= offset)
      pixels += "#";
    else
      pixels += ".";
  }

  public String getPixels() {
    return pixels;
  }

  public int getX() {
    return x;
  }
}

저자가 눈여겨보라고 한 것이 셋이다. 첫째, 고쳐지는 상태가 여섯 필드에 흩어져 있다. 둘째, 사이클을 하나씩 돌며 픽셀을 채운다. 셋째, addx 가 두 사이클을 쓴다는 사실을 처리하려고 extraCycles 라는 잔재주가 들어갔다. 그리고 메서드가 작게 나뉘어 있어도 그 메서드들은 전부 가변 필드로 서로 묶여 있다. 가변 클래스의 메서드가 늘 그렇다.

불변식이 장의 판정

4SOLID — 다섯 원칙이 함수형에서 서는 자리

이 절의 목표SOLID 다섯 원칙이 객체지향 전용이 아니라는 저자의 주장을, 원칙마다 함수형에서의 위반 사례와 장치로 확인한다.
왜 여기 있나저자가 20년 전 객체지향 맥락에서 SOLID 를 썼기 때문에 많은 사람이 이것을 객체지향의 것으로, 함수형과는 상극으로 여긴다. 저자는 그것이 불행한 오해이고 SOLID 는 스타일과 무관한 일반 설계 원칙이라고 한다. 9장이 아키텍처 경계를 함수형에서 세웠다면, 이 장은 그 경계를 긋는 원칙들을 세운다.

이 장은 원칙마다 요약이고 완전한 설명이 아니라고 저자 스스로 말한다. 이 문서도 같다 — 원칙마다 한 줄 정의, 함수형에서의 사례, 저자의 결론 셋만 적는다. 다섯 원칙의 무게는 같지 않다. 저자의 말로 OCP 가 도덕적 심장이고, SRP 가 조직하는 힘이며, LSP 와 ISP 는 부주의가 만든 구덩이 주변의 경고 표지이고, DIP 가 나머지 전부의 밑바탕 장치다. 그래서 DIP 에 가장 긴 사례가 붙는다.

SRP — 바뀌는 이유가 다른 것을 한 모듈에 두지 않는다

여기서 읽을 것 — 함수형에서 SRP 위반이 어떤 모양인지. 클래스가 없어도 위반은 똑같이 생긴다. 한 함수 안에서 누가 바꾸는 코드인가가 갈리는 자리를 본다.

SRP 는 모듈이 바뀌는 원인에 집중하라는 말이다. 원인은 사람이다 — 소프트웨어를 바꾸자고 하는 것은 사람이고, 같은 것을 요구하는 사람들의 묶음이 액터다. 액터가 다르면 요구하는 변경의 방향이 다르고 서로 엇갈리기도 한다. 한 모듈이 둘 이상의 액터에 책임지면 그 변경들이 서로 간섭하고, 단순한 변경에 시스템이 엉뚱한 곳에서 깨지는 취약함이 생긴다.

OCP — 고치지 않고 늘린다, 추상 계층은 함수다

여기서 읽을 것 — 인터페이스라는 문법이 없는 언어에서 추상 계층을 무엇으로 만드나. 저자가 같은 copy 프로그램을 네 번 쓴다. copy 본문이 바뀌는지만 보면 된다.

OCP 는 1988년 Bertrand Meyer 의 말로, 모듈은 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 것이다. 모순처럼 들리지만 늘 하는 일이다. C 의 copy 는 getchar 와 putchar 로 글자를 옮기는데, 운영체제에 문자 인식기와 음성 합성기를 새 장치로 붙여도 고치지도 다시 컴파일하지도 않고 돈다. 높은 수준의 정책이 낮은 수준의 세부를 추상 계층을 통해 만나기 때문이다. 객체지향은 그 계층을 다형 인터페이스로 만든다. 함수형 언어에는 오래된 다른 수단이 있다 — 함수.

주의독립 배포는 어디까지 되나

OCP 의 이득 하나는 정책과 세부를 따로 컴파일해 따로 배포하는 것이다. Java 라면 jar 둘. 함수 인자 · 맵 · 다형 함수 셋은 그것을 못 한다 — 정책과 세부를 다른 jar 에서 동적으로 실을 수 없다. 저자는 이것이 Java 보다 훨씬 덜 문제라고 한다. Clojure 는 "싣는 것" 이 거의 늘 소스 컴파일이라, jar 는 아니어도 소스 파일에서 동적으로 컴파일해 싣는다. 그래도 완전한 독립 배포가 꼭 필요하면 defprotocol 과 defrecord 가 있다. protocol 은 Java 인터페이스가 되어 따로 컴파일할 수 있다. 저자는 이것이 객체지향처럼 느껴지면 그것은 실제로 객체지향이기 때문이라고 한다 — JVM 은 객체지향 기반이고 Clojure 는 그 위에 잘 맞는다.

이 소절이 세운 것추상 계층은 함수 · 맵 · 다형 함수 · protocol 넷 중 무엇이어도 copy 는 안 바뀐다

인터페이스 문법이 없어도 정책이 세부를 모르게 하는 길이 넷 있고, 넷 다 copy 본문을 건드리지 않는다. 독립 배포까지 필요하면 protocol 이 Java 인터페이스를 실제로 만든다. 다음은 그 추상 계층을 지키지 못했을 때다.

LSP — 하위 타입은 상위 타입의 기대를 어기지 않는다

여기서 읽을 것 — LSP 위반이 왜 OCP 위반으로 이어지는지, 그리고 저자가 ISA 라는 말을 왜 믿지 않는지. 사례가 둘이다. 하나는 급여, 하나는 정사각형.

OCP 를 지원하는 언어는 LSP 도 지원해야 한다. LSP 위반은 전부 잠재된 OCP 위반이기 때문이다. 1988년 Barbara Liskov 가 하위 타입을 이렇게 정의했다 — 상위 타입을 쓰는 어떤 프로그램에서도 하위 타입이 그 자리를 대신할 수 있어야 한다.

불변식저자의 대리자 규칙

사물의 대리자는 그 사물들이 갖는 관계를 공유하지 않는다. 기하학에서 정사각형이 직사각형인 것은 사실이지만, 코드 속 정사각형 객체는 직사각형 객체가 아니다 — 둘은 도형이 아니라 도형의 대리자이고, 정사각형 객체는 직사각형 객체처럼 행동하지 않는다. 그래서 저자는 ISA 규칙을 좋아하지 않고, 두 타입을 아예 따로 두고 정사각형을 직사각형 함수에 넘기지 않는 쪽을 택한다. 다형 함수 · protocol · vtable 로 푸는 것은 연습 문제로 남긴다.

이 소절이 세운 것LSP 위반은 상위 정책에 if 를 끼우게 만들고, 그것이 OCP 위반이다

기대를 어긴 하위 타입은 상위 함수에 예외 처리를 밀어 넣는다. 현실에서 하나가 다른 하나의 일종인 두 사물이 코드에서도 하위 타입 관계라는 보장은 없다. 다음은 인터페이스의 크기에 관한 원칙이다.

ISP — 필요 없는 것에 의존하지 않는다

여기서 읽을 것 — 인터페이스가 선언되지 않는 언어에서 이 원칙이 무슨 뜻인지. 이름 속 인터페이스라는 낱말이 Java 의 interface 가 아니라 모듈의 접근점 전부라는 데서 답이 나온다.

이 원칙의 이름은 정적 타입 객체지향 언어에서 왔다. Java 의 AtmInteractor 인터페이스에 메서드 셋이 묶여 있으면, 그중 하나만 부르는 사용자도 셋 전부에 의존한다. 하나의 서명이 바뀌거나 하나가 추가되면 그 사용자를 다시 컴파일하고 배포해야 한다. Java 에서는 인터페이스를 셋으로 가르고 한 클래스가 셋을 모두 구현하는 것으로 푼다.

Clojure 에서는 애초에 갈라져 있다
atm · 다형 함수 셋
1(defmulti request-account :interactor)선언 하나가 함수 하나
2(defmulti request-amount :interactor)
3(defmulti request-pin :interactor)같은 파일에 있어야 할 이유도 없다
다형 함수 셋은 하나의 선언 아래 묶여 있지 않다. 같은 소스 파일에 있을 필요도 없고, 각자 제 기능의 모듈에 선언될 수 있다. 하나의 서명이 바뀌어도 나머지를 쓰는 사용자에게는 영향이 없다. 동적 타입 언어에서는 필요 없는 것에 의존하지 않기가 더 쉽다. 그러나 그것이 원칙이 적용되지 않는다는 뜻은 아니다.
그래서왜 그래도 신경 쓰나

이름 속 인터페이스라는 낱말은 Java 의 interface 클래스가 아니라 일반적인 뜻이다 — 모듈의 접근점 목록 전부. Java 는 클래스와 소스 파일이 강하게 묶여 있어 ISP 가 막으려는 조건이 저절로 만들어진다. Clojure 는 그 제약이 없어서 아무 파일에 아무것이나 선언할 수 있고, 그래서 사용자가 필요 없는 것에 의존하게 만드는 조건을 만들기가 오히려 더 쉽다. 대가는 정적 언어보다 작지만 0 이 아니다. Clojure 는 모듈 사이의 소스 의존이 순환하면 안 된다는 엄격한 요구가 있어서, 함수가 많은 모듈일수록 순환에 끼어들 확률이 커진다. 그리고 저자가 가장 큰 이유로 드는 것은 이것이다 — 불필요한 의존을 줄인 모듈 구조는 사람이 관심사를 가르고 결합을 낮추려고 애썼다는 표시이고, 읽는 사람이 그 배려에 고마워한다.

불변식저자의 ISP 한 줄

같이 쓰이는 것을 모으고, 따로 쓰이는 것을 갈라라. 필요 없는 것에 의존하지 마라.

이 소절이 세운 것동적 언어는 ISP 를 지키기 쉽지만 어기기도 쉽다

인터페이스가 선언되지 않으니 이미 갈라져 있고, 파일 제약이 없으니 아무것이나 한 파일에 몰아 넣을 수도 있다. 원칙은 그대로 산다. 마지막은 나머지 넷의 밑바탕이 되는 원칙이다.

DIP — 소스 의존을 추상으로 향하게 한다

여기서 읽을 것 — 이 장의 절반이다. 비디오 대여점 사례에서 requires 의 방향만 따라가면 된다. 책 그림의 화살표와 파일 머리의 requires 가 정확히 같다는 것이 요점이다.

먼 옛날 소프트웨어는 소스 의존과 실행 의존이 나란했다. 높은 수준 모듈이 중간 수준을 부르고 중간이 낮은 수준을 부르는데, 부르는 쪽이 늘 불리는 쪽의 소스 파일을 include · import · require 했다. 그래서 높은 수준의 정책이 낮은 수준의 세부에 떼어 낼 수 없이 의존했다. 1960년대 말 Dahl 과 Nygaard 가 ALGOL 컴파일러의 자료 구조 하나를 스택에서 힙으로 옮기며 객체지향을 발견했고, 그와 함께 의존을 쉽고 안전하게 뒤집는 능력이 생겼다. 부르는 쪽과 불리는 쪽 사이에 인터페이스를 끼우면, 실행은 아래로 흐르되 소스 의존은 둘 다 인터페이스를 향한다.

이론은 여기까지고, 저자는 Martin Fowler 의 Refactoring 초판에 나온 비디오 대여점 예제를 Clojure 로 다시 쓴다. 고객이 영화를 며칠 빌리고, 영화 종류(일반 · 신작 · 어린이)와 일수로 요금과 포인트를 셈해 명세서를 찍는 프로그램이다. 첫 판은 계산과 형식이 한 함수에 있어 SRP 위반이고, 명세서 첫 줄 문구가 바뀌면 시험이 전부 깨진다. 저자는 이것을 계산 모듈 · 형식 모듈 · 통합 시험 셋으로 가른다. 그리고 묻는다 — DIP 위반을 봤는가.

불변식이 장의 판정

SOLID 다섯 원칙은 함수형에서 전부 성립한다. SRP 와 LSP 위반은 함수 하나 안에서도 똑같이 생기고, OCP 의 추상 계층은 함수 · 맵 · 다형 함수 · protocol 넷으로 만들 수 있고, ISP 는 오히려 지키기 쉽되 어기기도 쉽고, DIP 의 의존 역전은 requires 의 방향으로 그대로 드러난다. 비디오 대여점은 모듈 열하나로 갈리고 가장 중요한 소스 의존이 뒤집혀, 높은 수준 정책이 낮은 수준 세부에 의존하지 않는다.

저자가 장을 닫는 문장은 이렇다 — 전체 구조는 객체지향 프로그램과 아주 비슷하게 보이지만, 전부 함수형이다.

이 소절이 세운 것의존을 뒤집는 장치는 다형 함수와 derive 이고, 결과는 requires 의 방향에 드러난다

최상위 정책은 추상 둘만 requires 하고 구현 넷의 이름을 모른다. 정책 종류와 영화 종류의 쌍으로 갈리고, 파생 정책은 하나만 덮는다. 그림의 화살표와 파일 머리의 requires 가 같다. 아래는 이것을 이 장이 받았던 물음으로 되돌린다.

이 절이 세운 것SOLID 는 스타일과 무관한 원칙이고, 함수형에서는 그 장치가 함수와 다형 함수다

이 절이 있는 이유로 돌아온다 — SOLID 가 객체지향 전용이라는 오해였다. 다섯 원칙 모두 함수형에서 위반이 생기고 장치가 있다. 인터페이스 자리에 defmulti 가, 추상 클래스 자리에 defmulti 와 구현 하나가 든 모듈이, 상속 자리에 derive 가 선다. 9장에서 "아키텍처로는 같은 그림" 이라고 한 것이 이 장에서 원칙 다섯으로 뒷받침된다.

저자가 이 장 어디에서도 다루지 않은 물음이 하나 남아 있다. 9장이 미룬 객체와 함수의 거리가 장점인지 단점인지다. 이 장은 그 물음에 답하지 않고, 그 거리 위에서도 원칙이 선다는 것만 보였다.

5전체를 한 번에

이 절의 목표7장부터 12장까지 여섯 장이 무엇을 쟀는지 한 화면에 모으고, 미뤄진 물음이 어디로 이어지는지 안다.
왜 여기 있나세 문서에 걸친 여섯 장이라 한 번 모아 두지 않으면 "무엇이 답이 났고 무엇이 남았는지" 가 흩어진다.

여섯 장이 잰 것

여기서 읽을 것 — 앞의 둘은 차이를, 가운데 둘은 같음을, 뒤의 둘은 같음 위의 도구를 쟀다.

7장부터 12장까지 — 무엇을 쟀나→ 커진다
7·8장볼링 · 버스 기사상태 변화가 커질수록 두 스타일이 갈린다차이
9·10장급여 — 다형성 · 타입아키텍처와 타입의 눈으로는 다시 만난다같음
11장CRT — 데이터 흐름상태를 값으로 흘린다편향의 이름
12장SOLID나누는 원칙 다섯이 그대로 선다도구
차이를 재던 책이 같음을 재고, 이제 그 같음 위에서 설계 도구를 꺼낸다. 저자가 예고한 대로 설계로 갈수록 두 스타일의 차이는 덜 중요해진다.
이 소절이 세운 것차이 → 같음 → 도구의 순서다

비교 분석 부는 차이에서 같음으로 갔고, 함수형 설계 부는 그 같음 위에서 원칙을 꺼낸다. 아래 두 목록은 11장과 12장이 각각 무엇을 남겼는지다.

11장이 남긴 것

여기서 읽을 것 — 11장에서 세운 것을 네 줄로. 마지막 줄이 저자의 한 문장이다.

  • 함수형 프로그램은 배관 쪽으로 기운다. map · filter · reduce 로 목록을 다른 목록으로 바꾸고, 한 원소씩 도는 반복을 피한다.
  • Java 코드는 필드 여섯이 메서드 셋을 묶는다. addx 의 두 사이클을 세려고 extraCycles 라는 잔재주가 든다.
  • Clojure 코드는 state 값이 함수 다섯을 지난다. 두 사이클은 x 를 두 번 넣는 자료의 모양이 되고, 함수 사이의 결합은 흐르는 자료의 모양뿐이다.
  • 저자의 한 문장 — 가변 언어에서는 행위가 객체를 흐르고, 함수형 언어에서는 객체가 행위를 흐른다.
이 소절이 세운 것11장은 편향을 이름 붙였고 우열은 말하지 않았다

같은 문제를 반복으로도 배관으로도 풀 수 있고, 함수형 언어를 쓰면 배관 쪽으로 기운다는 것이 전부다. 다음은 12장이 남긴 것이다.

12장이 남긴 것

여기서 읽을 것 — 원칙 다섯이 각각 함수형에서 무엇으로 서는지 한 줄씩.

  • SRP — 바꾸는 사람이 다르면 다른 모듈에. 파서 안의 신용 한도 검사가 위반이고, 명세에 넣어도 같은 위반이다.
  • OCP — 추상 계층은 함수다. 함수 인자 · 함수를 담은 맵 · 다형 함수 · protocol 넷 중 무엇으로도 copy 는 안 바뀐다. 독립 배포까지 필요하면 protocol.
  • LSP — 위반은 상위 정책에 if 를 끼우게 하고 그것이 OCP 위반이다. 코드 속 객체는 사물의 대리자라 사물의 관계를 공유하지 않는다.
  • ISP — 동적 언어는 이미 갈라져 있지만 아무것이나 한 파일에 몰 수도 있다. 같이 쓰이는 것을 모으고 따로 쓰이는 것을 갈라라.
  • DIP — requires 를 추상으로 향하게 한다. 비디오 대여점 모듈 열하나. 인터페이스는 defmulti 하나짜리 모듈, 추상 클래스는 defmulti 넷과 구현 하나, 상속은 derive.
불변식두 장을 덮고 남는 것

함수형 설계는 상태를 값으로 흘리는 배관을, 객체지향이 쓰던 원칙 다섯으로 나눈다. 저자가 12장을 닫는 말이 그것이다 — 전체 구조는 객체지향 프로그램과 아주 비슷하게 보이지만 전부 함수형이다.

이 소절이 세운 것12장은 다섯 원칙 전부를 함수형 장치로 옮겨 세웠다

원칙은 그대로이고 문법만 바뀐다는 것이 12장의 결론이다. 다음 소절은 두 장이 각 스타일에 실제로 내린 판정을 표로 모은다.

그래서 어느 쪽이 나은가

여기서 읽을 것 — 두 스타일의 잘하는 것·못하는 것·단서를 나란히 놓은 표와, 답이 난 물음과 나지 않은 물음의 경계. 책이 적은 것만 옮겼다.

객체지향 (Java 코드)함수형 (Clojure 코드)
잘하는 것인터페이스와 클래스 파일이 나누는 구조를 강제한다. ISP 가 막으려는 조건이 저절로 만들어지는 대신, 어디서 나눌지가 문법에 드러난다추상 계층을 함수로 만든다. 판별값이 쌍이면 자유도 둘로 갈리고, derive 로 하나만 덮어쓴다 — 대부분의 객체지향 언어에서 어려운 일
못하는 것새 기능이 언어에 덧붙인 것처럼 어색하다. 데이터 흐름 스타일을 쓸 수는 있지만 말이 많고, 반복 쪽으로 기운다독립 배포가 기본으로는 안 된다. 함수 · 맵 · 다형 함수는 jar 로 갈라 실을 수 없다. 그리고 파일 제약이 없어 필요 없는 것에 의존하게 만들기가 더 쉽다
저자가 단 단서가변 클래스의 메서드는 늘 가변 필드로 묶인다 — 작게 나눠도 그렇다protocol · record 로 독립 배포를 얻으면 그것은 객체지향이다 — JVM 이 객체지향 기반이라서
두 장 모두 어느 쪽 손도 들지 않는다. 11장은 편향을, 12장은 성립을 말한다.
그래서답이 난 것과 나지 않은 것

답이 났다 — 배관의 뜻. 상태를 값으로 만들어 함수에서 함수로 넘기는 것이고, 그러면 함수는 자료의 모양으로만 묶인다.

답이 났다 — SOLID 의 성립. 다섯 원칙 모두 함수형에서 위반이 생기고 장치가 있다. 문법이 바뀔 뿐 원칙은 같다.

답이 나지 않았다 — 객체와 함수의 거리. 9장이 미룬 물음이다. 함수형의 객체에 메서드가 강하게 붙어 있지 않은 것이 장점인지 단점인지를 11장도 12장도 묻지 않는다. 두 장은 그 거리 위에서도 배관과 원칙이 선다는 것만 보였다.

이 소절이 세운 것배관의 뜻과 원칙의 성립은 답이 났고, 객체와 함수의 거리는 여전히 남았다

두 장은 도구를 주고 우열은 묻지 않았다. 다음 소절은 남은 물음과 이 장들이 가리킨 뒤 장이다.

여기서 미뤄진 물음과 그것이 이어지는 곳

여기서 읽을 것 — 12장 본문이 각주로 가리킨 뒤 장들. 제목으로 짚은 것이라 내용은 그 장을 읽어야 안다.

  • 16장 디자인 패턴 되짚기 — 12장이 통합 시험의 마지막 의존을 끊는 데 쓸 수 있다고 한 Abstract Factory, 그리고 OCP 에서 본 장치들이 패턴으로 다시 나올 자리다.
  • 17장 Wa-Tor — 12장이 statement-policy 에서 쓴 Template Method 패턴, 그리고 ISP 에서 말한 "모듈 사이의 소스 의존은 순환하면 안 된다" 는 Clojure 의 요구가 실제 프로그램에서 어떻게 부딪히는지가 여기다.
  • 13장 테스트 — 12장이 시험과 제품 코드 사이의 결합을 지켜보라고 했고, 저자가 다른 책을 가리켰다. 제목으로 볼 때 그 이야기가 이어지는 자리다.
이 소절이 세운 것미뤄진 물음은 13장·16장·17장으로 이어진다

Abstract Factory 와 Template Method 는 패턴 장으로, 순환 의존은 Wa-Tor 로, 시험의 결합은 테스트 장으로 간다. 객체와 함수의 거리는 이 셋 어디에도 명시되지 않았다.

이 절이 세운 것여섯 장을 잇는 선 하나와, 미뤄진 물음 하나

이 절이 있는 이유로 돌아온다 — 흩어진 조각을 한 화면에 모으려던 것이었다. 모으면 선 하나가 남는다. 상태 변화가 커질수록 갈리던 두 스타일이 아키텍처에서 만나고, 그 위에서 같은 원칙으로 나뉜다. 답이 난 것은 배관의 뜻과 SOLID 의 성립이고, 답이 나지 않은 것은 객체와 함수의 거리다. 그 물음은 뒤 장으로 간다.
