두 장 모두 두 쪽을 견주되, 9장은 같다는 쪽으로, 10장은 저자가 고른 셋째 길로 닫는다.

9장은 “함수형 프로그램에도 객체는 있고, 다만 그 객체는 함수에 덜 묶여 있다 — 그것이 장점인지는 뒤 장에서 계속 캐 본다” 로 닫는다. 10장은 “이런 라이브러리는 양쪽 세계의 가장 좋은 것보다 나은 것을 준다” 로 닫는다.

이 문서가 두 장을 합쳐 읽은 한 문장은 이렇다. Clojure 풀이는 객체지향의 경계를 구현을 고르는 함수의 선언과 파일 배치로 되살리고, 타입이 지키던 객체의 모양은 명세로 필요한 만큼 지킨다.

9장의 답은 의존이 뒤집힌 자리에, 10장의 답은 명세를 검사하는 자리에 기댄다. 다음 절은 9장의 Java 풀이에서 경계가 처음 그려지는 자리부터 본다.

이 소절이 세운 것 Java 풀이의 경계는 인터페이스 셋 아래를 지나는 점선이다

점선 위의 run 은 인터페이스만 부르고, 점선 아래의 구현이 그 인터페이스를 향한다. Clojure 풀이에서 같은 선이 어디 서는지가 다음 소절들의 물음이다.

Clojure 풀이 — 직원 목록이 배관을 지난다

여기서 읽을 것 — 같은 문제를 Clojure 로 풀 때 직원 목록이 어떻게 흐르고, 그 목록의 원소가 무엇인지.

정의 다형 함수 — defmulti 와 defmethod

다형 함수는 이름 바로 뒤에 적은 함수의 결과(판별값)를 보고 구현을 고르는 함수다. defmulti 가 그 함수와 판별 함수를 선언하고, defmethod 가 판별값 하나에 몸통 하나를 채운다.

(defmethod calc-pay :hourly [employee]
  (let [db (:db employee)
        time-cards (:time-cards db)
        my-time-cards (get time-cards (:id employee))
        [_ hourly-rate] (:pay-class employee)
        hours (map second my-time-cards)
        total-hours (reduce + hours)]
    (* total-hours hourly-rate)))

(defmethod calc-pay :commissioned [employee]
  (let [db (:db employee)
        sales-receipts (:sales-receipts db)
        my-sales-receipts (get sales-receipts (:id employee))
        [_ base-pay commission-rate] (:pay-class employee)
        sales (map second my-sales-receipts)
        total-sales (reduce + sales)]

주의 클래스 그림이 아니다

Java · C# 에서는 인터페이스의 함수마다 다른 모듈에 구현할 길이 없지만, Clojure 에서는 그렇게 가를 수 있다. 저자는 “이것은 아키텍처 그림이지 클래스 그림이 아니다” 라고 경고한다 — 세 상자는 네임스페이스와 소스 파일이고, 인스턴스를 만들지 않는다.

그렇다고 객체가 없는 것은 아니다 — 직원 · 급여 지시, 그리고 급여 종류와 지급 방법도 객체이고, 그 객체들이 흐르는 함수가 있다.

불변식 네임스페이스 — 클래스 비슷한 것

Clojure 에서는 네임스페이스 하나가 제 소스 파일 하나에 들고 파일 이름이 네임스페이스 이름을 따른다 — Java 가 public 클래스를 제 이름의 파일에 두게 하는 것과 아주 비슷하다. 저자는 “그래서 각 Clojure 네임스페이스를 클래스 비슷한 것으로 여기게 될 수 있다” 고 하고, 딱 맞지는 않아도 나쁜 생각이 아니라고 한다.

이 소절이 세운 것 선언 파일을 떼면 정책과 구현이 가운데 선언만 바라본다
