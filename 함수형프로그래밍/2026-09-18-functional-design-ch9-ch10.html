1이 두 장은 8장이 미룬 물음을 받는다

이 절의 목표9장과 10장이 각각 무엇을 묻는 장인지, 그리고 7·8장의 결론에서 어떻게 이어지는지 안다.
왜 여기 있나8장은 "어느 쪽이 나은가는 뒤 장으로 미룬다" 로 끝났다. 9장은 그 물음을 아키텍처의 눈으로, 10장은 타입의 눈으로 받는다. 이 이어짐을 모르면 급여 문제가 갑자기 나오는 이유도, 명세가 왜 그렇게 긴지도 알 수 없다.

8장에서 이어지는 두 실

여기서 읽을 것 — 8장이 남긴 두 관찰이 각각 어느 장으로 가는지. 하나는 9장의 출발점이고 하나는 10장의 출발점이다.

이 절의 목표객체지향의 세 속성 중 가장 이롭다는 다형성이 함수형에서도 서는지, 서면 아키텍처 경계도 같은 자리에 그어지는지 본다.

문제는 이렇다. 직원 기록 데이터베이스가 있고, 급여 프로그램이 매일 돌면서 그날 줄 사람에게 급여를 만든다. 직원은 세 축에서 갈린다.

run() 은 직원을 한 명씩 돌며 세 전략에 묻기만 한다. 세 인터페이스가 정책과 세부를 가르고, 점선이 그 경계를 표시한다. Clojure 코드에 가져갈 물음은 둘이다 — 인터페이스 없이 어떻게 묻기만 하는가, 그리고 그 점선은 어디에 그어지는가.

Clojure 코드 — 배관, 그리고 인터페이스 없이 서는 다형성

여기서 읽을 것 — 같은 문제가 반복 대신 흐름으로 풀리는 모양, 그 흐름 속에서 객체가 어디에 있는지, 그리고 인터페이스가 없는데도 다형 함수가 어떻게 갈리는지. 마지막에 의존 방향을 본다.

저자는 함수형 코드를 UML 이 아니라 데이터 흐름도로 그린다. 아래 그림이다.

흐름도는 처리와 자료의 관계를 잘 보이지만 아키텍처 결정을 보이는 데는 UML 클래스도만 못하다고 저자 스스로 적는다. 그래도 그 흐름도에서 함수형의 최상위 함수가 나온다.

Java 코드와 다른 점은 반복이 아니라는 것이다. 직원 목록이 프로그램을 흘러 지나가며 단계마다 바뀐다 — 흐름도의 화살표 그대로. 저자는 이것이 함수형 프로그램이 구상되고 쓰이는 전형이라고 한다. 함수형 프로그램은 한 걸음씩 밟는 절차보다 배관에 가깝다. 데이터를 한 칸씩 도는 대신 데이터의 흐름을 조절하고 바꾼다.

그런데 Java 코드에 있던 그 점선은 어디 있는가. 저자는 시험에서 실마리를 찾는다.

데이터베이스는 직원 목록이고 직원은 정해진 필드를 가진 해시맵이다. 객체와 그리 다르지 않다. 함수가 돌려주는 지급 지시서도 해시맵이다 — 또 하나의 객체. 나머지 두 시험은 시급제 직원을 금요일에 입금으로, 수수료제 직원을 격주 금요일에 급여 담당자 보관으로 주는 경우이고, 세 시험이 :schedule · :pay-class · :disposition 세 축을 하나씩 바꾼다. 시급제 시험은 DB 에 :time-cards 가, 수수료제 시험은 :sales-receipts 가 직원 id 별로 붙어 있다는 것도 보인다.

급여가 맞게 계산되고 지급 방식이 맞게 해석된다. 어떻게 그렇게 되는가 — 저자가 "모든 것의 열쇠" 라고 부르는 자리다.

defmulti 는 Java 인터페이스와 비슷하되 같지 않다. 다형 함수 하나를 선언하는 것은 같은데, 갈리는 기준이 다르다. Java · C# · Ruby · Python 은 객체에 내재한 타입으로 갈리고, 여기서는 이름 뒤에 적은 판별 함수의 결과로 갈린다. get-pay-class 는 직원의 pay-class 첫 칸을 돌려주고, 시험에서 본 대로 그 값은 :salaried · :hourly · :commissioned 다. 각 값에 대한 몸통이 defmethod 로 더 아래에 있다.

함수가 함수를 어떻게 부르는지가 아래다. Java 쪽의 객체 모델 자리에 Clojure 쪽에서는 이 그림이 놓인다 — 다형 함수가 갈리는 자리에는 판별값이 무엇일 때인지를 적었다.

PaySchedule · PayClassification · PayDisposition 은 네임스페이스이고 소스 파일이지 클래스가 아니다. 인스턴스를 만들지 않고, 객체지향의 뜻으로 객체를 나타내지도 않는다. 그렇다고 이 해법에 객체가 없는 것은 아니다 — 직원, 지급 지시서, 심지어 pay-class 와 disposition 이 객체다. 다만 객체지향 언어에서만큼 메서드가 강하게 붙어 있지 않을 뿐이고, 그 객체들이 지나가는 함수가 있다.

이 소절이 세운 것다형성은 판별 함수로 서고, 의존 역전이 같은 자리에 경계를 긋는다

인터페이스 없이 묻기만 하는 방법은 defmulti 였다 — 타입이 아니라 판별 함수의 결과로 갈린다. 점선은 호출보다 아래에 선언된 구현이 있는 자리, 곧 의존이 뒤집힌 자리에 그어진다. 인터페이스를 따로 떼어 내면 그림이 Java 와 같아진다. 이제 두 그림을 나란히 놓고 무엇이 같고 무엇이 다른지 센다.

Clojure 에서 네임스페이스와 소스 파일은 깊이 묶여 있다. 네임스페이스마다 파일 하나, 파일 이름은 네임스페이스 이름을 따른다 — Java 가 public 클래스를 같은 이름의 파일에 넣게 하는 것과 매우 비슷하다. 그래서 네임스페이스를 클래스 비슷한 것으로 봐도 대체로 나쁘지 않다.

저자가 경고하는 유혹이 하나 있다. 클래스로 나누라고 강제하는 구조가 없으니 함수를 손 가는 대로 네임스페이스에 묶기 쉽고, 그러면 파일 구조가 있어야 할 것보다 엉성하고 부서지기 쉽게 된다. 그래서 함수형을 쓸 때도 객체지향의 분할 규율을 계속 적용하는 것이 나쁘지 않다고 적는다.

불변식이 장의 판정

아키텍처 관점에서 두 스타일은 거의 차이가 없다. 함수형 프로그램은 데이터 흐름을 조절하는 배관이고 가변 객체지향 프로그램은 객체를 한 걸음씩 도는 절차라 다르지만, 함수형의 함수도 객체지향과 같은 종류의 아키텍처 요소로 나눌 수 있다.

미룬 것 — 함수형에도 객체는 있되 그 객체가 함수와 덜 단단히 묶여 있다. 그것이 장점인지 단점인지는 뒤 장에서 계속 살핀다. 그리고 설계와 아키텍처로 갈수록 함수형과 불변 객체의 객체지향 사이의 차이는 점점 덜 중요해질 것이라고 예고한다.

이 소절이 세운 것그림은 같고, 상자의 정체와 객체·함수의 거리만 다르다

Java 와 Clojure 의 아키텍처도는 같은 모양이다. 다른 것은 상자가 클래스가 아니라 네임스페이스라는 것과, 객체에 메서드가 붙어 있지 않다는 것 둘이다. 첫째는 판정이 났고 둘째는 미뤄졌다. 아래는 이 결론을 이 장이 받았던 물음으로 되돌린다.

이 절이 세운 것다형성은 함수형에서도 서고, 경계도 같은 자리에 그어진다

이 절이 있는 이유로 돌아온다 — 객체지향의 가장 이로운 속성이 함수형에서도 서는가였다. 선다. defmulti 가 인터페이스의 일을 하고, 구현이 호출보다 아래에 놓여 의존이 뒤집히며, 그 자리에 아키텍처 경계가 그어진다. 인터페이스를 떼어 내면 그림이 Java 와 같아진다.

다만 한 가지가 남는다. 함수형의 객체는 해시맵이고 아무나 아무것이나 넣을 수 있다. 그 불안이 다음 장의 출발점이다.

4타입 — 컴파일러 없이 타입의 온전함을 지키는 법

이 절의 목표해시맵 객체에 타입이 없다는 불안을 저자가 무엇으로 푸는지, 그리고 정적·동적 타입 논쟁에서 어디에 서는지 본다.
왜 여기 있나9장의 객체는 해시맵이었다. 급여 칸에 문자열이, 지급 주기 칸에 정수가 들어가도 컴파일러는 모른다. 9장이 세운 아키텍처가 그 위에 서 있으니 이 불안을 풀지 않으면 9장의 결론이 반쪽이다.

무엇이 불안한가 — 해시맵은 무타입이다

여기서 읽을 것 — 불안의 정확한 크기. 전부가 위험한 것이 아니라 어디까지는 시험이 막고 어디부터 못 막는지.

앞 장이 남긴 것은 이렇다. 객체라고 부른 것은 그냥 해시맵이고 완전히 무타입이다. 누구든 아무 제약 없이 아무것이나 넣을 수 있다. :pay-class 의 급여 칸에 숫자 대신 문자열이, :schedule 칸에 키워드 대신 정수가 들어가도 컴파일러는 검사하지 않는다. 저자의 말로는 "온갖 지옥이 열릴 수 있다".

많은 함수형 언어와 많은 객체지향 언어가 그 지옥을 막으려고 정적 타입을 택했다. Clojure · Python · Ruby 는 다른 수단에 기댄다.

주의TDD 가 막아 주는 것과 못 막는 것

TDD 를 하는 사람은 보통 이 지옥을 크게 걱정하지 않는다. 시험이 주고받는 객체가 제대로 만들어졌는지를 대체로 보장하기 때문이다. 그래도 객체 전체가 꽤 복잡해지는 큰 시스템에서는, 동적 타입 언어가 (그리고 대부분의 정적 타입 언어조차) 주는 것보다 더 형식적이고 완전한 타입 온전성 수단이 필요하다.

이 소절이 세운 것시험이 대부분을 막지만, 큰 시스템에는 더 형식적인 수단이 필요하다

불안은 실재하고, TDD 가 대부분 덮는다. 남는 것은 복잡한 시스템에서의 형식적 보장이다. 저자는 그 수단으로 clojure.spec 을 쓴다 — 다음 소절이 그 명세다.

명세 — ::db 에서 위로 읽는다

불변식검사가 도는 때를 저자가 고른다

정적 타입은 컴파일할 때 전부 검사한다. 동적 타입은 검사하지 않는다. 명세는 그 둘 사이 어디든 놓을 수 있다 — 시험에서만, 특정 함수의 앞뒤에서만, 의심될 때만 켜서. 이것이 다음 소절의 판정으로 이어진다.

이 소절이 세운 것명세는 컴파일러가 아니라 시험과 함수 경계가 돌리고, 도는 때는 저자가 정한다

같은 명세를 시험의 입출력에서 돌릴 수도, 함수의 앞뒤에 걸 수도, 꺼 두었다 켤 수도 있다. 정적 타입이 "항상" 이고 동적 타입이 "결코" 라면 명세는 "원할 때" 다. 다음 소절은 그것을 정적·동적 논쟁 위에 놓는다.

이 절이 세운 것해시맵의 불안은 명세로 풀리고, 그 명세는 컴파일러보다 유연하다

앞의 두 지점은 차이를 쟀고, 뒤의 두 지점은 같음을 쟀다. 저자가 예고한 대로, 설계와 아키텍처로 갈수록 두 스타일의 차이는 덜 중요해진다.
이 소절이 세운 것앞의 둘은 차이를, 뒤의 둘은 같음을 쟀다

상태 변화가 커질수록 두 스타일이 갈린다는 것이 7·8장이고, 아키텍처와 타입의 눈으로는 다시 만난다는 것이 9·10장이다. 아래 두 목록은 9장과 10장이 각각 무엇을 남겼는지다.

9장이 남긴 것

여기서 읽을 것 — 9장에서 세운 것을 다섯 줄로. 어느 줄이 판정이고 어느 줄이 유보인지를 본다.

  • 두 언어 모두 최상위 함수는 여덟 줄이다. Java 의 run() 은 반복 — 직원마다 지급일이면 계산해서 보낸다. Clojure 는 배관 — 직원 목록이 함수 다섯을 지나 지시서가 된다.
  • 다형성은 defmulti 로 선다. 타입이 아니라 판별 함수의 결과로 갈린다. 급여 계산은 pay-class 의 첫 칸으로.
  • 구현이 호출보다 아래에 있어 의존이 뒤집힌다. 구현 파일이 정책 파일을 requires 하고, 정책은 구현을 모른다. 그 자리에 아키텍처 경계가 그어진다.
  • 인터페이스를 떼어 내면 Java 의 UML 과 같은 그림이 된다. 상자가 클래스가 아니라 네임스페이스라는 것, 인터페이스의 함수마다 다른 파일에서 구현할 수 있다는 것만 다르다.
  • 판정 — 아키텍처로는 거의 차이가 없다. 유보 — 객체가 함수와 느슨한 것의 장단. 경고 — 함수를 손 가는 대로 묶지 말고 객체지향의 분할 규율을 계속 쓰라.
이 소절이 세운 것9장의 판정은 동형이고, 유보는 객체와 함수의 거리다

다형성과 경계가 같은 자리에 선다는 것이 판정이고, 메서드가 붙어 있지 않은 객체가 좋은가는 유보다. 다음은 10장이 남긴 것이다.

10장이 남긴 것

여기서 읽을 것 — 10장에서 세운 것을 네 줄로. 이 장은 유보 없이 판정으로 닫힌다.

  • 해시맵 객체는 무타입이다. TDD 가 대부분 막지만 큰 시스템에는 더 형식적인 수단이 필요하다.
  • clojure.spec 명세가 그 수단이다. 큰 것이 작은 것을 담는 나무이고, 분량은 정적 타입 언어에서 적었을 만큼이다. ::db 에서 위로 읽는다.
  • 검사는 시험의 입출력에서, 또는 함수의 앞뒤에서 돈다. 컴파일러가 아니라 저자가 시점을 고른다.
  • 판정 — 양쪽의 최선보다 낫다. 원하는 만큼, 원하는 때, 정적 타입이 못 재는 동적 제약까지.
불변식두 장을 덮고 남는 것

함수형 프로그램의 함수도 객체지향과 같은 종류의 아키텍처 요소로 나뉘고, 그 위의 객체는 클래스 대신 명세로 타입을 얻는다. 문법이 강제하던 두 가지 — 인터페이스와 타입 — 가 문법 없이 서고, 그 대신 어디서 나누고 언제 검사할지를 저자가 고른다.

이 소절이 세운 것10장은 판정으로 닫히고, 남는 미결은 9장의 하나뿐이다

명세가 양쪽보다 낫다는 것이 10장의 판정이고 유보는 없다. 두 장을 합쳐 남는 물음은 객체와 함수의 거리 하나다. 다음 소절은 두 장이 각 스타일에 실제로 내린 판정을 표로 모은다.

그래서 어느 쪽이 나은가

여기서 읽을 것 — 두 스타일의 잘하는 것·못하는 것·단서를 나란히 놓은 표와, 답이 난 물음과 나지 않은 물음의 경계. 책이 적은 것만 옮겼다.

객체지향 (Java 코드)함수형 (Clojure 코드)
잘하는 것나누는 구조를 문법이 강제한다. 클래스가 파일을 강제하고 인터페이스가 경계를 강제한다. 저자는 이 분할 규율을 함수형에서도 계속 쓰라고 권한다인터페이스의 함수마다 다른 파일에서 구현할 수 있고, 타입 검사를 원하는 만큼 원하는 때 돌릴 수 있다. 정적 타입이 못 재는 동적 제약도 명세로 적는다
못하는 것타입 시스템이 표현하지 못하는 제약이 있다. 저자는 "대부분의 정적 타입 언어조차" 큰 시스템에 필요한 만큼의 타입 온전성을 주지 못한다고 적는다객체가 무타입이다. 명세 없이는 아무나 아무것이나 넣는다. 그리고 함수를 손 가는 대로 묶기 쉬워 파일 구조가 엉성해지기 쉽다
저자가 단 단서아키텍처로는 함수형과 거의 차이가 없다 — 우위의 근거가 되지 못한다객체가 함수와 느슨히 묶인 것이 장점인지 단점인지는 뒤 장에서 계속 살핀다
9장은 어느 쪽 손도 들지 않고 동형이라고 답한다. 10장은 스타일이 아니라 타입 검사의 방식에 대해 판정하고, 그 판정은 명세 쪽이다.
그래서답이 난 것과 나지 않은 것

답이 났다 — 아키텍처. 함수형 프로그램도 객체지향과 같은 종류의 아키텍처 요소로 나뉘고 같은 자리에 경계가 선다. 다형성은 defmulti 로, 경계는 의존 역전으로.

답이 났다 — 타입. 무타입 해시맵의 불안은 명세로 풀리고, 저자는 그 명세가 정적·동적 양쪽의 최선보다 낫다고 판정한다.

답이 나지 않았다 — 객체와 함수의 거리. 함수형의 객체는 메서드가 강하게 붙어 있지 않다. 그것이 장점인지 단점인지를 저자는 "뒤 장들에서 계속 살핀다" 고 적고, 설계와 아키텍처로 갈수록 그 차이가 덜 중요해질 것이라고만 예고한다.

이 소절이 세운 것아키텍처와 타입은 답이 났고, 객체와 함수의 거리는 남았다

9장은 동형을, 10장은 명세를 답했다. 어느 칸도 한쪽의 완승이 아니다. 다음 소절은 남은 물음이 어느 장으로 이어지는지다.

여기서 미뤄진 물음과 그것이 이어지는 곳

여기서 읽을 것 — 남은 물음과 이 장들이 쓴 도구가 뒤의 어느 장에서 다시 나오는지. 제목으로 짚은 것이라 내용은 그 장을 읽어야 안다.

  • 11장 데이터 흐름 — 9장이 함수형 코드를 UML 대신 데이터 흐름도로 그렸다. 저자는 흐름도가 아키텍처 결정을 보이는 데는 UML 만 못하다고 했다. 그 흐름도가 설계 도구로 어디까지 가는지가 여기다.
  • 12장 SOLID — 9장의 의존 역전과 아키텍처 경계, 그리고 "객체지향의 분할 규율을 계속 쓰라" 는 권고가 원칙의 이름으로 다시 나올 자리다. 저자는 "원칙 · 패턴 · 아키텍처를 살피며 더 보겠다" 고 예고했다.
  • 16장 디자인 패턴 되짚기 — 9장의 Java 코드가 쓴 Strategy 패턴이 함수형에서 어떤 모양이 되는지. defmulti 가 그 답의 일부다.
이 소절이 세운 것미뤄진 물음은 11장·12장·16장으로 이어진다

데이터 흐름도가 설계 도구가 되는가, 의존 역전이 원칙으로 서는가, Strategy 가 함수형에서 어떤 모양인가 — 셋이 9장의 흐름도 한 장, 뒤집힌 requires 한 줄, defmulti 셋에서 각각 출발한다.

이 절이 세운 것네 장을 잇는 선 하나와, 미뤄진 물음 하나

이 절이 있는 이유로 돌아온다 — 흩어진 조각을 한 화면에 모으려던 것이었다. 모으면 선 하나가 남는다. 상태 변화가 커질수록 갈리던 두 스타일이, 아키텍처와 타입의 눈으로는 다시 만난다. 답이 난 것은 아키텍처의 동형과 타입의 명세이고, 답이 나지 않은 것은 객체와 함수의 거리다. 그 물음은 뒤 장으로 간다.
