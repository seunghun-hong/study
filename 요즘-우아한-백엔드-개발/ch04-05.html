14장 · 5장 한눈에 — 조회 구조와 비동기 처리는 남겼다

이 절의 목표 4장과 5장에 함께 던질 물음(운영 중인 구조에서 무엇을 그대로 두고 무엇을 바꿨나)과 두 장의 답을 안다
왜 여기 있나 4장과 5장은 서로 다른 시스템의 이야기라, 같은 물음 하나로 두 장을 읽어야 장마다 얻은 것을 서로 비교할 수 있다.

4장과 5장은 모두 이미 운영 중인 서버의 구조를 바꾼 이야기다. 4장은 배달 주소가 어느 행정동 · 법정동에 드는지 답하는 C++ 서버를 자바 · 스프링부트로 옮겼고, 5장은 대용량 엑셀을 만들어 메일로 보내는 비동기 작업을 카프카에서 RDB 기반 Task 큐로 옮겼다. 5장의 엑셀은 워커(백그라운드에서 실제 작업을 수행하는 서버)가 만들고, 새 구조에서는 워커가 Heartbeat(살아 있음을 알리려 주기적으로 보내는 신호)로 살아 있음을 알린다.

두 장에 함께 던질 물음은 운영 중인 구조를 바꿀 때 무엇을 그대로 두고 무엇을 바꿨는가이다. 4장과 5장은 이어지는 이야기가 아니라 같은 물음에 저마다 답하므로, 두 장의 답을 한 테이블에서 먼저 보고 까닭은 본문에서 찾는다.

물음4장 C++ → 자바5장 카프카 → RDB Task 큐
그대로 둔 것동 데이터(전국 행정동 · 법정동 데이터)를 메모리에 올려 이진 탐색으로 찾는 조회 구조요청은 바로 받고 뒤에서 엑셀을 만들어 메일로 보내는 비동기 처리
바꾼 것언어와 웹 서버(C++ → 자바 · 스프링부트), 싱글 스레드 → 멀티스레드작업을 넘기는 큐(카프카 메시지 → RDB 테이블 행)와 엑셀을 만드는 서버가 살아 있는지 보는 방식
바꾼 까닭비교적 작은 실수에도 서버 전체가 멈출 위험, 팀의 C++ 유지보수 어려움, 공통 배포 · 모니터링을 붙이기 어려움30분 넘는 작업 중 카프카가 살아 있는 서버를 죽은 것으로 보고 같은 작업을 다시 넘겨 메일이 2번 나감
바꾼 뒤 남은 일힙의 큰 데이터가 GC 로 CPU 를 주기적으로 올려, 객체 대신 기본 자료형인 Primitive Type 저장을 늘렸다책은 DB 를 계속 조회하는 부하와 폴링 주기(3초)만큼의 처리 시작 지연을 허용할 만하다고 봤다

두 장의 전환점 — 남긴 메모리 조회와 틀린 생존 판정이 흐름을 바꿨다

여기서 읽을 것 — 띠의 단계마다 이어진 소절과, 그 소절에서 찾을 물음. 4장 쪽은 C++ 서버를 옮긴 까닭, 메모리 조회 구조를 남긴 결정, GC 와 Primitive 컬렉션이다. 5장 쪽은 중복 발송을 낳은 max.poll.interval.ms, 작업 행과 Heartbeat 다.

4장 · 5장 흐름이 바뀌는 다섯 단계
  1. 1 C++ 서버를 옮긴 까닭 성능은 충분했던 서버를 운영 위험 때문에 옮긴다찾을 것 — 옮기기 전에 정한 두 전제, 성능(서버 대수를 늘리지 않는다)과 장애 최소화(문제가 보이면 바로 되돌린다)가 뒤의 결정을 어떻게 정하나 C++ 서버를 옮긴 까닭 — 비교적 작은 실수에도 전체가 멈출 수 있었다
  2. 2 메모리 조회 구조를 남긴 결정 캐시 레이어 대신 기존 메모리 조회를 유지한다찾을 것 — 캐시 레이어를 두는 안 대신 메모리 조회 구조를 고른 근거는 무엇인가 동 데이터 저장 위치 — 캐시 레이어 대신 메모리에 둔다
  3. 3 GC 문제와 Primitive 컬렉션 GC 설정 대신 저장 자료형을 바꿔 GC 를 줄인다찾을 것 — 저장 방식을 바꾼 효과가 메모리를 덜 써서만인가 Primitive 컬렉션 — GC 설정보다 저장 자료형을 먼저 바꿨다
  4. 4 카프카가 중복 발송을 낳은 흐름 30분 넘는 작업이 카프카의 max.poll.interval.ms(poll() 사이 최대 5분)를 넘긴다찾을 것 — 카프카가 살아 있는 워커를 죽은 것으로 판정하는 조건 카프카 구조의 중복 발송 — 긴 작업 중인 워커가 죽은 것으로 판정됐다
  5. 5 작업 행 · Heartbeat · 복구 작업 행의 상태와 Heartbeat 로 작업을 넘기고, 실패한 작업과 멈춘 작업은 서로 다른 함수가 대기 상태로 되돌린다찾을 것 — 카프카의 max.poll.interval.ms 를 무엇이 대신하나 Redis 분산 락으로 작업 선점 — Heartbeat 는 따로 돈다

띠는 모든 소절이 아니라 두 장의 흐름이 바뀌는 소절만 실었다. 4장에서는 둘째 단계에서 남긴 메모리 조회 구조가 셋째 단계의 GC 문제를 낳고, 5장에서는 넷째 단계에서 틀린 생존 판정을 다섯째 단계의 Heartbeat 가 대신 맡는다.

24장 C++ 서버의 자바 전환 — 조회 구조를 남기고 GC 를 덜었다

이 절의 목표 C++ 서버를 자바로 옮긴 까닭과 전제, 전환에서 남긴 구조와 바꾼 구조, 배포 뒤 생긴 GC 문제와 그 해결을 안다
왜 여기 있나 성능이 좋던 서버를 더 느린 언어로 옮기면서 성능을 어떻게 지켰고, 배포 위험을 어떻게 줄였는지가 4장에서 읽을 것이다.

4장의 서버는 배달 주소의 위경도를 받아 어느 행정동 · 법정동에 드는지 답한다. 홈 화면 진입부터 쿠폰 발급 · 주문까지 쓰여, 피크 시간에는 전체 서버 기준 1분에 80만 개 이상의 동 데이터 요청을 받는다.

책은 맺음에서, 자바로 옮긴 뒤 처음 목표대로 더 적은 비용의 서버로 같은 트래픽을 문제없이 처리할 수 있게 됐고 모니터링과 유지보수도 더 간편해졌다고 적었다(112쪽). 비용이 얼마나 줄었는지와 서버 대수가 달라졌는지, 모니터링과 유지보수가 어떻게 간편해졌는지는 책이 적지 않았다.

C++ 서버를 옮긴 까닭 — 비교적 작은 실수에도 전체가 멈출 수 있었다

여기서 읽을 것 — C++ 서버가 운영에서 겪던 위험과, 팀이 정한 성능 전제 · 장애 최소화 전제의 대응

기존 서버는 C++ 로 짠 웹 서버로, 서버 한 대가 피크 시간에 2000 TPS(초당 처리하는 트랜잭션 수)를 넘는 요청에 10ms 이하로 응답했다. 동 데이터는 S2 Geometry(구 모양의 지구를 2차원 평면 셀로 나눠 다루는 구글의 공간 데이터 기술) 형태로 가공해 둔다.

문제는 성능이 아니라 운영이었다. 라이브러리 입력 포맷이 맞지 않거나 메모리를 잘못 다루는 비교적 작은 실수에도 서버 전체가 멈출 수 있었다. 팀은 C++ 전문성이 자바보다 낮은 데다 처음 개발한 사람도 없었고, 사내 공통 배포 · 모니터링 시스템도 붙이기 어려웠다.

전제걱정한 것팀이 정한 대응
성능자바는 JIT 컴파일(실행 시점에 컴파일하는 기법)로도 C++ 만 못하고, GC 가 큰 S2 데이터에 걸림돌이다성능이 지나치게 낮아 서버 비용이 늘면 전환을 원점부터 다시 검토한다
장애 최소화전사에서 쓰는 서버라 이슈가 생기면 전면 장애로 이어지기 쉽다Canary 배포(일부 트래픽에만 새 버전을 노출하고 넓히는 배포)를 여러 번 하고 빠르게 롤백할 방법을 찾는다
팀은 성능과 장애 최소화를 염두에 두고 전환 방식과 배포 방식을 검토했다.

팀이 장애 최소화를 전제로 둔 데에는 까닭이 하나 더 있다. 언어부터 HTTP 요청 처리 구조, 배포와 모니터링 파이프라인까지 새로 짜는 만큼, 이슈는 언제나 날 수 있다고 봤다.

기존 C++ 모듈 — 싱글 스레드라 자바에 여지가 있었다

여기서 읽을 것 — 기존 서버의 스레드 모델 · 데이터 저장 구조와, 자바로 옮길 때 그대로 쓴 S2 라이브러리

검토는 기존 모듈 구조를 파악하는 데서 시작했다. 기존 서버는 저수준 HTTP 라이브러리를 쓴 C++ 프로젝트였고, 팀은 자바 · 스프링부트로 옮기며 HTTP 요청 처리 구조도 새로 작성했다. 기존 서버가 스레드 하나로 돈다는 점은 희소식이었다.

항목기존 C++ 모듈자바 전환에서
멀티스레딩이벤트 루프(결과를 기다리지 않고 다음 작업을 처리하는 비동기 방식) 기반 싱글 스레드멀티스레드를 쓰면 자바가 느려도 비슷하거나 더 높은 성능을 낼 수 있다고 추측했다
데이터 저장 구조DB 없이 전국 S2 데이터를 정렬된 배열로 외부 스토리지에 두고, 기동 때 내려받아 메모리에서 이진 탐색으로 찾는다그대로 둘지 바꿀지 따로 검토했다
기존 서버가 스레드 하나로 2000TPS 를 냈으므로, 자바가 느려도 스레드를 여럿 쓰면 따라잡을 수 있다고 책은 추측했다.

S2 라이브러리는 비슷한 인터페이스의 자바 구현체가 있었다. 기능이 모두 호환되지는 않지만 필요한 기능은 다 있어 그대로 썼고, 성능 자료를 찾지 못해 뒤의 성능 테스트로 검증했다.

동 데이터 저장 위치 — 캐시 레이어 대신 메모리에 둔다

여기서 읽을 것 — 1안 캐시 레이어와 2안 메모리 조회 유지의 하는 일 · 좋은 점 · 드는 것, 팀이 고른 안의 근거

기존 구현은 전체 동 데이터를 메모리에 올리고 이진 탐색으로 찾았다. 팀은 구조까지 고칠지, 구조는 그대로 두고 언어만 안정적으로 옮길지를 놓고 검토했다.

데이터가 자주 바뀌지 않는다는 점을 들어 팀은 전환이 서비스에 주는 영향을 줄이려 기존과 같은 2안을 골랐고, 필요해지면 캐시나 DB 레이어를 다시 검토하기로 했다. 이 선택으로 동 데이터는 기동 때마다 자바 힙에 굉장히 많은 수의 객체로 올라가고, 배포 뒤의 GC 문제는 바로 여기서 나온다.

여기서 읽을 것 — nGrinder 부하 테스트 결과로 성능 전제를 어떻게 판단했는지, Canary 단계마다 넓혀 간 트래픽과 확인한 것, ALB TargetGroup 으로 신규 서버에 보낼 비율을 나눈 방법

기존 서버와 같은 대수로 피크 트래픽을 받으려면 한 대가 2000TPS 이상을 처리해야 했다. nGrinder(가상 사용자를 만들어 서버에 부하를 주는 성능 테스트 도구)로 성능에 가장 영향이 큰 API 에 부하를 준 결과 최대 약 3,500 TPS 가 나와, 전환해도 성능에 문제가 없다고 판단했다.

정의 Canary 배포

Canary 배포는 전체 사용자에게 한 번에 배포하지 않고 일부 트래픽에만 신규 버전을 노출하여 문제를 확인한 후 점진적으로 확대하는 배포 방식이다. 장애가 나도 영향은 새 버전을 노출한 트래픽에 그친다.

팀은 Canary 배포를 여러 번으로 나눠 짧게 열고 롤백하기를 되풀이했다. Canary 를 오래 두면 전면 장애가 아닌 특정 조건의 이슈가 발견되지 않은 채 오래 갈 수 있어서다.

배포 뒤 CPU 스파이크 — Major GC 에서 왔다

여기서 읽을 것 — 배포 뒤 응답 시간 지표가 어떻게 바뀌었는지, Ramp-Up 테스트가 스파이크를 놓친 까닭, Major GC 한 번의 단계(Concurrent Mark · Pause Remark)와 CPU 스파이크의 관계

배포는 중간에 의심스러운 지표로 잠시 롤백하는 등 이슈는 있었지만 장애 없이 끝났다. 응답 시간의 MAX 는 눈에 띄게 줄었는데, 책은 기존 서버가 이벤트 루프 방식이라 간혹 지연이 있었던 것으로 추측한다. AVG · p99 · p95 응답 시간은 퍼센트로는 크게 늘었지만, 팀은 목표 성능을 만족했다고 판단했다(응답 시간의 목표 수치는 책이 적지 않았다).

CPU 가 주기적으로 오르는 현상도 보였다. 성능 테스트는 Ramp-Up(낮은 트래픽부터 최고 트래픽까지 부하를 차츰 올리는 테스트 방식)이라, 중간 수준 트래픽을 오래 유지할 때 발생하는 CPU 스파이크를 잡지 못했다.

CPU 는 GC 로 힙 사용량이 떨어질 때마다 오르지 않고 2번에 1번꼴로 올랐다(책이 힙 그래프와 CPU 그래프를 비교해 본 것, 105쪽). GC 로그를 보니 Major GC(Old 영역까지 정리하는 G1 의 Concurrent Cycle)가 잦았고, Major GC 시점에 CPU 가 크게 올랐다.

전체 데이터를 힙에 두니 대부분이 Old 영역(오래 살아남은 객체가 놓이는 힙 영역)에 놓여 Major GC 가 쉽게 일어나고, 마킹할 객체도 많아 오래 걸린다고 책은 추측했다. jstat 으로 보니 Old 영역 사용률도 높았다.

Primitive 컬렉션 — GC 설정보다 저장 자료형을 먼저 바꿨다

여기서 읽을 것 — GC 튜닝 대신 검토한 두 방식과 고른 fastutil, 개선 전후 테스트에서 Major GC 가 어떻게 달라졌는지, 힙 크기를 바꾼 추가 테스트로 책이 내린 해석

팀은 IHOP(GC 가 언제 수행될지를 조절하는 임곗값) 같은 GC 튜닝보다 메모리 저장 구조 개선이 먼저라고 판단했다(108쪽). 저장 구조 개선을 먼저 고른 까닭은 책이 적지 않았다. 검토한 방식은 인메모리 데이터 스토어와 Primitive 컬렉션이다.

정의 Primitive 컬렉션

Primitive 컬렉션 방식은 많은 수의 객체로 저장하던 데이터를 대부분 Primitive Type 으로 저장하도록 최적화해 GC 가 볼 객체 수를 줄이는 방식이다. 예를 들어 List<Long> 은 값마다 Long 객체를 하나씩 만들지만, fastutil 의 LongArrayList 는 값을 long 배열 하나에 담는다. List<Long> 과 LongArrayList 는 문서의 일반 예이고, 책은 바꾼 자료구조를 싣지 않았다.

Primitive 컬렉션 라이브러리들은 기능과 벤치마크에 큰 차이가 없어, 팀은 인지도가 가장 높고 최근 활동도 활발해 보이는 fastutil(Primitive Type 컬렉션을 지원하는 자바 라이브러리)을 골랐다. 그리고 fastutil 로 데이터를 최대한 Primitive Type 으로 저장하게 고쳤다.

35장 엑셀 생성 큐 — 카프카를 RDB Task 큐로 바꿨다

이 절의 목표 엑셀 생성 작업을 카프카에서 RDB Task 큐로 옮긴 까닭과, 작업 행에 담긴 진행 상태 · 마지막 생존 신호 시각 · 재시도 횟수와 Redis 분산 락이 저마다 무엇을 맡아 중복 · 유실 · 장애를 다루는지 안다
왜 여기 있나 메시지 큐라는 흔한 선택이 오래 걸리는 작업에서 오히려 중복 발송을 낳았다. 작업 시간이 큐 선택을 어떻게 바꾸는지가 5장에서 읽을 것이다.

전자계약서 시스템은 여러 업무용 대용량 엑셀을 만들어 이메일로 보낸다. 조건에 따라 만드는 데 오래 걸려, 화면에서 결과를 기다리지 않게 카프카로 비동기 처리했다.

카프카 구조의 중복 발송 — 긴 작업 중인 워커가 죽은 것으로 판정됐다

여기서 읽을 것 — 엑셀 생성이 30분을 넘은 까닭, max.poll.interval.ms 와 리밸런싱이 같은 이벤트를 다른 워커에 넘긴 경위, 그 설정값을 늘리는 방법의 한계

어드민에서 엑셀 생성을 요청하면 API 서버(프로듀서)가 카프카에 이벤트를 발행하고, 워커(백그라운드에서 실제 작업을 수행하는 서버)가 컨슈머로 이벤트를 소비해 엑셀을 만든 뒤 메일로 보낸다. 발송이 끝나야 워커가 카프카에 ACK(메시지를 정상 처리했다는 확인 응답)를 보낸다.

처음에는 대부분 10분 안에 끝났지만, 행마다 API 호출이 필요한 새 엑셀 타입이 생기며 데이터 조회만 30분 넘게 걸렸다. 카프카는 poll()(컨슈머가 카프카에서 메시지를 가져오는 호출) 사이의 간격이 max.poll.interval.ms(poll() 호출 사이에 허용하는 최대 시간, 여기서는 5분)를 넘으면 컨슈머가 죽었다고 본다. 그러면 리밸런싱(컨슈머 그룹의 파티션 할당을 다시 조정하는 과정)으로 같은 메시지를 다른 컨슈머에게 넘긴다.

max.poll.interval.ms 를 1시간으로 늘리고 싶어지지만 근본 해결이 아니다. 1시간 30분 걸리는 작업에서 같은 문제가 다시 나고, 무엇보다 실제 워커 장애를 알아채는 데 1시간이 걸린다.

ACK 를 앞당긴 핫픽스 — 중복은 막고 유실은 못 막는다

여기서 읽을 것 — 기존 listen() 과 핫픽스 listen() 에서 ACK 줄이 옮겨 간 위치와, 그 뒤 오류 · 배포 때 이벤트가 어떻게 되는지

중복 발송은 실제 운영 업무에 바로 영향을 주는 문제라, 근본 해결 전에 핫픽스를 넣었다. listen() 은 카프카 메시지를 받는 함수이고 엑셀은 excelCreateManager.createExcel() 이 만든다. 핫픽스는 createExcel() 을 코루틴(코틀린의 가벼운 비동기 실행 단위)으로 넘겨 백그라운드에서 돌리고, listen() 이 ACK 를 바로 보내게 바꿨다.

책 117쪽 — 기존 listen()
1// 기존: 엑셀 생성 완료 후 ACK
2fun listen(message: Message, ack: Acknowledgment) {
3 excelCreateManager.createExcel(message) // 30분 이상 소요
4 ack.acknowledge() // ACK 늦음엑셀을 다 만든 뒤에야 ACK 가 나간다
5}
책 117쪽 — 핫픽스 listen()
1// 임시 해결: 비동기 처리 + 즉시 ACK
2fun listen(message: Message, ack: Acknowledgment) {
3 CoroutineScope(singleThread).launch {
4 excelCreateManager.createExcel(message) // 백그라운드에서 처리
5 }
6 ack.acknowledge() // 즉시 ACK엑셀 생성이 끝나기 전에 ACK 가 나간다
7}
엑셀 생성을 백그라운드로 넘기고 ACK 를 바로 보내, 카프카가 워커를 죽은 것으로 보지 않게 했다.

책은 listen() 의 두 버전만 실었고 둘러싼 클래스는 싣지 않았다

엑셀 생성을 코루틴으로 넘기면 listen() 이 바로 끝나 다음 poll() 이 5분 안에 오므로, poll() 사이의 간격이 max.poll.interval.ms 를 넘지 않아 리밸런싱이 일어나지 않는다. 그러나 ACK 를 먼저 보냈기 때문에 뒤에서 오류가 나도 이벤트가 다시 오지 않아 작업을 잃고, 배포나 장애로 프로세스가 멈추면 처리 중이던 이벤트를 복구하지 못한다. 그래서 팀은 장시간 비동기 작업에 카프카가 꼭 필요한지부터 다시 논의했다(118쪽).

카프카 없이 갖출 요구사항 — RDB 저장과 Heartbeat 로 채운다

여기서 읽을 것 — 카프카 도입 때 기대한 탄력 대응과 확장을 실제로 누렸는지 본다. 이어 요구사항마다 그것을 채우는 것을 본다 — RDB 테이블 행, Heartbeat, Fallback 스케줄러, handleRetry(), 워커, Redis 분산 락.

팀은 요청 처리와 실제 처리를 분리해 순간적인 트래픽 변화에 탄력적으로 대응하고, 필요하면 컨슈머 그룹(같은 Topic 을 함께 구독해 부하를 나눠 처리하는 컨슈머들)을 확장할 수 있으리라 기대하고 카프카를 도입했다. 그러나 책은 실제 운영에서 탄력 대응과 확장이라는 기대를 거의 누리지 못했다고 적었다. 엑셀 발송은 트래픽이 폭발적으로 증가할 일이 없었다. 프로듀서와 컨슈머가 모두 같은 서비스 안에 있어 컨슈머 그룹을 여러 개로 늘릴 필요도 없었다.

오히려 작업이 오래 걸려 max.poll.interval.ms 를 자주 넘겼고, 그렇다고 늘리면 실제 장애를 늦게 아는 딜레마가 생겼다. 책은 같은 서비스 안에서 발행하고 소비하는 장시간 비동기 작업에는 카프카가 필요 없다고 결론짓고, 새 구조가 갖출 요구사항을 정리했다.

새 구조는 엑셀 생성 작업을 RDB 에 영구 저장하고, 워커가 Heartbeat(살아 있음을 알리려 주기적으로 보내는 신호)를 갱신하며 작업 상태를 관리한다. 여러 워커 가운데 하나만 작업을 잡게 하는 Redis 분산 락도 쓴다. 외부 API 실패 같은 일시적 오류로 실패한 작업은 handleRetry() 함수가 재시도 횟수를 하나 늘려, 3회 미만이면 다시 대기 상태로 돌리고 3회에 이르면 최종 실패로 끝낸다.

RDB Task 큐의 구조 — 작업 한 건이 테이블 한 행이다

여기서 읽을 것 — excel_download_request 테이블의 컬럼과 status 값, 그림 5.2 에서 API · 워커 · Fallback 스케줄러가 행을 바꾸는 순서

정의 RDB 기반 Task 큐

엑셀 생성 작업을 RDB 에 영구적으로 저장하고, 워커가 주기적으로 Heartbeat 를 갱신하며 작업 상태를 관리하는 구조다. 카프카 구조에서는 메시지 하나가 작업 하나를 담았고, 새 구조에서는 테이블 행 하나가 담는다.

엑셀 생성 요청은 excel_download_request 테이블에 영구 저장되는 작업(task) 행이 된다. 행의 status 는 PENDING(대기) · IN_PROGRESS(처리 중) · DONE(완료) · FAILED(최종 실패) 가운데 하나다. 행에는 마지막 Heartbeat 시각(last_heartbeat_at)도 함께 들어 있으므로, 워커가 멈추거나 재시작해도 행을 보고 작업을 복구할 수 있다.

그림 5.2 의 이름 몇 개는 책 121쪽의 DDL · 123~124쪽의 코드와 다르다(DDL 은 그림 뒤 컬럼 테이블에 옮겼다). 그림의 COMPLETE · FAIL 은 DDL 과 코드의 DONE · FAILED, lastHeartbeatAt 은 last_heartbeat_at, HeartbeatUpdater 는 뒤에서 볼 executeTask() 의 Heartbeat 코루틴에 해당한다. 갱신 주기도 그림은 delay(10초), 코드는 delay(60_000)(1분)이라, 본문은 DDL 과 코드를 따라 DONE · FAILED 와 1분으로 쓴다.

그림 5.2 는 왼쪽 위에서 시작한다. 번호 (1)~(4) 와 오른쪽 FallbackSupport Scheduler(본문의 Fallback 스케줄러, 코드의 fallbackSupportScheduler())를 따라 읽는다.

여기서 읽을 것 — 워커가 후보 20건 가운데 2건만 잡는 코드와 그 개수의 까닭, 엑셀 생성 중에 Heartbeat 를 갱신하는 executeTask() 의 코루틴

작업을 잡으면 executeTask() 가 바로 status 를 IN_PROGRESS 로 바꾸고 락을 푼다. 락은 filter 안의 tryLock() 으로 잡은 때부터, executeTask() 가 status 를 IN_PROGRESS 로 바꾼 뒤 unlock() 할 때까지 쥔다. status 가 바뀐 뒤에는 WHERE status = 'PENDING' 조회에 나오지 않으므로, 다른 워커가 새로 조회해 잡을 일이 없다.

락이 풀린 뒤, 다른 워커가 앞서 읽어 둔 후보 목록으로 같은 작업의 락을 잡는 경우는 책이 다루지 않았다. 실린 코드에는 락을 잡은 뒤 status 를 다시 확인하는 줄이 없고, updateStatus() 의 안은 실리지 않았다.

재시도와 장애 복구 — 실패와 중단을 다른 함수가 맡는다

여기서 읽을 것 — handleRetry() 의 재시도 조건, 실패 & 재시도 시나리오에서 작업 행의 값 변화, Fallback 스케줄러가 멈춘 작업을 고르는 SQL 조건과 ShedLock

엑셀 생성 중 외부 API 실패나 일시적 네트워크 오류가 나면 executeTask() 가 handleRetry() 를 호출한다. handleRetry() 는 재시도 횟수를 하나 올려 3회 미만이면 PENDING 으로 되돌려 다른 워커가 다시 잡게 하고, 3회에 이르면 FAILED 로 끝낸다. 그래서 retry_count 에 저장되는 값은 2까지다.

retry_count 로 재시도가 되는데도 Fallback 스케줄러를 따로 두는 까닭을 책은 배포에서 찾는다. Graceful shutdown(진행 중인 작업이 끝나기를 기다렸다가 서버를 내리는 종료 방식)을 쓰면 배포가 30분~1시간씩 늦어지므로, 워커는 배포 때 엑셀 생성을 기다리지 않고 바로 종료한다. 서버가 갑자기 다운될 때도 복구 장치가 있어야 한다.

Fallback 스케줄러가 여러 워커에서 함께 돌면 같은 작업이 여러 번 복구될 수 있다. 그래서 ShedLock(같은 스케줄을 여러 인스턴스가 동시에 실행하지 못하게 하는 라이브러리)의 @SchedulerLock 으로 한 대에서만 돌게 한다.

handleRetry() 와 Fallback 스케줄러는 둘 다 작업을 직접 다시 돌리지 않고 PENDING 으로 되돌리며(handleRetry() 는 셋째 실패면 FAILED 로 끝낸다), 다시 잡는 일은 PENDING 작업을 조회하는 processExcelTasks() 가 맡는다.

코드에서 확인하기 — Fallback 스케줄러는 한 대에서만 돈다

여기서 읽을 것 — 재시도와 장애 복구 소절의 Fallback 스케줄러를 코드에서 본다. @SchedulerLock 줄에서 한 대에서만 도는지, findFallbackTasks() 줄과 그 위 주석에서 Heartbeat 가 2분 넘게 끊긴 작업을 고르는지, forEach 안의 updateStatus 줄에서 그 작업을 PENDING 으로 되돌리는지 확인한다.
